= Runbook: running the whole CI gate locally
:idprefix:
:idseparator: -

The maintainer's standing direction: testing should be as simple as possible. This is that -- a contributor with only `docker`, `docker compose` and `just` on the host can run the entire CI gate (every job `.github/workflows/ci.yml` runs) with one command, no Rust/Node/psql/cratestack toolchain installed locally.

If you already have the full host toolchain (Rust, Node 26 + pnpm, `psql` 16, the pinned `cratestack` CLI) and would rather run things natively, skip to <<host-toolchain-path>> below -- this runbook's `just ci` is not the only way to test, just the simplest one.

== Prerequisites

* `docker` and `docker compose` (v2.20+ -- this uses `depends_on: condition: service_healthy` and Compose's own `run --build`, both need a reasonably current Compose).
* `https://github.com/casey/just[just]`.

Nothing else. `ci/runner/Dockerfile` builds one image with everything else this gate needs: the pinned Rust toolchain, `rustfmt`/`clippy`, `postgresql-client-16`, Node 26 + pnpm (via corepack, pinned from `packageManager` in `package.json`), `cargo-deny`, and the `cratestack` CLI pinned to the exact version `cargo xtask cratestack-pin` reads from the root `Cargo.toml`.

== The one command

[,bash]
----
just ci
----

This builds (or reuses) the runner image, starts a disposable Postgres 16 for it, and runs `just ci-inner` inside the container -- the same 21 steps `.github/workflows/ci.yml`'s eight jobs run, in the same order, against the same pinned toolchain:

. cratestack CLI matches the pin (fails loudly, with the exact rebuild command, if the image has drifted from `Cargo.toml`)
. `cargo fmt --check` + `cargo clippy --workspace --all-targets -- -D warnings`
. `cargo test --workspace` (unit + in-process)
. `cargo metadata --locked` (the committed `Cargo.lock` must be current)
. The Rust SDK (`sdks/rust/vsms-sdk-rust`) -- check, clippy, test, `aws-lc-rs` absence, `cargo publish --dry-run`
. `examples/rust` -- check, clippy
. `cargo deny check` against all five manifests (root, the Rust SDK, `ci/e2e-integration`, `examples/rust/sms-send`, `deploy/backup-tool`)
. R1/R2/R6 and every drift guard -- `cargo xtask no-raw-sqlx parity sdk-schema-check workflow-paths docs-drift r6 node-sdk-types-check`
. `0001_init` matches `cratestack migrate diff`
. `0002_bootstrap` matches the design doc
. Apply migrations for real (`cargo run -p sms-migrate`) against a fresh scratch Postgres, then `ci/test-state-machine.sql`'s assertions (it runs inside a transaction and rolls back -- no lasting effect on the database the rest of this gate reuses)
. Install the sample Node webhook receiver's own dependencies (needed by one of the live suites below)
. Every live-Postgres suite (`cargo test --workspace --no-fail-fast -- --ignored`) -- by far the slowest single step
. `pnpm install --frozen-lockfile`
. `pnpm biome ci .`
. Generate the TypeScript client and check its routes against the pinned server (`just client-check`)
. Typecheck and build (`pnpm turbo run typecheck build`)
. Test (`pnpm turbo run test`)
. The sample Node receiver's cross-language HMAC signature vectors
. The official Node SDK (`@vymalo/vsms-node`) -- build, typecheck, test, `npm pack --dry-run`
. Every mermaid diagram in `docs/architecture.md`/`docs/roadmap.md` parses (no browser)

A failing step stops the gate there (`set -euo pipefail`), with a `=== STEP n/21: ... ===` banner printed before each one so the log says exactly where it got to.

=== How long

First run is slow -- a full toolchain image build, then a cold `cargo`/`pnpm` fetch into the named volumes `compose.test.yaml` reserves for the cargo/pnpm caches (`cargo_registry`, `cargo_git`, `pnpm_store`), plus a cold `target/`/`node_modules` build inside the bind-mounted repo itself (deliberately not a named volume -- see that file's own comment on `CARGO_TARGET_DIR`). Expect a good chunk of an hour on a modest machine. Every run after that reuses those caches and the built image, and is close to what `.github/workflows/ci.yml` itself takes.

=== Fast iteration

[,bash]
----
just ci-quick
----

Everything above except the live-Postgres suites (step 13) and the JS typecheck+build (step 17) -- the two most expensive steps, and the two least likely to catch a mistake in a small, focused change. Not a substitute for `just ci` before opening a PR; a genuine "did I break something obvious" loop while iterating.

=== Running one suite by hand

[,bash]
----
just ci-shell
# now inside the container, with the same mounted repo and the same
# Postgres reachable at postgres:5432 (VSMS_TEST_DATABASE_URL is already set):
cargo test -p sms-worker --no-fail-fast -- --ignored
cargo test --test hooks_live_postgres -- --ignored --nocapture
----

=== Resetting

[,bash]
----
just ci-clean
----

Removes the `vsms-ci` Compose project entirely -- containers, network, and every named volume (Postgres data, cargo registry/git caches, pnpm store). Scoped to this project's own name only; it never touches `compose.yml`'s `vsms` project, `compose.dev.yaml`'s `vsms-dev`, `compose.demo.yaml`'s `vsms-demo`, or `sms-test-support`'s own `vsms-test-harness`. Doesn't remove `target/`/`node_modules` -- those live in the bind-mounted repo itself, like a native build's would; `cargo clean`/`rm -rf node_modules` if you want those back to zero too. Not required for correctness between runs -- only useful to reclaim disk or force a clean rebuild.

== What's actually running

`compose.test.yaml` (Compose project `vsms-ci`) is two services:

* `postgres` -- a plain, disposable `postgres:16`, no host port published (nothing outside the Compose network needs to reach it).
* `runner` -- built from `ci/runner/Dockerfile`, the repo bind-mounted read-write at `/repo`, running as uid:gid 1000:1000 (not root -- see that compose file's own comment for why: a root-owned file written into the bind-mounted working tree would be unreadable/undeletable by a non-root host user afterward). `VSMS_TEST_DATABASE_URL` points it at the `postgres` service, which is `backends/crates/sms-test-support`'s own override hook -- the harness skips trying to start its own nested `docker compose` (this container has no Docker socket to do that with anyway) and instead provisions its per-binary scratch databases directly against this URL's server.

If your host user isn't uid/gid 1000:1000, override it:

[,bash]
----
VSMS_CI_UID=$(id -u) VSMS_CI_GID=$(id -g) docker compose -f compose.test.yaml run --build --rm runner just ci-inner
----

== Verifying nothing leaked into the tree

`just ci` must leave `git status` clean of anything but the change you actually made -- `frontends/packages/sms-client` (generated by step 16) is gitignored except its own `package.json`, which `--tanstack` (see the `client-gen` recipe's own comment) keeps byte-identical to the committed copy. If `git status` shows anything under that package other than an untracked, gitignored directory, something about the client generation has drifted -- see that recipe's own comment before assuming the fix is to just commit it.

== The host-toolchain path

If you already have Rust, Node 26 + pnpm, `psql` 16, and a pinned `cratestack` CLI installed natively:

[,bash]
----
just check        # cargo check --workspace --all-targets
just lint         # fmt --check, then clippy -D warnings
just test         # unit + in-process only
just test-live    # every live-Postgres suite -- brings up its own Postgres via `compose.yml`
just all-checks    # lint, test, and the xtask guards -- NOT the live suites, deny, or the js job
----

`just all-checks` is a fast local subset, not the whole gate -- it does not run `cargo deny`, the live-Postgres suites, or anything on the TypeScript side. `just ci`/`just ci-inner` above is the only single command that runs everything CI runs; the host-toolchain recipes are for iterating on one piece without paying for a container build.

See xref:getting-started.adoc[`getting-started.adoc`] for first-time setup of that native toolchain, and `AGENTS.md`'s own "Repo automation moved to `xtask`" section for what each `cargo xtask <check>` actually does.
