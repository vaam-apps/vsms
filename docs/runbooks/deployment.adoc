= Deployment -- from a bare VM to a running stack
:idprefix:
:idseparator: -

A from-scratch deploy of §9.2's shape: Docker Compose on one VM, Caddy
terminating TLS, Postgres as the only coordination mechanism. Each step
proves something works before the next builds on it, the same convention
xref:getting-started.adoc[`getting-started.adoc`] uses -- if a step fails, stop
there rather than pushing through.

This is the automatable half. It does not decide _where_ that VM is --
https://github.com/vymalo/vsms/issues/3[#3] (cross-border data transfer
under Law No. 2024/017) blocks that decision, not this runbook.

== Known seams -- read this before you start

All three gaps this section used to name are closed, and this file was
left saying otherwise for longer than it should have -- the same
"documentation asserts something the code does not do" shape `AGENTS.md`
keeps rediscovering, found here while writing the backend-only section
below:

* *`sms-gateway register-client` exists* (`backends/apps/sms-gateway/src/main.rs`,
`Command::RegisterClient`) and registers an integrator's own Ed25519 public
key as an `AppClient` -- step 5 below uses it for the console composer's
key. The gateway never generates, sees or stores a private key; there is no
token to mint and no `provision-client` any more (deleted in VS-4).
* *`sms-gateway create-app` exists* (`Command::CreateApp`, production-readiness
audit N1) and closes what used to be a real chicken-and-egg gap: creating
the very first `App` a real production deployment sends through --
``App.create``'s own `@@allow` is `hasRole('owner') || hasRole('admin')`,
and nothing this deployment can mint over HTTP carries either role until
a human has paired a console (VS-5b), which itself needs
`sms-gateway bootstrap`/`provision-user` to have already run.
`create-app` writes through the same hand-built
`owner`-role context every other bootstrap subcommand in this file uses
-- see step 5's own note on the composer's key.
`vsms-demo-seed` (`ghcr.io/vaam-apps/vsms/demo`, a separate binary/image --
see that crate's own module doc) is explicitly not a substitute for this
in a real deployment: it's demo-only, seeds fixture data no production
`App` should carry, and isn't referenced anywhere below.
* *`backends/apps/sms-fake-orange` exists* as a real binary/image, and
`compose.demo.yaml` (repo root, not this file's own
`deploy/docker-compose.yml`) wires it in for a GHCR-only showcase -- see
that file's own header for how it differs from this runbook's
production-shaped stack. `deploy/docker-compose.yml` itself still has no
`fake-orange` profile; every step below still assumes real Orange
Cameroon `client_credentials`, except the backend-only verification
section, which points `ORANGE_CM_BASE_URL` at a manually-run
`sms-fake-orange` container instead -- see that section for exactly how.

== Prerequisites

* A VM with Docker Engine and the Compose plugin (`docker compose version`
should print v2.20+ -- `service_completed_successfully` depends-on
conditions, used below, need it).
* Two DNS records (A/AAAA) pointed at the VM -- one for the gateway's
public origin, one for the admin console. A real domain, not just an
IP: Caddy's automatic HTTPS needs one. (Testing
without public DNS: see ``deploy/Caddyfile``'s own comment for the
`tls internal` swap -- everything else below still applies.)
* Real Orange Cameroon `client_credentials` and a contracted sender ID.
Placeholder credentials get you through migrations and a running stack,
but every submit attempt fails at Orange's own OAuth endpoint -- the
same boundary xref:36-handset-gate.adoc[`36-handset-gate.adoc`] documents.
* `openssl` on your workstation, for generating a Postgres password and
the `SMS_HASH_PEPPER` step 1 below needs, and for the Ed25519 keys (the
envelope keys in step 1, the composer's key in step 5):
`openssl genpkey -algorithm ed25519`.

== 1. Clone and configure

[,bash]
----
git clone https://github.com/vaam-apps/vsms.git
cd vsms/deploy
cp .env.example .env
chmod 600 .env

# Production-readiness audit B2: deploy/docker-compose.yml's `backup`
# service mounts this as a `configs:` reference, which fails `docker
# compose up` outright ("bind source path does not exist") if the file
# is missing — required even when BACKUP_RCLONE_REMOTE ends up being a
# bare local path with no real credentials to fill in. See the "Secrets"
# section below for the full reasoning.
cp secrets/rclone.conf.example secrets/rclone.conf
chmod 600 secrets/rclone.conf

# VS-3: the signed transport's two server keys. `sms-gateway serve` refuses
# to start without both (and refuses the same key twice). Never reuse a dev
# key here; the next key is the one a later rotation promotes.
openssl genpkey -algorithm ed25519 -out secrets/envelope-current.pem
openssl genpkey -algorithm ed25519 -out secrets/envelope-next.pem
sudo chown 65532:65532 secrets/envelope-current.pem secrets/envelope-next.pem
sudo chmod 0400 secrets/envelope-current.pem secrets/envelope-next.pem
----

Fill in `.env` -- every var traces to a real `+#[arg(long, env = ...)]+` in
`backends/apps/sms-gateway/src/main.rs` / `backends/apps/sms-worker/src/main.rs`, or to a
`docker-compose.yml` service block; see that file's own comments for
which. At minimum:

[,bash]
----
# a real, random Postgres password
openssl rand -base64 24
# a real, random SMS_HASH_PEPPER (minimum 32 bytes) — #134/#140
openssl rand -base64 48
----

`secrets/envelope-current.pem` signs every response and
`secrets/envelope-next.pem` is the key the next rotation promotes. An
integrator pins the public half of *both*; print them once the stack is up with
`docker compose run --rm sms-gateway server-keys` (it needs no database) and
hand the two lines to the integrator. They are paths, not secret values, in
`.env`-land: the files are the secret.

The worker's `hooks` role seals every webhook delivery with
`secrets/envelope-current.pem` too, so a receiver pins the same two public keys
for the gateway's answers and for the deliveries it receives. Both containers
run as uid 65532, which is why the one `chown`/`chmod 0400` above serves both.

=== Rotating the envelope keys

Both processes read their key once, at start-up, so a rotation is a restart:

. Ship every client and every webhook receiver that pins the new `next` public
  key (`docker compose run --rm sms-gateway server-keys` after the swap prints
  it; an integrator pins *both* halves, so this step is what makes the
  rotation a non-event for them).
. Promote it: move `secrets/envelope-next.pem` over
  `secrets/envelope-current.pem`, mint a new `envelope-next.pem`, keep the
  `chown`/`chmod` above.
. **Restart the gateway and the worker together** (`docker compose up -d
  --force-recreate sms-gateway sms-worker`). A worker left running keeps
  sealing deliveries with the old key; receivers that still pin it accept them,
  but the moment the old key is retired from their pins every delivery from that
  worker is refused. On Kubernetes the same step is `kubectl rollout restart` of
  *both* deployments: the chart mounts the worker's key with `subPath`, and a
  `subPath` Secret mount never sees an edited Secret, so the worker will not
  pick the new key up on its own the way a directory mount eventually would.
. Retire the old public key from the receivers' pins once no delivery sealed
  with it can still be retried (a retry is sealed afresh, so after the restart
  nothing is).

`SMS_HASH_PEPPER` backs `Message.msisdnHash`/`bodyHash` (HMAC-SHA256) --
`sms-gateway serve` validates it (minimum 32 bytes) before doing anything
else, so a missing or too-short value fails the container at boot, not at
the first `sendMessage` call. Generate it once and keep it: rotating later
does not retroactively rehash rows already written under the old value --
see ``backends/crates/sms-api/src/pepper.rs``'s own module doc.

== 2. Build and bring up Postgres + migrations first

[,bash]
----
docker compose --env-file .env up -d --build postgres migrate
docker compose logs migrate
----

Expect `migrations up to date` as the last line. `migrate` is a one-shot
container (see ``backends/apps/sms-migrate/src/main.rs``'s own module doc) -- it
applies `backends/migrations/postgres/{0001_init,0002_bootstrap}` exactly
once each, tracked in a `schema_migrations` table this deploy path owns,
under a Postgres advisory lock. It never regenerates anything; the two
`up.sql` files it runs are embedded verbatim into the binary at compile
time (`include_str!`), from what's committed. If it exits non-zero,
nothing downstream is safe to start -- fix this before continuing.

== 3. Bootstrap: orange_cm Provider/Route, first operator

`sms-gateway serve` calls `resolve_provider_row_id`
(`backends/apps/sms-gateway/src/main.rs`) _before_ binding its listener, so a
fresh database makes the container exit immediately and crash-loop under
`restart: unless-stopped` if an `active` `Provider` row is missing -- *you
cannot `docker compose exec` into a container that never stays up.* (It needs
no signing key from the database: since VS-4 the gateway's only keys are the
two envelope keys of step 1.) `admin` has the equivalent gap one layer up: it
starts fine, but nobody can use it without at least one operator account.
`sms-gateway bootstrap` (production-readiness audit N2) closes both in one
idempotent call, chaining the two steps this runbook used to walk through one at
a time -- see "What `bootstrap` does" below if you need to run, or understand,
either of them individually.

*R4 (`CONTRIBUTING.md`: "the admin console is optional, the backend
must run without it") -- the command below is for a deployment bringing up the
console.* For a genuinely backend-only deployment, omit
`--owner-email`/`--owner-display-name` entirely -- `bootstrap` still creates the
`orange_cm` `Provider`/`Route` (everything `sms-gateway`/`sms-worker` themselves
need to start), and explicitly skips the owner-account step rather than either
attempting it with nothing to configure it from or silently doing nothing.
Passing one of the two without the other is refused with a named error.

[,bash]
----
docker compose --env-file .env build sms-gateway
docker compose --env-file .env run --rm sms-gateway bootstrap \
  --owner-email you@example.com \
  --owner-display-name "Your Name"
----

(Not `sms-gateway bootstrap` as the second argument -- the image's
`ENTRYPOINT` is already the binary; only the subcommand goes after the
service name.) `run --rm`, not `exec`, for the same reason every
one-off command in this runbook uses it: there is no running
`sms-gateway` service container to exec into yet. Safe to re-run against
an already-bootstrapped deployment: every step is a clean no-op the second
time.

`--owner-role-key` (default `owner`) is also available if this deployment needs
a different role -- see `Command::Bootstrap`'s own `--help` for the full flag
list.

=== What `bootstrap` does, step by step

Read this if you need one of the two steps on its own, or are debugging a
partially-bootstrapped database.

==== The `orange_cm` Provider row and a catch-all Route

`resolve_provider_row_id` in `backends/apps/sms-gateway/src/main.rs`
runs before the listener binds too -- the identical crash-loop trap,
this time for a missing `Provider` row. Nothing seeded this row until
https://github.com/vymalo/vsms/issues/148[#148]: a fresh database made
the container exit immediately and crash-loop under
`restart: unless-stopped`, and this runbook used to work around it with
a raw `psql` `INSERT` run _after_ bringing the containers up -- which
meant watching `sms-gateway` crash-loop, then fixing it by hand.
`sms-gateway seed-dispatch` closes that gap: a real CLI subcommand,
going through the CrateStack delegate under a hand-built `owner` context
(never raw SQL -- R1), idempotent by construction. On its own:

[,bash]
----
docker compose --env-file .env run --rm sms-gateway seed-dispatch
----

*Renamed from `seed-provider` (#62).* The `Provider` row alone used to
be enough to make this deployment functional; it no longer is.
https://github.com/vymalo/vsms/issues/62[#62]'s routing rules engine
made ``sms-worker``'s `dispatch` role refuse every message with no matching
`Route` row -- a deliberate cutover from routing's old "any active
provider" placeholder -- so a deployment with an active `Provider` and no
`Route` starts and reports healthy, but every message it accepts lands in
`rejected` forever, silently. `seed-dispatch` now seeds both in one call:
the `Provider` row exactly as `seed-provider` always did, plus a
hardcoded catch-all `Route` (no flags to configure it -- a real routing
policy is the admin console's job, not this bootstrap command's) pointing
at it. Both halves are idempotent -- the `Provider` half by `create` +
catching the `23505` on ``Provider.key``'s `@unique` index; the `Route`
half, which has no unique column to catch a conflict on, by looking up an
existing route for the provider first -- so re-running the whole command
against an already-seeded deployment is a clean no-op on both.

Its own defaults already match the row this runbook used to hand-write --
`--key orange_cm`, `--kind orange_cm_http`, `--credential-ref
env:ORANGE_CM_CLIENT_SECRET`, `--max-tps 10`, `--max-daily-submissions
100000`, `--cost-per-segment-xaf 0` -- so no flags are required here, and
`bootstrap` itself exposes no flags for this step either (same defaults).
`config`/`credential-ref` stay placeholders regardless of what's passed:
confirmed against ``send_test_message.rs``'s own doc comment, neither
binary reads this row's `config`/`credentialRef` to construct the real
`OrangeCmProvider` -- both build it from their own CLI flags/env instead
(§2.4). This row's job is only to exist, carry `key = 'orange_cm'`, and
end up `state = 'active'`, which the subcommand also guarantees (a fresh
row is created `disabled` -- ``Provider.state``'s own `@default` -- and
activated in a second write).

==== Create the first operator

The console has no login (VS-5b): nobody types a password into it. A person
uses it with a key their own browser made and something vouched for -- a vaam
admin phone, or, for the first operator and as the break-glass, you on the
command line (<<Pairing the console>> below). Either way the key is attached
to an *existing* account, so the first operator's account has to exist:

[,bash]
----
docker compose --env-file .env run --rm sms-gateway provision-user \
  --email you@example.com --display-name "Your Name" --role-key owner
----

`provision-user` still prints a generated password once; the console never
asks for it (the password login and the OpenID routes it served go with
VS-4). What matters here is the account: `pair-console-key --user
you@example.com` attaches the browser's key to it, and the key speaks as
that account's role. A person paired by a vaam admin phone instead gets an
`admin` account created for them on first pairing, never an `owner`.

`--role-key` takes any of §5.2's six built-in roles -- `owner`, `admin`,
`operator`, `developer`, `auditor`, `support` -- all seeded by
`0002_bootstrap`. `system` is not among them and cannot be created;
`roles_key_not_reserved_check` rejects it, because a human account
holding it would pass every `hasRole('system')` policy through generated CRUD.

The console authenticates upstream as the *paired person's own key*, so a
paired `owner`/`admin`/`operator` can perform the writes that need a human
role (a `Provider` edit, for example). One exception remains by design: the
composer's `previewMessage`/`sendMessage` calls, which `sendMessage` structurally
requires an app principal for (see
`backends/crates/sms-api/src/procedures.rs::caller_client_id`), go through the
composer's own service key (<<The composer's key>> below). Worth knowing: the
messages list, its live updates and the dashboard read _every app's_ rows,
not just one's -- any paired human, regardless of role, can see across `App`
boundaries, per ``Message``'s own row policy.

== 4. Bring up sms-gateway and sms-worker

[,bash]
----
docker compose --env-file .env up -d sms-gateway sms-worker
docker compose ps
----

Both wait on `migrate` finishing successfully (`service_completed_successfully`,
not just "started"). ``sms-gateway``'s `HEALTHCHECK` hits its own
`GET /healthz` (added by this same PR -- there was no health endpoint for
either binary before it); `sms-worker` has no HTTP surface, so its
`HEALTHCHECK` instead checks the mtime of a heartbeat file its `main.rs`
touches every 15s (see ``backends/apps/sms-worker/Dockerfile``'s own comment for why
that's a more meaningful signal than a bare "is the process running"
check). Give both `--start-period` a few seconds before checking status.
`sms-gateway` should now report `(healthy)` on the first attempt -- both
the envelope keys of step 1 and the `Provider` row from step 3's bootstrap
already exist, so neither startup dependency is missing this time.

== 5. Provision the admin console's keys

The console holds two kinds of key, and neither is a login.

=== The composer's key

`previewMessage` and `sendMessage` are procedures only an *app* may call, so a
person's browser key cannot, and the console's composer sends through a service
key of its own: an Ed25519 `AppClient` key, registered once, whose private half
never reaches vsms. A real deployment's first `App` is a business decision
(quota, IP allowlist, a `SenderId` actually approved by a real provider account)
this runbook cannot make for you; `sms-gateway create-app --slug <slug> --name
"<display name>"` writes the row (idempotently, under a hand-built `owner`
context):

[,bash]
----
docker compose --env-file .env run --rm sms-gateway create-app \
  --slug my-app --name "My App"
----

`monthlyQuota`/`ipAllowlist`/`transliterateToGsm7` are fixed placeholders this
command doesn't expose flags for -- adjust the row afterward from the console.
Then generate the key, hand the console its private half, and register the
public half:

[,bash]
----
umask 077
mkdir -p secrets && chmod 711 secrets
openssl genpkey -algorithm ed25519 -out secrets/console-composer.pem
sudo chown 10001:10001 secrets/console-composer.pem   # admin's runtime uid
sudo chmod 0400 secrets/console-composer.pem

# The public half as register-client takes it: the raw 32 bytes, base64url.
PUBLIC_KEY="$(openssl pkey -in secrets/console-composer.pem -pubout -outform DER \
  | tail -c 32 | base64 | tr '+/' '-_' | tr -d '=\n')"

docker compose --env-file .env run --rm sms-gateway register-client \
  --app my-app --client-name console-composer --label "console composer" \
  --scope sms:send --scope sms:read --public-key "$PUBLIC_KEY"
----

`register-client` is idempotent: the key is identified by its RFC 9679
thumbprint, so running it twice leaves one row. `--client-name` gives the
composer its own principal (`appc_<slug>_console-composer`), so its rate-limit
bucket, idempotency namespace and scopes are not shared with any other
integration of the same App. Do *not* grant it `console:pair`: that scope
belongs to vaam's pairing client alone, and the gateway refuses it anywhere
but this command line.

``chmod 711`` on `secrets/` (not `700`) matters: a directory with no execute
("search") bit for "other" blocks any other uid from even traversing into it,
whatever the file inside allows. ``admin`` reads the key through a
`configs:` reference (``SMS_COMPOSER_KEY_FILE``), which fails `docker compose
up` outright if the file is missing, instead of a bind mount that would be
created silently as an empty directory.

Also set `SMS_ENVELOPE_SERVER_KEY_CURRENT` and `SMS_ENVELOPE_SERVER_KEY_NEXT` in
`.env` to the two *public* keys the gateway prints (they are what the browser
pins, and what the composer's client verifies answers with):

[,bash]
----
docker compose --env-file .env run --rm sms-gateway server-keys
----

A console deployed without the composer key serves every other screen; only the
composer reports that it has no key.

The composer spends this key only for a person the gateway names. Before each
send or preview the browser seals a call to `authorizeComposition` with the
person's own key, and the gateway answers it only for a signed-in `owner`,
`admin` or `operator` holding `sms:send`; the console's server opens that answer
under the two public keys above, and goes on only if it names a person, that
operation and the hash of the message about to be sent. An `auditor`, a `support`
or `developer` user, a role that lost `sms:send`, and any app client's key are
refused (a `403` the composer shows), however they were paired.

=== Pairing the console

A person's console key is made by their own browser the first time they open the
console, and shown as a QR (docs/design/console-pairing.md). It becomes valid
when the gateway has a ``ConsoleKey`` row for it, and there are two ways to make
one:

* *A vaam admin phone* scans the QR and approves with biometrics, and vaam
  relays the pairing to ``registerConsoleKey`` with its pairing client (an
  `AppClient` holding `console:pair`, registered with `sms-gateway
  register-client --scope console:pair`, never through the console). The person
  gets an `admin` account on first pairing, never an `owner`. This path depends
  on vaam's relay (VA-4); until it exists, use the next one.
* *You, on the command line*, which is also the break-glass and the only way to
  enrol an `owner`:
+
[,bash]
----
docker compose --env-file .env run --rm sms-gateway pair-console-key \
  --user you@example.com --public-key "<the k field of the QR>"
----
+
It attaches the key to an existing active account, with no proof of possession
(you holding the database is the authority), creates no user and changes no
role. The console notices on its own within a couple of seconds.

A key lasts 30 days and is never extended; the console says when it is close and
asks for a new pairing when it ends. `/console` ("This console") revokes it.

== 6. Bring up admin and Caddy

[,bash]
----
docker compose --env-file .env up -d --build admin caddy
docker compose ps
----

``admin``'s `HEALTHCHECK` hits its existing `GET /api/health`, which touches no
external dependency and needs no credential: the console has no login, so there
is nothing in front of it to exempt. `caddy` depends on both `sms-gateway` and
`admin` being healthy before it starts routing -- see ``deploy/Caddyfile``'s own
comment for why the gateway and admin domains have to stay two separate origins
rather than one path-routed domain (the console keeps its paired browser key in
IndexedDB, which the browser scopes to the console's own origin).

*`deploy/Caddyfile` uses `rate_limit`, a third-party module the stock
`caddy:2-alpine` image does not carry* -- ``deploy/docker-compose.yml``'s
`caddy` service ``build``s from `deploy/caddy.Dockerfile` (an xcaddy build
adding it) for exactly that reason, not the stock image. An earlier
revision of this paragraph said the compose edit to pick that Dockerfile
up was still outstanding; that edit landed and this paragraph was simply
never corrected to match -- found while writing this file's own
"Backend-only deployment" section below, the same "documentation asserts

== 7. Verify

[,bash]
----
curl -f https://$SMS_GATEWAY_DOMAIN/healthz
curl -f https://$SMS_ADMIN_DOMAIN/api/health
----

Both should return `200`. Every other route of the gateway is sealed: an unsigned
request, such as `curl -i https://$SMS_GATEWAY_DOMAIN/jobs`, is refused with a
bare `401`, and a request for a route that does not exist (`/token`, `/login`)
answers `404`. If you're on the `tls internal` local/demo
path, add `-k` or trust Caddy's local CA first. This exact sequence -- all
five containers, real health checks, a real Caddy TLS hop in front of
both origins -- was run end to end against a throwaway config while
building this PR, using `tls internal` in place of real DNS; see the PR
description for what specifically was and wasn't verified.

== Enabling MTN delivery receipts (MADAPI)

Only if this deployment sends through MTN. Orange needs nothing here --
its DR endpoint is whitelisted by a manual support ticket, covered in
xref:36-handset-gate.adoc[36-handset-gate.adoc].

*MTN delivery receipts do not arrive unless you register an endpoint
first.* MADAPI requires two independent things: `requestDeliveryReceipt:
true` on every outbound message, which `sms-provider-mtn` always sends,
and a `deliveryReportUrl` registered against your approved
`serviceCode`. Skip the registration and messages submit successfully,
reach `submitted`, and then sit there permanently with no receipt ever
arriving -- which looks exactly like a broken route and is why this
section exists rather than a line in a table.

Unlike Orange's whitelisting, this is a real API call, so run it once per
approved short code:

[,bash]
----
docker compose run --rm sms-gateway mtn-subscribe-dlr \
  --delivery-report-url "https://$SMS_GATEWAY_DOMAIN/dlr/mtn_cm" \
  --target-system vsms
----

`MTN_CLIENT_ID`, `MTN_CLIENT_SECRET`, `MTN_SERVICE_CODE` and
`MTN_BASE_URL` come from the environment (see `deploy/.env.example`), so
they are not repeated on the command line -- the secret in particular
should never land in shell history.

Note the path segment is `mtn_cm`, matching `SmsProvider::key` and what
``sms-gateway``'s `+/dlr/{providerKey}+` handler matches against. A
subscription registered against any other path will be accepted by MTN
and then silently 404 on every receipt.

`run --rm`, not `exec`: this command needs no database and no running
gateway, and the gateway may legitimately not be up yet.

== Backend-only deployment (R4, `CONTRIBUTING.md`)

*"Some deployments will ship the backends only, with no admin surface at
all. That is a supported configuration, not a degraded one."* Both
`admin` and `caddy` carry `profiles: [console]` in
`deploy/docker-compose.yml` -- a bare `docker compose --env-file .env up
-d` brings up `postgres`, `migrate`, `sms-gateway`, `sms-worker`, `backup`
and `prometheus` (the last two unconditional: R4's own fourth clause,
"a backend-only deployment must still be observable and operable," and
neither is console-specific) and nothing console-shaped at all -- not
`admin`, not the bundled Caddy edge. Add `--profile console` (or
`COMPOSE_PROFILES=console`) to bring both back.

*Why `caddy` is gated too, not just `admin`.* `deploy/Caddyfile` is one
file with two unconditional site blocks, `{$SMS_GATEWAY_DOMAIN}` and
`{$SMS_ADMIN_DOMAIN}` -- see that file's own header for the reason two
domains exist at all (the console keeps its paired browser key in
IndexedDB, which the browser scopes to its own origin, so path-routing one
domain to both services isn't an option). There is no way to make only the second block
optional without editing that file, which is a third-party-module build
out of scope here. A backend-only compose deployment therefore has no
bundled TLS edge for `sms-gateway` either -- front it with your own
reverse proxy/ingress, the same "operator's own opinion" posture
`deploy/charts/vsms/values.yaml` already takes for `ingress.gateway`
(disabled by default), or enable `--profile console` anyway and simply
never start `admin` itself.

*A `:?`-required env var interpolates for every service in the file,
independent of which profile is active or which services you actually
ask to start* -- confirmed live, not assumed (`docker compose config`
failed on `SMS_API_URL` with `admin` excluded by every measure

== Rate limiting (#156) -- what was actually proven, against a real stack

``deploy/Caddyfile``'s `rate_limit` block was verified against a genuinely
separate compose project (`-p vsms156`, non-default host port `18080`,
built from `deploy/caddy.Dockerfile` and the same `sms-gateway`/`migrate`
images this tree produces elsewhere), not asserted from reading the
config. *It once also throttled the gateway's `/token` endpoint; that endpoint,
and with it the two `token_*` zones and `SMS_TOKEN_RATE_LIMIT_*`, were deleted
with the OpenID Provider (VS-4).* What remains at the edge is the one
unauthenticated route, `+/dlr/{providerKey}+`; every other route is sealed, and
an unsigned request is refused at the envelope layer before any database work.

*`+/dlr/{providerKey}+`, per-source-IP zone* (tested at a scaled-down
`events=4, window=20s`; shipped default `100/10s`): the first 4 requests
to `/dlr/orange_cm` got a real `400` from `sms-gateway` (malformed DLR
payload, on purpose -- proves the request reached the app), the 5th
onward got `429` with `Retry-After` set, straight from Caddy (`Server: Caddy`,
no application body). Waiting out the window recovered it.

*Keying, verified both directions, not just claimed:*

* A second, genuinely different source IP (a separate container on the
compose network, confirmed via Caddy's own `log_key`-enabled logs to
be a distinct `remote_ip`) got its own, independent budget -- unaffected by the
first source's bucket already reading `429` -- and throttled identically once
_it_ sent enough requests.
* Sending `X-Forwarded-For: 1.2.3.4` and, on a separate request,
`X-Forwarded-For: 9.9.9.9` from an already-throttled source
did *not* create new buckets and did *not* lift the throttle --
both still got `429`. Confirms the key is genuinely
`{http.request.remote.host}` (the real TCP peer Caddy accepted the
connection from), not anything a client-supplied header can influence.

That burst was originally run against a composite `(IP, path)` key, and
the run also showed a different `providerKey` from the same source
getting its own bucket. *That composite key has since been removed*, so
the per-path isolation it demonstrated no longer applies. The reason is in
``deploy/Caddyfile``'s own comment on the zone: a composite key silently
disables `ipv6_prefix`, because the module only masks a key that parses
as a bare IP. Keeping IPv6 masking was judged the more valuable of the
two, since only one provider is wired up today.

*Not verified by this burst test, and worth being explicit about:*
the aggregate zone (`dlr_global`) was confirmed to parse and load
(`caddy validate`, and `log_key` showed it evaluating on every request) but was
not driven past its own (200/10s) threshold by volume; it shares the exact same
sliding-window mechanism already proven above, just with a static instead of a
dynamic key.

== Ordering and failure modes, summarized

|===
| Component | Waits on | What "not ready" looks like

| `migrate`
| `postgres` healthy
| exits non-zero; nothing downstream should start (compose enforces this via `service_completed_successfully`)

| `sms-gateway`
| `postgres` healthy, `migrate` completed
| *will not even start* without the two envelope keys of step 1 or step 3's `orange_cm` `Provider` row -- both are resolved before the listener ever binds, so either one missing crash-loops the container (#148)

| `sms-worker`
| `postgres` healthy, `migrate` completed
| starts fine with no envelope keys (only `sms-gateway` loads them) and fine with no `Provider`/`Route` either -- `dispatch` role specifically needs step 3's `Provider` row _and_ its catch-all `Route` (#62) to route anything, other roles don't, and none of them crash-loop on the absence of either the way `sms-gateway` does on a missing `Provider`: a `dispatch` role with nothing to route to just rejects every message it claims, silently, forever

| `admin`
| `sms-gateway` healthy
| starts; the composer reports it has no key until step 5's is registered, and every other screen works

| `caddy`
| `sms-gateway` and `admin` healthy
| won't route until both are up
|===

Two instances of `migrate` starting at once (a redeploy racing a still-up
previous stack) serialise on a Postgres advisory lock
(`backends/apps/sms-migrate/src/main.rs`) rather than double-applying -- see that
binary's own module doc for why a `schema_migrations` tracking table
exists only in this deploy path, not in the committed
`backends/migrations/` tree.

== Secrets -- the decision, and what it doesn't protect against

*No `sops` here*, despite §9.2 mentioning it. This deployment's secrets
are: `POSTGRES_PASSWORD`, `ORANGE_CM_CLIENT_SECRET`, `SMS_HASH_PEPPER`,
the admin console's `console-composer.pem`, and the backup service's
`rclone.conf`. The first three live in `deploy/.env` (`chmod 600`, never
committed -- `.gitignore`/`.dockerignore` both exclude it); the last two
live in `deploy/secrets/` (also never committed -- `.gitignore` ignores
everything in that directory except the two example/placeholder files
this repo ships) mounted read-only into the one container that needs
each.

*`deploy/secrets/rclone.conf` must exist before the first `up`* -- even
when `BACKUP_RCLONE_REMOTE` (`.env`) is a bare local path and rclone
needs no real credentials at all. Production-readiness audit B2: a
`volumes:` bind mount onto a not-yet-existing host path used to be
created *silently as an empty directory* by the Docker daemon, and
`backup` would then fail obscurely against a directory where it expected
a config file. `deploy/docker-compose.yml`'s `backup`/`admin` services
now reference both files as `configs:` instead, which fails `docker
compose up` outright ("bind source path does not exist") if either is
missing -- so this step is no longer optional busywork, it's what keeps
`up` from either silently misbehaving or refusing to start at all:

[,bash]
----
cp secrets/rclone.conf.example secrets/rclone.conf
chmod 600 secrets/rclone.conf
# then fill in a real remote's credentials — see that file's own header,
# or docs/runbooks/backup-restore.adoc — unless BACKUP_RCLONE_REMOTE is a
# bare local path, in which case the copied-verbatim empty file is
# already a valid, working config.
----

That is genuinely less than §9.2's own aspiration, and the honest
threat model is: this protects against the secrets ending up in git
history, in a Docker image layer, or in `docker inspect` output visible to
anyone without host access. It does *not* protect against anyone with
read access to the VM's filesystem, and it does *not* give you audited,
rotatable secret access the way `sops` + age/KMS would. For a single VM
with a small operator set, that trade is reasonable; it stops being
reasonable the moment more than a couple of people need host access, or
this deploys to more than one VM. Revisit with real `sops` (age-encrypted,
keyed to each operator, decrypted only at container start) before either
of those becomes true -- not preemptively, since a half-wired `sops` setup
that still leaves plaintext secrets in `.env` for the vars this file
doesn't cover would be worse than being honest about the current gap.

== Releasing a new version

`.github/workflows/release.yml` builds and pushes four images
(`sms-gateway`, `sms-worker`, `admin`, and `migrate` -- #145 added the
fourth, for the Helm chart's migrate Job below) to GHCR, plus the
`deploy/charts/vsms` Helm chart as an OCI artifact, on two triggers:

* *Every push to `main`* -- `:main` (mutable, moves with each push) and
`:sha-<12 hex>` (immutable, one commit). The chart publishes as
`0.0.0-main.<sha>`.
* *Any `v*.*.*` tag* -- `:$TAG` and `:latest`, unchanged from what this
workflow did before #145. The chart publishes as `$TAG` with its
leading `v` stripped (Chart.yaml requires strict semver).

A third trigger, `workflow_dispatch`, exists only to smoke-test the
pipeline itself from a branch that isn't `main` and isn't tagged -- it
tags images `:branch-<slug>` / `:sha-<12 hex>` and the chart
`0.0.0-dev.<sha>`, deliberately never touching `:main`/`:latest`. #145's
own PR used this to prove the pipeline works before this section existed
to document it -- see that PR for the exact GHCR references it produced.

On the VM (compose path), two ways to upgrade -- production-readiness
audit S6 closed the gap where only the first of these actually worked:

*Build from source* (unchanged, still the default -- `build:` is still
present on every service that has one):

[,bash]
----
cd deploy
git pull
docker compose --env-file .env up -d --build
----

*Pull pre-built GHCR images* -- `migrate`/`sms-gateway`/`sms-worker`/`admin`
now also carry a matching `image:` (`docker-compose.yml`'s own header
comment has the full reasoning), so `pull` has something real to fetch
instead of silently no-op'ing against a locally-built, untagged image:

[,bash]
----
cd deploy
export VSMS_IMAGE_TAG=v0.3.1   # or the tag you're upgrading to
docker compose --env-file .env pull
docker compose --env-file .env up -d
----

`VSMS_IMAGE_OWNER` (default `vaam-apps`) is the second half of that
reference -- `release.yml` publishes to
`ghcr.io/${{ github.repository_owner }}/...` unconditionally, and this
repository's own GitHub owner has moved twice: `v0.2.1` and earlier
published under `ghcr.io/vymalo/...`, `v0.3.0` alone under
`ghcr.io/vaam-store/...`, and `v0.3.1` on lands under `ghcr.io/vaam-apps/...`,
this file's own default now. Pulling an older release means setting BOTH
knobs together, never one without the other:

[,bash]
----
export VSMS_IMAGE_OWNER=vymalo
export VSMS_IMAGE_TAG=v0.2.1
----

Either path is a real, working upgrade mechanism now; before this PR,
`docker compose pull` was a documented no-op against a compose file with
no `image:` anywhere, silently leaving `up -d` to build (or reuse) a
local image regardless of what had actually been pulled.

=== Ordering -- why a Helm hook, not an init container

`sms-gateway serve` calls `+resolve_provider_row_id(...)?+` before binding its
listener (this file's own steps 3 and 4, above) -- a fresh database makes the
container exit immediately on a missing `Provider` row, not fail its first DLR
callback (https://github.com/vymalo/vsms/issues/148[#148]: the `orange_cm`
`Provider` row used to have no seeding path under Helm at all -- no window
exists between the pre-install hooks completing and the gateway `Deployment`
being created for an operator to seed anything by hand, unlike compose, where a
human can at least `docker compose exec` into Postgres while the container
crash-loops). The chart's `seedDispatch` controller is a `pre-install` Helm
hook Job for exactly this reason: Helm does not create _any_ other release
resource -- including the `sms-gateway` Deployment -- until every pre-install
hook Job has succeeded. A post-install step or a readiness check on the gateway
would both deadlock permanently, since the gateway can never become ready
without this step having already run.

`migrate` (weight `-20`) and `seedDispatch` (weight `-15`, renamed from
`seedProvider` in https://github.com/vymalo/vsms/issues/62[#62] --
see that renamed job's own comment in `values.yaml` for why: it seeds a
catch-all `Route` alongside the `Provider` row now, since a `Provider`
with no `Route` routes nothing since #62's engine landed) are both
`pre-install,pre-upgrade` hooks -- safe on every deploy because both are
genuinely idempotent: `migrate` via ``backends/apps/sms-migrate``'s own
advisory-lock-guarded `schema_migrations` tracking table, `seedDispatch`
via ``sms-gateway seed-dispatch``'s own dedupe on both halves (`Provider`:
`create` + catch-`23505`; `Route`: look up an existing one for the
provider first -- see step 3 above). The distinct weights keep the two hooks a
single, strictly-ordered chain rather than two of them racing at a shared
weight; see ``values.yaml``'s own comment on `seedDispatch` for the full
reasoning. (A third hook, `rotateSigningKey`, minted the signing key of the
embedded OpenID Provider and went with it in VS-4.)

`admin.serverKeys.current`/`.next` is enforced with Helm's `required` function --
an install with any of them missing fails immediately with a named field, not a
cryptic render error or a silently-broken Pod.
