# vsms — project context

A2P SMS gateway for Cameroon (MTN + Orange). OTP and notification delivery, provider abstraction over HTTP APIs and SMPP, Next.js admin console.

**Read [`docs/architecture.md`](docs/architecture.md) before making design decisions.** It is the spec, and every claim in it was verified against the real toolchain rather than assumed. This file is the subset that must be in context for *every* session.

**Milestone 1 done.** The auth shape is decided ([#6](https://github.com/vymalo/vsms/issues/6)): `authkestra-op` stays, pinned `=0.3.3`, and machine callers authenticate with **`private_key_jwt`** — no shared client secret exists anywhere in this system. The `GrantType` `#[serde(untagged)]` bug that shaped the original design is **fixed in 0.3.2** (verified by round-tripping every variant; see §4.2). Schema and migrations for it have landed: `OauthClient` lost `secretHash` and gained `tokenEndpointAuthMethod` + `jwks`, plus new `OauthSigningKey` and `ClientAssertion` models. `/token` rate limiting is explicitly out of scope — it is a reverse-proxy concern, and with no Argon2 at the token endpoint the original urgency is gone.

Three things about that schema are load-bearing and easy to undo by accident:

- **`tokenEndpointAuthMethod` has no `@default` on purpose.** A `@default` would drop it from `CreateOauthClientInput`, and a *missing* method is how authkestra spells "accepts a secret from either transport, refuses assertions" — the one state `private_key_jwt` must never reach. `crates/sms-api/tests/create_inputs.rs` turns its disappearance into a compile error.
- **`@sensitive` on `OauthSigningKey.privateKeyPem` is not confidentiality.** It redacts audit snapshots only; the model's `hasRole('system')` read policy is the entire control. `system` is synthetic and no issued token may carry it — an `AuthProvider` that mints `system` for HTTP callers hands out the key that signs every token, through generated CRUD.
- **`ClientAssertion` is insert-only, written as `create` + catching `23505`.** authkestra requires `record_jti` to be atomic; a read-then-write is the TOCTOU race the table exists to prevent.

**`aws-lc-rs` enters this tree from authkestra alone — cratestack selects `ring` throughout.** An earlier revision of this file claimed four independent paths including cratestack and sqlx; that was **wrong**, and read off a misinterpreted `cargo tree -i aws-lc-rs`. That command lists everything depending on the shared `rustls`, not everything *asking for* `aws-lc-rs`; because Cargo unifies features, one `rustls` in the graph carries both providers' feature flags regardless of who requested which. Read `cargo tree -e features -i rustls` instead, which shows the actual feature edges.

What the sources say: `cratestack-sqlx` selects `sqlx-core`'s `_tls-rustls-ring-webpki`, and `cratestack-client-rust` selects `reqwest`'s `rustls-tls`, which in reqwest 0.12 expands to `rustls-tls-webpki-roots` → `__rustls-ring`. Both hard-select **ring**. The `aws-lc-rs` edge is `reqwest 0.13`'s *default* features via `authkestra-engine` — exactly what [marcjazz/authkestra#179](https://github.com/marcjazz/authkestra/pull/179) (in 0.3.3) made opt-out-able.

Confirmed empirically rather than argued: setting `default-features = false, features = ["rustls-no-provider"]` on the four authkestra pins makes `cargo tree -i aws-lc-rs` report *"did not match any packages"* — it leaves the graph entirely. **So a static musl/`scratch` build or a `cargo-deny` policy banning `aws-lc-rs` is achievable today, with no upstream blocker.** Not done here because `rustls-no-provider` panics at `reqwest::Client::new()` unless the application installs a `CryptoProvider` in `main` first, and that runtime path is unverified — do that work deliberately, with a live TLS test, not as a drive-by.

**That deliberate work landed.** The four authkestra pins carry `default-features = false, features = ["rustls-no-provider"]` (root `Cargo.toml`); `app/sms-gateway/src/main.rs` and `app/sms-worker/src/main.rs` each call `rustls::crypto::ring::default_provider().install_default()` as the literal first line of `main`, before anything else runs, so it happens before any dependency — including ones this repo's own code never directly calls, like authkestra's internal flow/discovery/captcha HTTP clients — has a chance to construct a `reqwest::Client`. `ring`, not `aws-lc-rs`, matching this section's own "cratestack selects ring throughout." `app/sms-gateway/tests/tls_no_provider_live.rs` is the live TLS test that was missing: a second, independently-featured `reqwest 0.13.4` dependency (`reqwest-no-provider`, same version already in the graph via authkestra's own pin) performs a real HTTPS GET against `https://api.orange.com/` — the same host `ORANGE_CM_BASE_URL` defaults to in production — after installing the provider, and the test was verified to actually fail (the exact panic this section describes, reproduced on purpose by temporarily removing the install call, then restored) before being trusted to pass for the right reason. Corroborated independently, not just by this repo's own test: `cratestack-client-rust`'s own `CratestackClient::new` (found while investigating this mechanism, in `cratestack-client-rust-0.7.10/src/client/core.rs`) calls the identical `rustls::crypto::ring::default_provider().install_default()` before building its own client — the same fix, arrived at independently upstream.

Leader election landed on top of that (`#28`): `crates/sms-worker/src/lease.rs` — an R1 exception, allowlisted by path in `ci/assert-no-raw-sqlx.sh`. Deliberately **doesn't** use §7.2's own illustrative `pool.acquire()` sample — a `PoolConnection` returns to the pool rather than closing on drop, so a lease dropped without an explicit `release()` (a panic, a `kill -9`) would leak the lock at the Postgres level forever, unreachable, on a session silently recycled to serve unrelated future queries. Verified live that this trap is real (a second, independent connection stayed unable to acquire a lock left behind by a dropped `PoolConnection`) and that `RoleLease` avoids it (a dedicated, never-pooled `PgConnection` — dropping it closes the socket immediately, and Postgres's own session-advisory-lock semantics release the lock the moment that session ends, no cooperation from `sqlx` required). `run_singleton` wires this into a retry loop (5s interval, per §7.2) behind a `CancellationToken`, releasing explicitly on SIGINT/SIGTERM as the fast path and falling back to the drop-triggered release on a hard kill. Manually verified end to end against a real two-node setup: standby correctly stands by while the other holds the lock, `kill -9` failover reclaims within one retry cycle (~5s, no cooperation from the killed process needed), graceful SIGTERM triggers explicit release before exit.

**`ProviderError::Indeterminate` (#119) closed the gap where a timed-out submit was indistinguishable from an outage.** Before it, the five variants (`Permanent`/`Transient`/`Unavailable`/`Rejected`/`Unsupported`) had no way to say *"the request was sent and we never learned the outcome"*, so `sms-provider-orange-cm` mapped every transport failure — including a read timeout arriving after Orange may already have accepted the message — to `Unavailable`, whose own contract is "fail this submission over to the next route". That is a resubmit, and with no idempotency key anywhere it means a duplicate SMS. Meanwhile `uncertain`, the state that exists precisely to mean "we don't know", was reachable **only** from an inbound DLR.

Three parts, each with a trap:

- **The predicate is connect-vs-read, not "is it a timeout".** `is_connect()` is checked first and stays `Unavailable` — nothing was written, retry is safe. Only past the connect phase (`is_timeout() || is_body()`) is the outcome genuinely unknown. Getting this backwards either destroys legitimate failover or leaves the double-send in place. A 2xx whose body is malformed or missing `resourceURL` is also `Indeterminate` — Orange accepted it before we failed to read the reply.
- **`routed -> uncertain` had to be added to the state machine** (§2.10's table *and* §7.4's diagram, with `0002_bootstrap` regenerated, never hand-edited), because a timed-out submit leaves the row in `routed` with no provider ref — only `submitted -> uncertain` existed.
- **The message then leaves the claim candidate set permanently** (`candidates()` selects `accepted`/`queued`/`routed`), so it is never resubmitted. It stays resolvable because `providerMessageRefAlt` is stamped with `Message.id` on that path specifically — the value sent as Orange's `callbackData` *before* the network call, and therefore known regardless of outcome. The first attempt shipped without that stamp and a later DLR had nothing to correlate against; caught by the live test, not by review.

**The tradeoff is deliberate and is a product decision, not a free win: this trades a possibly *lost* message for never sending a *duplicate*.** For OTP traffic that is right — a duplicate OTP is worse than one the user re-requests. If notification traffic ever wants the opposite, the mapping needs to differ per message class.

**A fault-injecting fake of Orange, and a chaos suite over the message state machine, exist as of the `fake-orange-chaos` PR — a further automatable complement to `docs/runbooks/36-handset-gate.md`, and explicitly does not close `#36` either.** `crates/sms-fake-orange` is a participant, not a response stub: it answers the token/submit HTTP calls per a `FaultPolicy` (`Scripted` — an exact ordered sequence, for deterministic CI-gate tests; `Seeded` — a seeded PRNG drawing a realistic-weighted mix, always reproducible by seed), and independently schedules DLR deliveries as real HTTP POSTs against a caller-supplied `/dlr/{providerKey}` endpoint — including a DLR that deliberately races the submit response, proving the documented "`providerMessageRef` may not be persisted yet" correlation gap is real: at that instant neither `providerMessageRef` nor `providerMessageRefAlt` is set (the latter is only stamped by `write_submitted`/`write_transition`, both of which run *after* the race), so the DLR is silently dropped and the message later reaches a real terminal state via `expire_stale`, not stuck and not wrongly `delivered`. `crates/sms-worker/tests/chaos_live_postgres.rs` hand-rolls the same small `POST /dlr/{providerKey}` handler `app/sms-gateway/src/dlr.rs` owns in production (same "binary crate has no `lib.rs`" constraint `oidc_flow_live.rs` already worked around) against a real `axum::serve` on an ephemeral port, so the fake's DLR scheduler makes a genuine HTTP round trip into this system. Ten scripted tests cover one fault mode each (no DLR ever, the race above, duplicate/out-of-order/unknown-ref/post-terminal DLRs, 429-then-recovery, outright rejection, a malformed/missing-resourceURL 201, a post-accept timeout, and a 401 token failure); five seeded sweeps (fixed seeds 1–5, ~7s each) drive a batch of messages through a weighted-random fault mix and assert invariants rather than exact outcomes — no message lost (terminal, or the separately-documented `undelivered` gap below), nothing left claimable, `attempts <= maxAttempts`, and — checked against the fake's own request ledger, not this system's database — a message that went `uncertain` via `Indeterminate` is never submitted again. Connection-level nastiness (RST mid-response, refused connections, byte-dribble) is explicitly out of scope, noted as future work: `wiremock`'s `Respond` trait can only ever emit a well-formed HTTP response, and the connect-refused half is already covered directly, against a real socket, by `sms-provider-orange-cm`'s own `a_connect_refusal_is_still_unavailable`.

Two real findings, not invented ones: **`DeliveryReceipt`'s `list`/`detail` policy was missing `hasRole('system')`** — the *seventh* instance of the exact same gap shape this file has now recorded six times before (`App`, `AppClient`, `SenderIdRegistration`, `OperatorPrefixRule`, `Provider`, `Job`) — found by the chaos suite's own `a_duplicate_delivered_dlr_is_idempotent` scripted test trying to read back `DeliveryReceipt` rows under a `system` context and getting zero. Fixed the same way as every prior instance (`schema.cstack` only — an `@@allow` change never touches DDL, confirmed both by rereading `#100`'s own commit, which states its analogous `Job` fix produced a byte-identical migration diff, and by diffing `cratestack migrate diff`'s output against the committed `0001_init` before and after this change). **Second, the chaos suite empirically confirms `dlr.rs`'s own documented `undelivered` gap is real, not just prose:** nothing currently drives `undelivered -> queued` (no retry path exists yet), and `expire_stale` only reaps `submitted`/`uncertain`, not `undelivered` — so a message that receives exactly one retryable-failure DLR and no follow-up sits in `undelivered` forever under this system's current scope — filed as [#122](https://github.com/vymalo/vsms/issues/122), since retryable failures silently vanishing is the worst-shaped bug an SMS gateway can have: not delivered, not failed, not expired, not reaped, and invisible to any alert. The seeded sweep's own invariant treats that as an accepted, documented outcome rather than "message lost," matching this file's own prior framing precisely rather than re-litigating it.

**`#134` closed the gap between what `docs/architecture.md:588` claimed and what `msisdnHash` actually was.** The doc had always said HMAC-SHA256 under a server-held pepper; `crates/sms-api/src/procedures.rs`'s `sha256_hex` was plain, unkeyed `SHA-256` — reversible by brute force in seconds over Cameroon's mobile numbering space (~10^7 candidates, per `crates/sms-msisdn`'s own prefix ranges), which means a "purge" that cleared `msisdn` but kept `msisdnHash` had not de-identified anything. The function's own doc comment already said the `sha256:` prefix existed "so a future second hash scheme... is distinguishable from this one" — it knew what was missing; the doc simply was never corrected to match, and this file never recorded the divergence. Found by a read-only audit ahead of a planned production release, filed and fixed in the same PR.

The fix: `crates/sms-api/src/pepper.rs` — a `HashPepper` newtype (hand-written `Debug`, not derived, so it can never leak through a struct that does derive `Debug`; a 32-byte minimum length, rejecting a trivially short pepper) wrapping real secret material, and `hmac_sha256_hex`, the one function that turns a pepper + plaintext into `hmac-sha256-v1:<hex>`. `Procedures::new` now takes a `HashPepper` — its `Default` impl is gone entirely (this repo's own standing preference: a hard cutover, never a default that has to invent a pepper), so every construction site supplies one explicitly: the router (from `sms-gateway serve`'s new required `--hash-pepper`/`SMS_HASH_PEPPER` clap arg, validated and constructed *before* the pool connects, so a missing or too-short pepper fails at startup, never at the first `sendMessage`), `examples/send_test_message.rs` (its own copy of the same flag), and every live-Postgres test. `bodyHash` is peppered under the same scheme, for the same reason (a templated OTP body is exactly as low-entropy and enumerable as an MSISDN) — decided only after grepping every reader of `bodyHash` in this tree and the admin console's generated TS client and confirming it is write-only, never cross-compared against a value computed outside this system.

`sms-worker` needed no changes: it never computes `msisdnHash`/`bodyHash` at all (`grep -rn Sha256` across `crates/` and `app/` confirms the computation lives in exactly one place), so there was no second binary to keep in lockstep — only `sms-gateway` and the standalone `send_test_message` example construct a `Procedures`, and both now require the same pepper by construction, not by convention.

No dual-read/rehash path was built, and per this file's own "no live database anywhere yet" fact, none was needed — every `sha256:`-prefixed value in this tree was test fixture data, updated to `hmac-sha256-v1:` for consistency, not migrated. The rotation consequence for when real traffic exists is documented in `pepper.rs`'s own module doc rather than solved: rotating the pepper does not retroactively rehash a single stored row, a row that still holds plaintext `msisdn` *can* be rehashed by a job that doesn't exist yet, a row whose `msisdn` has already been purged never can, and until any rehashing happens, opt-out matching and dedupe against old rows silently stop working the moment the pepper rotates — a `msisdnHash` computed under the new pepper never equals one stored under the old one, and nothing detects the mismatch.

One test-authoring trap worth internalising for next time: `send_message_live_postgres.rs`'s own `an_opted_out_recipient_is_refused_before_persistence` test had a `sha_of` helper that hand-rolled a second copy of the hash algorithm to precompute a matching `OptOut.msisdnHash` — exactly the kind of duplication that silently drifts the moment the real algorithm changes, which is precisely what happened here. Fixed by exposing `pepper::hmac_sha256_hex` as a public function instead of a private method, so the test now calls the *same* function production does rather than reimplementing it — removing the drift risk rather than just patching the one copy that happened to be caught this time.

One environment note worth recording rather than working around silently: this machine's globally installed `cratestack` CLI is `0.7.4`, newer than the pinned library family (`=0.6.7`), and `cratestack migrate diff` under that newer CLI emits foreign-key `ALTER TABLE` statements the pinned `0.6.7` emitter never has (confirmed: the *same* diff, run against the *unmodified* `main` schema, already disagrees with the committed `0001_init`) — a real, pre-existing skew between the installed CLI and the pinned library, not something this PR's own schema edit caused. The committed migrations were correspondingly left untouched, on the strength of the policy-only edit reasoning above, not regenerated with the mismatched CLI.

**Milestone 3 in progress.** `#38` (subscribers) and `#39` (the `drain` role) landed together, as one PR — they're two halves of one subsystem and the epic (#37) itself says so. `crates/sms-api/src/webhooks.rs` is #38's `Message.created`/`Message.updated` subscribers; `crates/sms-worker/src/drain.rs` is #39's role.

The load-bearing question a PR like this has to resolve before writing any code: if subscribers already insert `WebhookAttempt` rows synchronously, what does `drain` actually drain? Read straight from `cratestack-sqlx`'s vendored source, not guessed: every `@@emit`-annotated mutation triggers an *automatic* post-commit drain of its own process's runtime (`create.rs`/`update.rs`: `let _ = self.runtime.drain_event_outbox().await;`), and `CoolEventBus::emit` returns `Ok(())` for a topic with **zero registered handlers** — not an error, not a skip flagged anywhere (`cratestack-core/src/events/bus.rs`). So a process that writes to `Message` without having called `sms_api::webhooks::register_subscribers` on its own `Cratestack` instance first doesn't leave the row for `drain` to pick up later — its own automatic drain marks it delivered immediately, having done nothing, and the event is lost, silently, the moment the write commits, which is worse than "stalled." That makes registration mandatory in *every* writer process, not optional wiring for wherever `drain` happens to be scheduled: `app/sms-gateway`'s `serve` command and `app/sms-worker`'s `main` (unconditionally, regardless of `--roles`, since every role in one process shares one `Cratestack`/`CoolEventBus` — `Clone` shares the `Arc`-backed registry, not a copy) both call it now. What `drain`'s own periodic `.events().drain()` call actually adds on top of that is the one thing no writer's own post-commit drain gives you: a write-independent retry trigger for a row whose handler failed on an earlier attempt. Proven live, not asserted: `crates/sms-worker/tests/drain_live_postgres.rs` deliberately leaves a row stuck by registering an always-failing handler on one `Cratestack` instance, then shows a second, independent instance's `drain::tick` — running the real subscribers, with no further write on any emitting model in between — is what turns it into a real `WebhookAttempt`.

Two real schema-policy findings, not invented ones. First, **the eighth instance** of this file's own seven-times-repeated `hasRole('system')` gap: `WebhookEndpoint`'s `@@allow("read", ...)` didn't admit a system context, so the subscriber's own endpoint lookup would have silently matched zero endpoints against every event, forever, with nothing anywhere to notice. Fixed the same way as every prior instance — `schema.cstack` only, no DDL consequence, not regenerated — and `crates/sms-api/tests/system_context_golden_list_live_postgres.rs` moved `WebhookEndpoint` into `SYSTEM_READABLE_MODELS` to match. Second, found live while writing this PR's own tests and **deliberately not fixed here**: `WebhookAttempt`'s own `list`/`detail` policy has no `hasRole('system')` branch at all — only `create`/`update` do. Nothing #38/#39 builds ever reads `WebhookAttempt` under a system context in production, so this PR's own live tests read it back under `owner()` instead of `sys()`; #40's `hooks` claim loop will need that clause the moment it exists to claim attempts for delivery — the same shape as the eight instances before it, flagged here rather than fixed pre-emptively for a role this PR doesn't own.

A third real finding, caught by Lightbridge's review of this PR and independently confirmed before fixing, not a policy gap this time but a structural-reachability bug of exactly the same "advertised but never actually fires" shape: `message_event_type` mapped `MessageState::accepted` to `Some("message.accepted")` — correct per §8.4's own catalogue — but the first cut of `register_subscribers` wired up only `on_message_updated`. `accepted` is `Message.state @default('accepted')`, the row's state the instant it's created, and `message_state_transitions` (§2.10) lists it only as a `from_state`, never a `to_state` — nothing transitions *into* `accepted`, ever. So `message.accepted` could only ever have arisen from a `Message.created` event, which nothing subscribed to: an endpoint configured for `message.accepted` would have silently never fired, forever, exactly the "would have shipped looking correct" failure class this repo keeps finding. Fixed by registering `on_message_created` alongside `on_message_updated` in the same function, both driving the same `enqueue_message_webhook_attempts` — so nothing can register one without the other — and proven with a live test that goes through a real `db.message().create(...)`, not just the mapping function in isolation (a unit test asserting `message_event_type(accepted) == Some("message.accepted")` would have passed both before and after this fix, which is precisely the blind spot that let it through). The dedupe index (`endpoint_id`, `aggregate_id`, `event_type`) was also verified live to hold across the `created`/`updated` boundary, not just reasoned about: calling `enqueue_message_webhook_attempts` a second time against the same still-`accepted` message, simulating a retry or a race, still produces exactly one row.

Event coverage is deliberately narrow, the same scoping precedent #35's single `expire_stale` job kind set: only `Message.created`/`Message.updated` → `message.accepted/submitted/delivered/failed/expired/uncertain/cancelled` per §8.4's own catalogue (`queued`/`routed`/`undelivered`/`rejected` produce no event — not in the catalogue, matching the doc's own list exactly, not a gap). `OptOut.created`, `Provider.updated` (→ `provider.degraded`/`provider.recovered`), and `SenderIdRegistration` (which doesn't even `@@emit` today) are explicitly out of scope: `OptOut` has no `appId`, and every match in this milestone keys on `WebhookEndpoint.appId`, so which endpoints a global, cross-app opt-out should notify is a real product decision this PR doesn't make.

The stored `WebhookAttempt.payload` is the `data` object only (§8.4's `messageId`/`appId`/`clientRef`/`to`/`state`/`operator`/`segments`/`costXaf`, with `to` masked per the matched endpoint's own `maskRecipient` at insert time via `sms_msisdn::Msisdn::masked`), not the full outer envelope (`id`/`type`/`occurredAt`) — the natural `id` for that envelope is `WebhookAttempt.id` itself, which doesn't exist yet at subscriber time (it's the row the subscriber is in the middle of creating). Building the envelope, signing it, and delivering it is #40/#41's job, not this one's.

`drain`'s oldest-undelivered-age alerting (§39's own acceptance line: "alert on oldest-undelivered age, not just on errors") is a fifth named R1 exception — `cratestack_event_outbox` isn't a schema model (it's created lazily by the framework itself), so no delegate can read it; `CONTRIBUTING.md`'s exceptions table and `ci/assert-no-raw-sqlx.sh` both name `crates/sms-worker/src/drain.rs`. Found live while writing its own test, not assumed: `EXTRACT(EPOCH FROM ...)` returns Postgres `NUMERIC`, not `FLOAT8` — sqlx's `Option<f64>` decode rejected it outright ("mismatched types ... NUMERIC") until an explicit `::float8` cast was added.

`crates/sms-worker/src/lib.rs`'s role dispatch (`Role::Drain => { drain::run(ctx, worker).await; return; }`) is a small, mechanical addition, kept minimal on purpose — a sibling PR adding `Role::Hooks`'s own real body (#40) will conflict trivially with it. The stub test that used to exercise `Role::Drain` (`a_stub_role_never_resolves_on_its_own`) now uses `Role::Hooks` instead, the only role still a pure `std::future::pending` stub.

## Regenerating migrations — this repo's actual workflow, found the hard way

**Check your `cratestack` CLI version before running any of this — every time, not from memory.** This has drifted before: at the time of #121 (see below) the globally installed CLI was `0.7.4` against a pinned library family of `=0.6.7`, and the newer CLI's emitter produced foreign-key `ALTER TABLE` statements the pinned emitter never had — confirmed by running the diff against the *unmodified* schema and seeing it already disagree with the committed `0001_init`. **Corrected 2026-08-11 (#59): that specific mismatch no longer exists** — `cratestack --version` now reports `0.7.10`, exactly matching the root `Cargo.toml` pin (`=0.7.10`), verified by hand before regenerating anything for that PR. This entry stays as a standing instruction, not a one-time fact, because the two numbers move independently (the CLI is a global install on whatever machine runs this; the pin is a file in this repo) and nothing automated checks them against each other — the next mismatch will look exactly like the last one: a diff that "by the book" silently produces migrations the compiled library never emits. **A policy-only `@@allow` change never touches DDL and must not be regenerated at all** (that is how #121 correctly avoided this). For a real schema change, match the CLI to the pin first, every time.

There is no committed `schema.snapshot.json` baseline, so `cratestack migrate diff` has nothing to diff *against* — every invocation emits the **complete current schema**, not an incremental delta. `0001_init` already followed this shape before anyone here made it a deliberate policy: it contains all 16 (now 19) `CREATE TABLE`s in one file. That's fine and intentional at this stage — there is no live database anywhere, so there is no data-preservation reason to want a true incremental migration.

So: when the schema changes, **regenerate `0001_init` wholesale** with the exact command in §2.10, don't try to hand-write an incremental one. Then regenerate `0002_bootstrap` from the doc. Both from scratch, both committed, every time:

```bash
cratestack migrate diff --schema schema/schema.cstack --out-dir schema/migrations --backend postgres --name init
# copy the output over schema/migrations/postgres/0001_init/{up,down}.sql
python3 ci/gen-bootstrap-sql.py schema/migrations/postgres/0002_bootstrap/up.sql
```

The tool also writes `schema/migrations/postgres/schema.snapshot.json` as a side effect. Delete it — this repo doesn't use snapshot-based incremental diffing, and a stale one committed by accident would be misleading.

**Verify against a real database before trusting the regeneration**, not just `cratestack check` — "parses" is not "compiles" is not "applies". `docker run --rm -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16`, apply both migrations in order, then run `ci/test-state-machine.sql`. This is how the 0.5.0 enum-type change below was actually caught — `cratestack check` and `cargo build` both stayed green through it.

## The live suites run in CI now — and that changed everything

**Until #118, `.github/workflows/ci.yml` ran a bare `cargo test --workspace` with no `--ignored`, so all 14 live-Postgres suites were silently skipped in CI and had only ever been run by hand.** That is not a hypothetical gap: this file already records #29's `claim_live_postgres.rs` sitting unrun for a whole milestone while hiding a policy bug that made its query return zero rows. A suite CI never executes is the purest form of the "green `cargo test` proves nothing" problem `#87` is the reference example for.

`crates/sms-test-support` (#118, stabilised by #120) replaced the old convention — a human running `docker run postgres:16` and `ci/apply-migrations.sh`, then exporting `DATABASE_URL`. It manages **one** container by talking to the `docker` CLI directly, keyed by a fixed name and a distinctive label, and gives **each test binary its own database** inside it, created via `CREATE DATABASE ... TEMPLATE` from a once-migrated template and dropped/recreated per run. Live suites stay `#[ignore]`d; `just test-live` runs them, `just test-live-clean` removes the container.

Five things about it are load-bearing, each learned by something breaking:

- **Never cache a container handle in a `static`.** The first attempt held `testcontainers::ContainerAsync` in a `OnceCell`, reasoning that `Drop` would clean up. **Rust never runs `Drop` for a `static`'s contents on any process-exit path**, so every run leaked its container — 56 orphaned Postgres instances filled a 32 GB laptop before anyone noticed. There is no Ryuk reaper installed to catch what `Drop` misses. Nothing here may depend on a destructor running at exit.
- **Cleanup is scoped by the harness's own label (`dev.vsms.test-harness=true`), never by image or name.** A sweep filtered by `ancestor=postgres:16-alpine` would cheerfully destroy a developer's unrelated running database. Never `docker prune` in any form.
- **One database per test *binary*, not one shared database.** All 14 sharing one database let `kill9_reclaim_live`'s real `sms-worker --roles dispatch` subprocess claim *other suites'* leftover messages — the claim loop deliberately selects any eligible row, as it must in production. Passed alone, timed out under the full sweep.
- **The migration check fingerprints migration *content*** (stamped via `COMMENT ON DATABASE`), not merely whether `public.messages` exists. The existence check silently served a **stale schema** from a pre-existing container after a bootstrap-only change, so tests reported `ok` against migrations that had never been applied.
- **The container name is fixed and global**, so two concurrent `cargo test` invocations on one machine fight over it and corrupt each other's runs. This is real, not theoretical — it cost one investigation a stress run. Don't run overlapping live-test processes; scoping that name is tracked follow-up work.

`ca653a1` (#102)'s per-binary `tokio::sync::Mutex` remains load-bearing on top of all this: tests *within* one binary still share that binary's database, and Postgres's own `pg_type` catalog race on first use is what it exists to serialize. **Two suites never picked that pattern up** — `rbac_layer2_live_postgres.rs` (added by #112 ten hours *after* `ca653a1` landed) and `sms-worker/tests/live_postgres.rs` (predating it, shielded only by being unrun) — and both flaked in CI within hours of #118 turning the lights on. Any new live suite must take the mutex.

**A live suite can also fail for a reason that has nothing to do with Postgres — and #192's own M3 gate did, immediately, on `main`.** `app/sms-worker/tests/hooks_node_receiver_live.rs` spawns `node src/gate-receiver.ts` as a real subprocess out of `examples/node/webhook-receiver`. The `live` job installs `psql` and nothing else, so there was no Node toolchain and no `node_modules` on that runner: every run since #192 merged died at spawn with the test's own `"check that `pnpm install` has been run"` panic, and `main` was red on exactly that until it was fixed. It passed locally because a human had run `pnpm install` in that directory by hand — the same "green on the one machine that has the undeclared prerequisite" shape as `#87`, one layer up from Rust.

Two things about that example directory are load-bearing and were the actual root cause:

- **`pnpm-workspace.yaml` covers `admin` and `packages/*` — `examples/*` is deliberately outside it**, because the example is meant to be copied out and run standalone by an integrator. So a root `pnpm install` never installs it, and running `pnpm install` *inside* it without `--ignore-workspace` resolves against the root workspace and writes **no lockfile at all** (it succeeds, which is what makes it misleading). It now carries its own committed `pnpm-lock.yaml` and CI installs with `--ignore-workspace --frozen-lockfile`, so a floating `express@^5.1.0` can't change under CI — the unpinned-dependency-in-a-pipeline shape this file's release-engineering notes warn about elsewhere.
- **The same gap silently un-gated the cross-language signature proof.** `pnpm turbo run test` reaches workspace packages only, so `examples/node/webhook-receiver/src/cross-language-vectors.test.ts` had never run in CI either — while this file claimed the HMAC-SHA256 scheme was proven on both sides against `openssl`-computed fixtures, naming `pnpm test` as the TypeScript half's gate. The Rust half genuinely was gated; the TypeScript half was hand-run once. A cross-language agreement proof that only one side checks in CI is precisely the half that drifts. The `js` job now runs it.

## The demo runs, and the deployment exists — both landed 2026-08-08

**`just demo` brings up the whole system and a message reaches `delivered`.** Proven end to end twice, once from a cold reset, including a send from the admin console's composer showing up on `/messages` — cross-checked three ways (the UI, the Postgres row, and `sms-fake-orange`'s own log for that exact message id). Three things had to land first, and each was a real hole rather than a packaging exercise:

- **`#134`** — `msisdnHash`/`bodyHash` were plain unkeyed `SHA-256`, reversible in seconds over Cameroon's ~10^7 numbering space, while `docs/architecture.md` had always claimed HMAC-under-a-pepper. Now `hmac-sha256-v1:<hex>` keyed by `SMS_HASH_PEPPER` (`crates/sms-api/src/pepper.rs`). `Procedures::default()` is **deleted** so no construction site can silently get an unpeppered one, and the pepper is validated before the pool connects. Rotation does **not** rehash stored rows; see that module's doc.
- **`#137`** — nothing could produce an HTTP-usable credential. `provisionAppClient` needs `owner`/`admin`; `GatewayAuth` only ever mints `role: "app"`. `sms-gateway provision-client` closes it, writing `privateKeyPem` once with `O_EXCL` + `0600`. Its live test spawns a genuinely separate `serve` process and completes a real `private_key_jwt` exchange — the thing `send_test_message.rs` never proved, since the `AppClient` it writes has no `OauthClient.jwks`.
- **`#138`** — `crates/sms-fake-orange` had no binary target, so nothing could demo past `routed`. `app/sms-fake-orange` runs it as a process on a fixed port. Note `FaultPolicy::Scripted` *silently degrades to a bare accept with no DLR* when its queue empties — fine for a test that scripts exactly as many entries as it expects, wrong for a long-lived server, which is why `FaultPolicy::Always` exists.

**`#139` built the deployment**: three non-root glibc Dockerfiles (**not** musl — `AGENTS.md`'s own note says `rustls-no-provider` panics at `reqwest::Client::new()` without a `CryptoProvider` installed in `main`, and that path is unverified), a `deploy/` compose stack with a Caddy edge, an advisory-lock-guarded one-shot migrate job that **applies but never regenerates** migrations, `GET /healthz` on the gateway, and a GHCR release workflow on `v*.*.*`. Unverified and worth not assuming: real ACME issuance (tested with `tls internal` only), the GHCR publish path (no tag pushed at the time), and concurrent `migrate` racing under load. **Stale as of 2026-08-10** — see "rustls, musl, and distroless" below: the unverified path got verified, `sms-gateway`/`sms-worker` are musl-on-distroless now, and the migrate job is a small Rust binary (`app/sms-migrate`), not the `postgres:16-alpine` + `psql` image this paragraph describes.

**Two corrections to this file, both found by running the system rather than reading it.** First: the M1 paragraph above used to say the gateway "fails loudly on the first `/token` request if no active key exists, not at process start". **That was wrong** — `serve` calls `load_signing_keys(...)?` before binding the listener, so it exits at startup. It matters for orchestration: anything that waits for the gateway to be healthy before rotating a key deadlocks permanently, which is why the deploy runbook uses `docker compose run --rm` rather than `exec`. Second: `rust-version` claimed `1.85` while the committed `Cargo.lock` needs `1.88`; no CI job ever checked the claim, so it drifted silently.

One more of the same shape, caught wiring a container `HEALTHCHECK`: `admin/app/api/health` was behind Basic Auth, so under `DASHBOARD_AUTH=basic` — the only mode `NODE_ENV=production` accepts — an unauthenticated liveness probe got a permanent `401` and the container sat `unhealthy` while the process was fine.

**`#163` and `#168` both closed the same shape of gap — key the limiter where the identity is actually known — and landed together because the fixes interact.** `#163`: `crates/sms-api/src/router.rs`'s `RateLimitLayer` on the authenticated API surface keyed on `client_id_fingerprint`, an unverified bearer-token `sub` — a caller willing to forge a fresh `sub` per request got a fresh, full bucket every time, bypassing the per-principal limit entirely (the idempotency layer had the same shape of bug and was fixed first, in #153/#161, by requiring a *verified* `sub`; that fix doesn't transfer here, since `RateLimitLayer` only ever consumes from a bucket, never writes a value another request reads back, so the cheaper unverified read stays correct — the aggregate-throughput consequence is the only thing that needed closing). Fixed with a *second*, coarser `RateLimitLayer` keyed on `ConnectInfo<SocketAddr>` (`source_fingerprint`) — the real TCP peer, unspoofable, populated because `app/sms-gateway/src/main.rs` now serves through `into_make_service_with_connect_info`. Deliberately not `X-Forwarded-For`: found while designing this fix, not assumed, that `deploy/docker-compose.yml` has **two** internal callers of this router, not one — Caddy, and `admin` (`SMS_API_URL: http://sms-gateway:8080`, bypassing Caddy) — so a blanket trust config can't tell them apart, and Docker Compose assigns container IPs dynamically with no static-allowlist infrastructure to pin a single trusted hop against. `client_id_fingerprint` itself is untouched; the new layer only bounds the aggregate a flood of forged identities can reach.

`#168`: #156's Caddy-edge `/token` rate limiting keys on source IP only — `client_id` arrives solely in the form-urlencoded POST body, and every way the edge could read one field out of it was checked and rejected (documented with receipts in `deploy/Caddyfile`'s own comment) — so §4.2's "client_id *and* source IP" composite was never actually implemented, only the IP half. Fixed with a second, defense-in-depth limiter, `app/sms-gateway/src/token_rate_limit.rs`, mounted on `/token` itself in `app/sms-gateway/src/op.rs` (not `sms-auth`, not a first-party Caddy module — both real options, weighed and set aside for more work with the same outcome), keyed on the real `client_id` read from the request body it already buffers. This is a narrow, explicit reversal of §4's own "an infrastructure concern, not `sms-auth`'s" framing from #22 — justified because the edge #156 built to satisfy that framing turned out structurally unable to reach the composite key §4.2 itself already specified; the edge keeps doing flood protection, this layer adds only the dimension it cannot reach. Buffers and reconstructs the body via `axum::body::to_bytes` + `Request::from_parts` rather than consuming it — proven directly with a round-trip test, not assumed, since a `/token` handler receiving a drained body breaks every real exchange, not just an attacker's.

Both proven against the actual attack, not just a happy path: a flood of requests with a different forged `sub` each time is throttled collectively once the coarse bucket's burst is spent (`crates/sms-api/src/router.rs`'s own live-server test asserts `404, 404, 404, 429, 429` against a 3-token bucket), while a lone honest client at default production budgets never sees a `429`; a burst of `/token` requests sharing one `client_id` is throttled while a different `client_id` sent alongside is unaffected (`app/sms-gateway/src/token_rate_limit.rs`'s own tests). `docs/architecture.md` §4.2/§4.5/§4.6 and `deploy/Caddyfile`'s own `#168` comment are updated to match — this file has now recorded three separate instances of doc-vs-code drift in one day (the M1 "fails on first /token request" claim, `rust-version`, and the `/token`-rate-limiting-mechanism table row that named a crate `sms-auth` never linked), which is why this PR treated updating both as part of the fix, not a follow-up.

## `cargo deny` wired into CI, and the `rsa`/Marvin-Attack reachability call — landed 2026-08-10

`.github/workflows/ci.yml` never ran `cargo deny check` (#174) — the `deny.toml` and `just deny` existed, but nothing in CI called either, so `cargo deny check advisories` had been failing on `main` on RUSTSEC-2023-0071 (Marvin Attack: timing sidechannel key recovery in `rsa`) for however long it was present, silently. Same shape as the pre-#118 problem of live suites nobody ran. A new `deny` job now runs `EmbarkStudios/cargo-deny-action@v2` (all four categories: advisories, bans, licenses, sources) on every push and PR.

**There is no fixed version of `rsa` for RUSTSEC-2023-0071 — it cannot be resolved by bumping.** The advisory reads as a blanket "avoid using the `rsa` crate in settings where attackers can observe timing," which is not the same question as "is *this deployment's* actual use of it exploitable." `rsa` enters the graph twice, both under `authkestra-engine 0.3.3` (the OP that signs every access token and verifies `private_key_jwt` client assertions — not a leaf dependency): directly, and transitively through `jsonwebtoken 11.0.0`'s `rust_crypto` RS256 backend. Read both call sites rather than trusting the advisory headline (`cargo tree` cannot answer this — it only shows edges, not what the code does with them):

- `jsonwebtoken-11.0.0/src/crypto/rust_crypto/rsa.rs` calls only `Pkcs1v15Sign`/`Pss` `Signer::sign_with_rng` (a private-key **sign**) and `Verifier::verify` (a **public-key-only** verify). No `Decryptor`, no `decrypt`/`decrypt_blinded` call anywhere in the file.
- `authkestra-engine-0.3.3/src/token/mod.rs`'s `TokenManager::new_asymmetric` uses `rsa::` only to parse a PEM-encoded RSA private key and read `n`/`e` off it to publish the public JWK. Also no decrypt call.

The Marvin Attack (RUSTSEC-2023-0071's own CVSS vector: `C:H/I:N/A:N`, confidentiality-only) is specifically a **decryption**-oracle timing attack: an attacker submits chosen ciphertext and a network-observable timing difference reveals whether PKCS#1 v1.5 padding validated, which is what lets the private key be recovered. RSA **signing** exponentiates the private key over data this service itself chooses (never attacker-supplied ciphertext), and verification touches only the public key — neither operation hands a network attacker the decryption oracle the attack needs. Grepping both dependency sources for any decrypt-shaped call (`rsa::.*[Dd]ecrypt`, `Oaep.*decrypt`, `Pkcs1v15Encrypt`) returns nothing. Conclusion: **accepted, not silenced** — `deny.toml`'s `[advisories] ignore` entry for RUSTSEC-2023-0071 carries this same analysis inline, is scoped to that one advisory id (so any *other* new advisory still fails the job), and is time-boxed to be re-checked by 2026-11-10 or sooner if `authkestra` bumps past `0.3.3` or `rsa` ships a patched release — whichever comes first.

## Milestone 3 started: webhook signing and secret rotation (#41) — landed 2026-08-10

M3 (events, outbox drain, webhook delivery — epic #37) opens with `#41`, landed independently of `#38`–`#40`/`#42` (subscribers, `drain`, `hooks`, `reap_outbox` — all still open). Two things, deliberately factored apart:

**Cross-language proof, not just a doc-comment claim.** `crates/sms-webhook/tests/fixtures/cross_language_vectors.json` — signatures computed by a third tool (`openssl dgst -sha256 -hmac`, receipts in the file's own `$comment`), not by this crate's code or by the Node example's — is asserted against by both `crates/sms-webhook/tests/cross_language_fixtures.rs` (plain `cargo test`, no `--ignored`) and `examples/node/webhook-receiver/src/cross-language-vectors.test.ts` (`pnpm test`, Node's built-in test runner). `examples/node/webhook-receiver` predates #41 (`#150`) and was written against §4.4's prose with one flagged, honest guess — the MAC algorithm; its own README called this out explicitly as "the one genuine guess." Explicitly out of scope, matching #41's own issue text and this repo's M2-era convention of naming a scope cut rather than leaving it implicit: the `cleanup_secrets` job (§7.5) that clears `prevSecret` after 24 hours — one of the eight not-yet-built job kinds `#35`'s own status paragraph already lists — and everything `#38`–`#40`/`#42` own (outbox subscribers, the `drain` role, the `hooks` role that would actually attach these headers to an outbound HTTP request, and poison-row handling). `rotateWebhookSecret` and `crates/sms-webhook` are the signing/rotation half of the epic's own gate ("signature verifies in a sample Node receiver"); the other two clauses (no event loss on a mid-drain kill, exactly-once attempts across two workers) are `#44`'s, not this PR's.

## `#42` — `reap_outbox` and poison-row handling — landed 2026-08-11

§7.5's own table already answers the question a story like this has to resolve before writing any code — reap or quarantine a poison row: "Delete delivered `cratestack_event_outbox` rows >24h; alarm on high-`attempts` rows." That is a hard split, not a suggestion. `crates/sms-worker/src/jobs/reap_outbox.rs` implements exactly that, nothing more:

- **Delivered rows** (`delivered_at IS NOT NULL`) past a 24h retention are deleted. They already did their job — nothing in this codebase ever reads a delivered outbox row again — so keeping them is pure bloat.
- **Poison rows** (`delivered_at IS NULL`, `attempts` past #42's own threshold of `5`) are never deleted. A row stuck retrying forever is live evidence of a subscriber bug (§8.2: "short-circuits on the first failing handler," retried from the top on every drain); deleting it would erase the only record the bug happened *and* silently drop the event it was trying to redeliver — a customer-visible loss with no trace, strictly worse than an oversized table. Instead this job logs a `warn!` per row, every run, carrying `model`/`operation`/`last_error` so an operator can actually diagnose it. "Quarantine" (moving the row to a second table) was considered and rejected: there's no schema model backing this table in the first place, so a quarantine table would just be a second hand-rolled, policy-less table for no benefit over leaving the row in place and alerting loudly.

**Checked directly against the vendored source before writing any of this, not inherited from this file's own prose** (this file's own §8.2 section already says "no retry cap, no backoff, no dead-letter," but repeating a claim isn't the same as verifying it): `cratestack-sqlx-0.7.10/src/descriptor.rs`'s `drain_event_outbox` only ever `UPDATE`s `attempts = attempts + 1, last_error = $2` on a failed delivery and leaves `delivered_at` `NULL` — no comparison against any cap anywhere in that function, and no code path anywhere in `cratestack-sqlx` deletes a row of this table at all. `reap_outbox` is the entire mechanism; nothing upstream partially covers it.

**R1 exception, the sixth one** (`crates/sms-worker/src/jobs/reap_outbox.rs`, added to `ci/assert-no-raw-sqlx.sh` and `CONTRIBUTING.md`'s own table) — same reasoning as `drain.rs`'s fifth: `cratestack_event_outbox` has no schema model and therefore no delegate. Unlike `drain.rs`, this job can't lean on `db.events().drain()` having already run `ensure_event_outbox_table` immediately beforehand (it never calls `.drain()` itself, and nothing guarantees it runs after some other write already has), so both queries treat Postgres's `42P01 undefined_table` as "nothing to reap yet" rather than duplicating the framework's own table DDL a second time in application code.

Wired into the existing #35 infrastructure as a sibling of `expire_stale`, not a parallel mechanism: registered in `jobs::default_registry()`, scheduled hourly (§7.5's own cadence) in `scheduler::schedule()`.

**Live-tested against a real Postgres, and the tests were verified to actually fail, not just pass by construction** — the same discipline `#155`'s golden test and `ExpireStale`'s own tests already established in this file. `crates/sms-worker/tests/reap_outbox_live_postgres.rs` has no delegate to assert outbox state through either, so it proves "still there" and "gone" indirectly: a poison row's survival is proven by re-triggering `db.events().drain()` after `ReapOutbox::run_at` and observing the same always-failing handler fire again for the same message (a deleted row cannot be redelivered to anything); a delivered row's fate is read directly off `reap_delivered`'s own return value, `pub` for the same reason `drain::oldest_undelivered_age` is. Both guards were confirmed to catch a real regression by temporarily loosening each query's own `WHERE` clause (dropping the cutoff comparison, and admitting `delivered_at IS NULL` rows) and watching the corresponding test fail with the expected assertion, then restoring the correct query and watching it pass again — not assumed to work from reading the SQL.

## Milestone 3: the `hooks` role landed (#40) — outbound HTTP delivery, retries, and circuit breaking

`crates/sms-worker/src/hooks.rs` is `Role::Hooks`'s real body — the fifth role with an actual loop, and the piece that finally makes a `WebhookAttempt` row turn into an outbound HTTP request. `crates/sms-worker/src/claim.rs` gained `impl Claimable for WebhookAttempt`, reusing #29's CAS claim loop rather than a bespoke one, per that trait's own stated intent.

**The missing transition table, resolved in favour of R2 discipline, not an exception.** `AttemptState` shipped with #38/#39 but no `attempt_state_transitions` table or trigger existed — nothing had written `WebhookAttempt.state` yet, so R2 had nothing to decide against, and #38/#39's own PR left the question open for whoever built the first real driver. This PR adds `attempt_state_transitions` + `attempts_guard_transition` (§2.10, `0002_bootstrap` regenerated from the doc) — five edges: `pending -> delivering`, `failed -> delivering`, and `delivering -> {succeeded, failed, dead}`. `delivering -> dead` covers both reasons §8.5 stops retrying outright (`maxAttempts` exhausted, or an immediate 410 Gone); there is no `failed -> dead` edge, because the exhausted-attempts decision happens once, at the `delivering -> {failed | dead}` write itself. A `delivering` row whose lease expired (crash-reclaim) is a same-state write — same shape `Message`'s own `routed` reclaim already uses — so it needs no row in the table at all. Verified against a real Postgres, not just `cratestack check`: `ci/test-state-machine.sql` gained assertions for the auto-stamped `delivered_at`, the terminal `succeeded`/`dead` states, and the `failed -> delivering` retry edge; `ci/assert-state-machine-parity.py` now checks a third machine (`attempt`, alongside `message`/`job`) against a new `stateDiagram-v2` block in §8.5.

**`maxAttempts` is a `WebhookEndpoint` column, read per candidate, not a constant** — the backoff schedule itself (§8.5: 1s, 5s, 25s, 2m, 10m, 1h, 6h, 24h) is fixed and shared, same convention `jobs::backoff_for` already set, but how many entries into it a given endpoint actually gets before `dead` is that endpoint's own row.

**What resets `WebhookEndpoint.consecutiveFailures` — a design question the issue posed explicitly, answered and documented in §8.5's own "Implementation, #40" note:** a successful delivery resets it to zero (and clears `circuitOpenUntil`, defensively); crossing the 20-failure threshold that *opens* the circuit also resets it to zero, so the cool-down period is followed by a fresh 20-failure allowance rather than the very next post-cooldown failure reopening the circuit immediately. Candidate selection excludes both an inactive endpoint and one whose circuit is open — application-side, in `claim.rs`'s own `filter_by_endpoint_health`, not a join in the claim query itself, since `WebhookEndpoint` has no `@version` for a join to claim against even if the delegates offered one. By construction this also means `hooks` never records a failure against an endpoint whose circuit is already open — it never attempts one.

**What gets POSTed, confirmed before deciding what to sign, per the issue's own warning against that exact bug class:** `WebhookAttempt.payload` (written by #38's subscribers) is the §8.4 `data` object only, not the outer envelope — confirmed by rereading `webhooks.rs`'s own module doc before writing a line of `hooks.rs`. `build_envelope` constructs `{id, type, occurredAt, data}` at delivery time: `id` from `WebhookAttempt.id` (the only value that has existed since the row was created), `type` from `eventType`, `data` from `payload` parsed back into a JSON value and embedded as a nested object — never re-wrapped as a string. `occurredAt` is a documented approximation, not the original event's timestamp: `WebhookAttempt` carries no creation timestamp (no `@use(Timestamps)` on that model), and the framework's own `ModelEvent::occurred_at` is read and discarded by #38's subscriber before this row exists to store it on. `hooks` stamps it with the time of delivery instead — accurate for a first attempt, wrong by up to the full backoff schedule's span (24h) for an attempt that only succeeds on its last try. Closing this needs either `WebhookAttempt` to gain a stored event timestamp or #38's subscriber to thread `ModelEvent::occurred_at` through to it — both real changes to a model #38 owns, flagged here rather than silently accepted or fixed as a drive-by. **What gets signed is exactly what gets sent:** `build_envelope` returns one `String`; its bytes are both what `sms_webhook::sign_header` HMACs and what `reqwest` puts on the wire, never two independent serializations of the same logical value — `serde_json::Value`'s map type does not guarantee stable key order or whitespace across two separate `to_string()` calls, so a second serialization would risk exactly the silent sender/receiver mismatch this issue named as the classic bug to avoid.

**`maskRecipient` — enforced upstream (#38), verified not to be defeated here.** The masked (or unmasked) `to` value is already baked into `payload` at insert time via `sms_msisdn::Msisdn::masked`; `hooks.rs` never reads a `Message` row and never touches `payload`'s individual fields — it parses the whole object and embeds it verbatim. `hooks_live_postgres.rs`'s `a_masked_recipient_reaches_the_endpoint_unchanged_never_reconstructed` proves this against a real HTTP capture (wiremock's own `received_requests()`), not just a unit test of `build_envelope`: the masked value from a hand-seeded payload survives byte-for-byte into the actual POST body, and the fixture's own unmasked E.164 form is asserted absent from that body entirely.

**The ninth instance of this file's own `hasRole('system')` gap — flagged in advance by #38/#39's own PR, not found live.** `WebhookAttempt`'s `list`/`detail` policy had `create`/`update` admitting `hasRole('system')` from the start but no such clause on `list`/`detail` — #38/#39's own module doc named this explicitly as the gap `#40`'s claim loop would need closed the moment it existed. Fixed here (`schema.cstack` only, no DDL consequence), `crates/sms-api/tests/system_context_golden_list_live_postgres.rs` moved `WebhookAttempt` into `SYSTEM_READABLE_MODELS`, and the guard was proven to actually fail first — `hasRole('system')` temporarily removed from the `list`/`detail` clause reproduced exactly `assert_system_can_read_back!`'s failure message, naming `WebhookAttempt` and its (broken) clause, before being restored.

**Endpoint-side writes (`consecutiveFailures`, `circuitOpenUntil`, `active`) carried no CAS at the time** — `WebhookEndpoint` had no `@version`, the same fact `rotateWebhookSecret`'s own doc named (that procedure closed a *different* race with `@isolation("serializable")`, which didn't cover concurrent `hooks` workers failing against the same endpoint). Accepted as a best-effort read-modify-write: under concurrent failures the counter could under-count by a small amount, which only mattered for a heuristic that exists to stop hammering a dead endpoint, not a value anything bills against. **#59 added `@version` and `if_match` to these three writes** (`crates/sms-worker/src/hooks.rs`'s `record_endpoint_failure`/`reset_endpoint_failures`/`deactivate_endpoint`) without changing this paragraph's own accepted-under-count reasoning: each call site's existing `if let Err(error) = ... { warn!(...) }` already treated any write failure as best-effort and moved on, so a lost CAS race falls into the identical arm a lost silent-overwrite used to — the under-count is now a *detected*, not a *silent*, best-effort miss. See that section for the full reasoning.

`crates/sms-worker/src/lib.rs`'s role dispatch gained `Role::Hooks => { hooks::run(ctx, worker).await; return; }` — the small, mechanical addition #38/#39's own PR predicted would conflict trivially with a sibling PR adding `Role::Hooks`'s real body, which this is. The stub test that used to exercise `Role::Hooks` (`a_stub_role_never_resolves_on_its_own`) now uses `Role::Smpp` instead — the only role left with no real body (M7).

`crates/sms-worker/tests/hooks_live_postgres.rs` (8 tests, `wiremock`-backed): a clean delivery with a verified `sms_webhook::verify` signature and envelope shape against the exact bytes captured off the wire; a transient failure's backoff and endpoint bookkeeping; `maxAttempts` exhaustion going straight to `dead`; 410 Gone killing the attempt and deactivating the endpoint in the same tick; the circuit breaker opening and excluding the endpoint from the very next claim; the masked-recipient pass-through above; a malformed-payload attempt proven to leave the endpoint's circuit-breaker state untouched (see below); and a simulated crash-reclaim (a stale `delivering` lease) resuming without double-counting `attempts`. All pass stably across reruns against the same persistent database, same convention every other live suite here follows.

**Found by Lightbridge's review of this PR, confirmed real, and fixed before merge: a malformed payload must never trip an endpoint's circuit breaker.** The first cut routed a `WebhookAttempt.payload` that failed to parse as JSON — our own bug, written by #38's subscriber, not the endpoint's fault — into the same `Outcome::Retryable` arm a genuine HTTP failure uses, whose handling unconditionally calls `record_endpoint_failure`. A single corrupt row could therefore increment `consecutiveFailures` and open the circuit on an endpoint that was never sent a request and never did anything wrong — and retrying was pointless besides, since a stored payload never becomes parseable, so it only delayed an identical `dead` outcome while tripping the breaker on every attempt along the way. Fixed with a fourth `Outcome::MalformedPayload` variant, handled by its own arm: straight to `dead` with a loud `error!` (matching `#42`'s own `reap_outbox` precedent above — "make a broken row loud rather than quietly retry or hide it" — landed in the same milestone), and no call to `record_endpoint_failure` at all. `hooks_live_postgres.rs`'s `a_malformed_payload_goes_dead_without_ever_touching_the_endpoints_circuit_state` asserts the thing that actually matters — `consecutiveFailures` stays `0`, `circuitOpenUntil` stays unset, `active` stays `true`, and zero HTTP requests were ever made — not merely that the attempt reached a terminal state, which would have passed both before and after the fix. Verified to actually catch the regression: temporarily routing back through `Outcome::Retryable` reproduced a real test failure before the fix was restored.

## `#187`/`#193` — `WebhookEndpoint`'s two RBAC gaps closed together, landed 2026-08-11

Both found while implementing #41/#43, both filed rather than fixed inline (a schema policy question and a Layer 2 asymmetry, neither in scope for the PR that noticed them), both latent for the identical reason and closed together because they're the same shape: a caller narrower than "any human"/"nothing" respectively, and both invisible until M4 ships human logins (`GatewayAuth` still only ever mints `role: "app"`/`"system"` — #97/#98's scope cut, unchanged by this PR).

**`#187`: `WebhookEndpoint.read` narrowed from `auth().kind == "user"` to `hasRole('owner') || hasRole('admin') || hasRole('developer') || hasRole('system')`.** Before this, `auditor`/`operator`/`support` — none of which hold any webhook permission per §5.2 — could read a live signing secret that only `owner`/`admin`/`developer` could ever write. `@sensitive` never mitigated this (redacts audit snapshots only, no serde attribute — the field is still returned by the API, per this file's own §2.0 entry). **This is a reversible product call, not a forced one** — the issue's own named alternative was deciding secrets shouldn't live on a model humans read at all, on the grounds that an `auditor`'s oversight mandate is "see everything." Taken anyway, on the reasoning that oversight is served by seeing *that* a secret exists, was rotated, and when (every other field, untouched), not by seeing the secret's own value: a signing secret is a credential, not a record. `docs/architecture.md` §2.7's own `WebhookEndpoint` code sample and its "readable by humans only" paragraph are both updated to match — the code sample had also drifted from #41's actual `hasRole('system')` clause on `update` (present in `schema.cstack` since #41, never synced into the doc's illustrative block), fixed in the same edit since this PR was already touching that exact block.

Policy-only, no DDL: confirmed byte-identical, not assumed — `cratestack migrate diff` (isolated `=0.7.10` CLI, matching the pin) against the changed schema still diffs to nothing against the committed `0001_init/{up,down}.sql`, same verification `#100`/`#121` each record for their own analogous `@@allow` fixes. Migrations were correspondingly **not** regenerated.

**`#193`: `rotateWebhookSecret` gained `require_permission(ctx, "webhook:manage")`, matching `replayWebhookAttempt`'s own Layer 2 gate (#43, #191).** Before this fix, rotation — the more sensitive of the two operations, since it changes the credential every future delivery is signed with and starts the `prevSecret` overlap clock — enforced only Layer 1, while the less sensitive replay enforced both. The issue's own honest alternative (decide Layer 2 is redundant given Layer 1's already-role-scoped `@@allow`, and strike `webhook:manage` from §5.2's vocabulary instead) was rejected: a permission that appears in the role table and is never checked anywhere is worse than none, since it implies a control that doesn't exist, and `replayWebhookAttempt` already depends on it being real.

**The trap this PR's own test-writing hit, worth recording for the next Layer-2 addition to an existing procedure: adding a `require_permission` call to a procedure breaks every existing test that calls it with a context built by hand.** `Principal::into_context()` (`crates/sms-api/src/auth.rs`) never populates a `perms`/`scope` extension — only a real `GatewayAuth::authenticate` does, from JWT claims. `rotate_webhook_secret_live_postgres.rs`'s three pre-existing tests all called the procedure with a plain `owner()` context and started failing `Forbidden` the moment the gate was added, including the one asserting `NotFound` for a bogus id — `require_permission` runs *before* the lookup, so a missing-permission denial and a missing-row `NotFound` are trivially confused if the test context doesn't carry the claim the new gate checks for. Fixed by adding an `owner_with_webhook_manage()` helper (a plain `owner()` context plus a hand-inserted `perms: ["webhook:manage"]` extension) and switching every direct-call test onto it — the same pattern `replay_webhook_attempt_live_postgres.rs`'s own `developer_with_webhook_manage()` already established for the sibling procedure, just not yet needed here until this PR added the gate that makes it necessary.

**Denial proven live, the same way `replayWebhookAttempt`'s own gate was proven — the *allow* case still has no live token to prove it with (#97/#98).** `rotate_denies_a_caller_with_no_webhook_manage_permission` points the call at an endpoint id that doesn't exist and asserts `Forbidden`, not `NotFound` — the latter would mean the check was skipped and the lookup ran anyway. Verified to actually catch a real regression, not just pass by construction: temporarily commenting out the `require_permission` call reproduced exactly that failure (`expected Forbidden, got NotFound("no WebhookEndpoint with id ...")`) before the call was restored.

## Milestone 5 started: the MTN adapter via a licensed aggregator (#61)

`crates/sms-provider-mtn` is a second `SmsProvider` implementation, mirroring `crates/sms-provider-orange-cm`'s structure and both traps it already learned. Per the epic (#60) and the issue's own text, this targets MTN capacity **bought through a licensed aggregator, not a direct MTN interconnect** — the same posture §6.4 already recommends and the path that avoids decision #4 (own ART title?) entirely.

**No real aggregator contract exists, and none of this has been run against a live endpoint** — the crate's own module doc carries the full honesty ledger, but the short version: the connect-vs-read transport-error classification (`classify_transport_error`, identical reasoning to Orange's) is exactly as trustworthy as it is in `sms-provider-orange-cm`, because it follows from what `reqwest` itself guarantees, not from any vendor's docs. The request/response JSON shape (`POST {base_url}/v1/messages`, Bearer API-key auth, a `201` + `messageId`, a DLR `POST` echoing that same `messageId`) is an **invented placeholder**, chosen to match the common pattern across the aggregators §6.2 already names as candidates (Nexah, Africa's Talking, Infobip, Twilio), not transcribed from a real Swagger the way Orange's shape was transcribed from §6.2. Replace the request/response structs — not the `SmsProvider` impl or the error classification around them — the moment a real contract exists.

**`Capabilities` is genuinely different here, and it's a structural difference, not just different constants.** Orange's `capabilities()` is a bare function with no inputs — every field is a fixed fact about a self-service product. MTN-via-aggregator has no such fixed facts: `tps_ceiling`, `cost_per_segment_xaf`, and `supports_alphanumeric_sender` are commercial terms of a specific contract, so `MtnAggregatorConfig` carries them as caller-supplied fields and `capabilities()` reads them back rather than returning a compiled-in constant. This is the actual answer to #61's "the routing layer must read them rather than assume parity" — a router that special-cased `if key == "orange_cm"` couldn't even express MTN's numbers, since they aren't constants to special-case against. One field goes the other direction: this crate's assumed DLR shape echoes back the same `messageId` `submit()` already returns, so unlike Orange (which needs `receiptRequest.callbackData` + `SubmitAck::provider_ref_alt` to work around a DLR that can't otherwise correlate, #95), `provider_ref_alt` is always `None` here — a property of the *assumed* shape, not a proven simplification; revisit it alongside `dlr::parse` the moment a real payload exists.

**The connect-vs-read `Indeterminate` guard was proven to fail, not just asserted to pass** — house standard, applied here as it was for `#119`'s original Orange implementation: `classify_transport_error` was temporarily edited to swap the two branches (a connect failure reporting `Indeterminate`, a post-connect timeout/body error reporting `Unavailable`), and both `a_connect_refusal_is_still_unavailable` and `a_post_connect_timeout_is_indeterminate` failed with the exact `assertion failed: matches!(...)` message naming the wrong variant, before the fix was restored and both passed again.

**No new external dependency.** Every crate `sms-provider-mtn` depends on (`sms-provider`, `async-trait`, `chrono`, `reqwest`, `rust_decimal`, `serde`, `serde_json`, `thiserror`, `tracing`; `sms-encoding`/`tokio`/`wiremock` as dev-dependencies) was already in the workspace graph via `sms-provider-orange-cm`. `cargo tree -i aws-lc-rs` still reports no match, `cargo deny check` stays clean, and `./ci/assert-no-raw-sqlx.sh` passes untouched — this crate makes no database call of any kind, matching `sms-provider-orange-cm`'s own R1-exempt status (never touches R1 in the first place: it's a pure HTTP adapter).

**One real duplication worth naming rather than fixing here:** `classify_transport_error`'s connect-vs-read logic is now byte-for-byte the same reasoning in two crates (`sms-provider-orange-cm` and `sms-provider-mtn`), because it's provider-agnostic `reqwest` behaviour, not provider-specific. Not factored into a shared helper in `sms-provider` itself in this PR — two instances isn't yet a rule, and #61's scope is "build the adapter," not "refactor the trait crate." Worth doing the moment a third HTTP adapter (the config-driven `AggregatorHttpProvider` §6.2 also names, or SMPP's own connect/write distinction) needs the same logic a third time.

## Milestone 5: the routing rules engine landed (#62)

`crates/sms-routing` replaces `crates/sms-worker/src/claim.rs`'s M2 `cheapest_active_provider` placeholder with real `Route`-rule routing over §6.3: priority, weight, and `matchOperator`/`matchClass`/`matchAppId`/`matchPrefix` predicates. `crates/sms-worker/src/routing.rs` is the I/O glue between the two.

**The engine is a new, deliberately pure crate, not a module inside `sms-worker`.** #54's admin route simulator has to answer "given this recipient/class/app, which route wins and why" *without sending anything* — the same requirement that shaped `sms-provider`'s own purity (no cratestack, no I/O). `sms_routing::select_route` takes a caller-fetched `&[RouteRow]`, a caller-fetched `&HashMap<String, ProviderRow>`, a `RoutingCandidate`, a caller-supplied `exclude: &ExcludedRouteIds`, and a caller-drawn `f64`, and returns a `Decision` — nothing in the crate touches a database, a clock, or an RNG. `crates/sms-worker/src/routing.rs::decide` is the one place that fetches rows and draws the randomness (`rand::random()`), the same "convert the schema's enum onto the pure crate's mirrored one" pattern `dispatch.rs`'s own `decode_encoding` already established for `Encoding`.

**Weight implies randomness; "deterministic and explainable" (#62's own framing) implies it can't generate its own.** Resolved by injecting the draw rather than generating it: production draws once per decision at the I/O boundary; a replay (#54's simulator, every unit test in `crates/sms-routing/src/engine.rs`) calls `select_route` again with the exact same `draw` and gets the exact same `Decision`, because the function is a pure fold over its arguments. Within the winning priority band, the draw maps to a cumulative-weight range per member (`[low, high)` over `[0.0, 1.0)`); an all-zero-weight band falls back to a uniform split rather than dividing by zero (`weight == 0` is a legal `@range` value, not an error).

**Priority is the only cross-band ordering — no independent "more specific route wins" tiebreak.** A route with three `match_*` predicates set doesn't automatically outrank a wildcard route at the same priority; an operator who wants that has to set a higher `priority` explicitly. Either reading was defensible; this one was chosen because §6.3's own text ("sort by priority then weighted-random within a priority band") already says so — it wasn't a free design choice this PR made, just the first place anyone had to act on it precisely.

**`NULL` on any `match_*` column is a wildcard ("matches anything"), not "matches only a `NULL` value".** Stated explicitly because the schema gives no other signal — `matchOperator OperatorCode?` reads exactly as ambiguously as "match nothing with an operator set" would, and getting this backwards would make every route in a fresh deployment silently match zero traffic.

**`Route.matchPrefix` reuses `sms_msisdn::Msisdn::national()`, not a hand-rolled E.164 substring check** — the same national-digit convention `OperatorPrefixRule.prefix` and `sms_msisdn::OperatorPrefixTable` already use, so a route authored against `"677"` means the same thing an `OperatorPrefixRule` row authored against `"677"` does.

**No `Route` rows configured at all now refuses to dispatch, loudly — a real behaviour change from the M2 placeholder, weighed deliberately.** `cheapest_active_provider` always had exactly one thing to pick from (any active `Provider`); once routing is a real rule set, a silent "no routes configured yet, fall back to picking anything" path would mean routing quietly stops being explainable the moment *any* `Route` row exists but doesn't match — precisely the failure mode #62 exists to close. So an `accepted` message with zero eligible routes goes to `rejected`, `stateReason` carrying `routing::explain_no_route`'s own per-route summary. The cost of that choice is real, not hypothetical: `just demo` seeded no `Route` row before this PR, so `crates/sms-api/examples/send_test_message.rs` (what the demo's own fixture step runs) now also seeds a catch-all `Route` alongside its `Provider`, idempotently, the same self-healing discipline its neighbouring `ensure_provider` already uses.

## Milestone 5: failover and the provider circuit breaker landed (#63)

`crates/sms-worker/src/dispatch.rs` closes the gap #62's own status paragraph named explicitly: "failover and circuit breakers (`failoverRouteId`, #63)". The mapping is driven entirely by `sms_provider::ProviderError::routing()` (`crates/sms-provider/src/error.rs`) — a compiler-checked table, not a second hand-derived one — so this PR adds no new classification logic of its own, only the reaction to an existing one:

| `RoutingConsequence` | error | what `handle_submit_error` does |
|---|---|---|
| `RetryThisProvider { after }` | `Transient` | same-provider backoff, `routed -> queued`; no failover |
| `TryNextRoute` | `Permanent` | `attempt_failover`; exhausted -> `routed -> failed`, "no alternate route available" |
| `OpenCircuitAndTryNextRoute` | `Unavailable` | `record_provider_failure`, then `attempt_failover`; exhausted -> same-provider backoff (the old M2 single-provider degradation, still correct once no alternate exists) |
| `FailMessage` | `Rejected`/`Unsupported` | `routed -> failed`; no failover — retrying anywhere fails identically |
| `HoldIndeterminate` | `Indeterminate` | `routed -> uncertain`; unchanged from #119 — never even considered for failover |

**"Failover must not double-send: the claim loop's lease is what prevents it"** (the issue's own words) is the property `attempt_failover` is built around, and it is why this PR needed no new claim-loop mechanism at all. A failover reroute never calls `SmsProvider::submit` a second time inline — it writes `routed -> queued` with a *new* `providerId`/`routeId` stamped on the same `if_match(version)`-CAS'd row (`dispatch::write_failover`, mirroring `claim::apply_routing_decision`'s own `accepted` winner branch: `leaseUntil` set to `now`, immediately claimable, not a real lease) and returns. The actual resubmit happens on a later claim, through the ordinary `queued -> routed -> submit` path every other reclaim in this crate already relies on. This is only safe because `TryNextRoute`/`OpenCircuitAndTryNextRoute` (`Permanent`/`Unavailable`) both mean *nothing was ever accepted by the provider* — `Indeterminate`, the one variant that can't make that claim, never reaches `attempt_failover` at all, proven live (not just by the existing `ProviderError::routing()` unit test) by `dispatch_live_postgres.rs`'s pre-existing `an_indeterminate_submit_lands_in_uncertain_and_is_never_resubmitted`, unchanged by this PR and still passing.

**`Route.failoverRouteId` is not read by the failover mechanism.** Per #62's own module doc on `sms_routing::select_route`'s `exclude` parameter — "call `select_route` again with the failed route's id added to `exclude`" — that is exactly what `attempt_failover` does, over the *whole* route set, not a hand-rolled walk of one field naming a single specific next hop. `failoverRouteId` stays exactly what #62 already said it was: carried through `Winner` for an operator's own explanation trail, never consulted by the pure engine or by this PR's own caller.

**`Message.excludedRouteIds` (a new nullable column, `schema.cstack`) is each message's own accumulated exclude set, sentinel-packed via `sms_core::pack`/`unpack`** — necessary, not just convenient. A `Permanent` failure never opens a provider's circuit breaker (`crates/sms-provider/src/error.rs`'s own `permanent_never_opens_the_circuit_breaker` test) because it is specific to this one message (an unapproved sender ID, say), not a provider-wide outage — so nothing else marks that route ineligible for a second attempt by this same message. Without remembering it per-message, a second failover hop could pick the exact same already-failing route right back and fail identically forever. Capped at two entries (§6.3: "Failover capped at two hops — beyond that you're not routing, you're spraying") — `attempt_failover` checks the set's length *after* adding the currently-failing route and refuses to even query `select_route` once it would exceed two, the same "the caller isn't willing to act on the answer anyway" reasoning `sms_routing`'s own doc uses elsewhere.

**The provider circuit breaker (`Provider.consecutiveFailures`/`circuitOpenUntil`, two new columns) deliberately mirrors `WebhookEndpoint`'s own shape (#40/#41/#59) rather than inventing different semantics for a second breaker in this codebase** — same two fields, same reset-on-success-and-on-trip discipline (`dispatch::record_provider_failure`/`reset_provider_failures`, matching `hooks::record_endpoint_failure`/`reset_endpoint_failures` almost line for line), same best-effort `if_match`-CAS'd writes (a lost race under concurrent `dispatch` workers undercounts by a small amount — accepted, matching the identical reasoning `hooks.rs` already documents, since this is a heuristic to stop hammering a dead provider, not something anyone bills against). The constants differ because the spec differs: §6.3 says five consecutive failures and 60s for providers, not webhook delivery's 20-failure/15-minute numbers — same shape, different subsystem.

`crates/sms-worker/src/routing.rs::convert_provider` is the one reader, and it is the literal mechanism behind the ticket's own second acceptance clause ("must not fail a message a healthy alternative could carry"): an open circuit is treated exactly like `state != active` (`available = false`, with a reason) in the same `HashMap<String, ProviderRow>` every routing decision already builds, so *every future* `accepted` message — not just the one whose failure tripped the breaker — naturally skips that provider. Proven live, at the strongest level this admits: `dispatch_live_postgres.rs`'s `an_open_circuit_routes_new_messages_to_the_alternative_instead_of_rejecting` asserts the broken provider's own submit-call counter stays flat while a sixth, brand-new message reaches `submitted` entirely through the healthy alternative — not merely that it *eventually* succeeds after being tried against the broken one first.

**Deliberately not the literal "half-open with a single probe" §6.3's own prose describes.** Both breakers in this codebase (`WebhookEndpoint`'s and now `Provider`'s) fully reopen the moment `circuitOpenUntil` passes, with no rate-limited single-probe admission — a true single-probe half-open state needs a coordination mechanism (exactly one in-flight probe across however many `dispatch` processes exist) neither breaker has, and building one just for `Provider` would be a second, differently-shaped breaker for one property, which this section's own precedent (follow `hooks.rs`'s shape rather than inventing a better one) argues against. Revisit if a real incident shows the simpler reopen is too aggressive.

**Found live, not by review, and it is why the first attempt at the circuit-breaker test failed with the breaker never actually opening: `Provider`'s own `update` `@@allow` didn't admit `hasRole('system')`.** `dispatch.rs`'s new circuit-breaker writes run under this crate's internal `sys()` context, and without that clause every one of `record_provider_failure`/`reset_provider_failures`'s writes returned `Forbidden("update policy denied this operation")` — silently absorbed by the exact same best-effort "log and drop" handling `hooks::record_endpoint_failure` already established for a lost CAS race, so nothing anywhere *looked* broken except the one live assertion that actually checked the effect (`circuitOpenUntil` genuinely set on the `Provider` row) rather than merely that the surrounding calls didn't panic. This is a different shape from this file's own nine-times-repeated `list`/`detail` gap (that one fails silently to an empty array; this one fails loudly with `Forbidden`, just absorbed by a call site that was already designed to treat any write failure as best-effort) — worth naming as its own instance rather than folding into that count. Fixed the same way every prior instance was: `schema.cstack` only, confirmed byte-identical DDL via `cratestack migrate diff` before and after the policy-only change. Safe to grant: `GatewayAuth::authenticate` (`crates/sms-api/src/auth.rs`) constructs `role: "system"` exactly once, inside `Procedures::sys()`, never from a real bearer token (see that module's own "Never `system`" comment), so this adds no new HTTP-reachable capability to `PATCH /providers/{id}` (`router::PROVIDER_WRITE_ROUTES`) — `policy_golden_list_live_postgres.rs`'s own `provider_update_policy_matches_the_schema_exactly` now asserts the system-context case succeeds instead of asserting it was forbidden, with an inline note explaining why the reversal is safe.

**Guard-failure proofs, house standard.** (a) The pre-existing, single-provider `an_indeterminate_submit_lands_in_uncertain_and_is_never_resubmitted` turned out unable to prove "never fails over" on its own — its fixture has only one route, so a broken implementation that fails `Indeterminate` over anyway finds nothing eligible to reroute to and lands in the identical `uncertain` outcome by accident, passing for the wrong reason. Caught by actually running the break, not assumed: temporarily adding `RoutingConsequence::HoldIndeterminate` to `handle_submit_error`'s `should_attempt_failover` match left that test green. Fixed by adding a second test with a real healthy alternative, `an_indeterminate_submit_never_fails_over_even_with_a_healthy_alternative_available` (the two-provider fixture, `AlwaysErr`/`AlwaysOk`) — the same break against this test failed with `left: queued / right: uncertain` at the post-submit assertion (the message had rerouted to B and reached `queued` instead of staying `uncertain`), reverted, and reconfirmed all 11 of this file's tests green. (b) An open circuit routing to the alternative rather than rejecting: temporarily dropping the `!circuit_open` clause from `routing.rs::convert_provider`'s `available` computation reproduced `an_open_circuit_routes_new_messages_to_the_alternative_instead_of_rejecting` failing with `left: Some("<provider-a-id>") / right: Some("<provider-b-id>")` — the sixth, brand-new message's `providerId` came back pointed at the broken provider instead of the healthy one — reverted, reconfirmed green.

**Two active `Provider`s and two `Route`s, not one, is a new live-fixture shape this PR introduces (`dispatch_live_postgres.rs::seed_two_routed_providers`)** — every earlier live suite touching `claim.rs`'s `accepted` branch (`claim_live_postgres.rs`, the rest of `dispatch_live_postgres.rs`, `chaos_live_postgres.rs`, `kill9_reclaim_live.rs`) seeds exactly one of each, per #62's own "test-fixture blast radius" paragraph above. The three new tests (a `Permanent` failover, an open-circuit reroute, and the `Indeterminate`-never-fails-over guard above) also needed two small hand-rolled fake `SmsProvider` implementations (`AlwaysErr`/`AlwaysOk`, call-counted via `AtomicUsize`) rather than reusing `wiremock`-backed `OrangeCmProvider`: that adapter structurally never produces `ProviderError::Permanent` — every 4xx it sees other than 429 becomes `Rejected` (`sms-provider-orange-cm`'s own `classify_submit_error` doc) — so the `TryNextRoute` arm can't be exercised through the real adapter at all, and an exact submit-call count (not just a final `Message` state) is what actually proves "never resubmitted"/"never even attempted," the same discipline `an_indeterminate_submit_lands_in_uncertain_and_is_never_resubmitted`'s own `wiremock` `.expect(1)` already established.

## Milestone 5: grey-route detection landed (#64)

§6.4's own two-sentence spec — "monthly handset validation per route, plus an alert on delivery-rate divergence between routes that should behave identically" — splits cleanly into a buildable half and one that fundamentally cannot be automated, and the split is the whole design decision here, restated because it is easy to blur: a grey route rewrites the sender ID on the wire, after this system has already handed the message to a provider, and `DeliveryReceipt` still reports `delivered` regardless. No server-side signal can see the substitution. `OPEN_QUESTIONS.md` §2.4 already recorded this before any code landed; this PR narrows, but does not close, that gap — see that entry's own updated text for exactly what changed.

**The divergence half is fully buildable, and "should behave identically" is taken verbatim from the issue's own text: two routes to the *same operator*, for the *same message class*.** `crates/sms-worker/src/jobs/grey_route_watch.rs` groups terminal `Message` outcomes by `(Message.operator, Message.class)` — not `Route.matchOperator`/`matchClass`, which describe what a route is willing to carry, not what it actually carried for a given message; `Message.operator`/`class` are stamped once at classification time and (for `routeId`) reflect the final route after any #63 failover reroute. `uncertain` (#119's own "the outcome was genuinely never learned") is excluded from both sides of the ratio, not folded into either — counting it as failure would flag every route behind a slow-to-respond provider purely from timeout volume.

**Sample size matters more than the delta — three independent, deliberately redundant gates, all documented inline in `grey_route_watch.rs`'s own module doc:** `MIN_SAMPLE` (30 terminal messages per side, a visible floor an operator can point to, not an emergent property of a formula), a two-proportion z-test (`Z_THRESHOLD = 3.0`, ~p<0.0027 two-tailed — the standard-error term is what naturally makes a 50%-vs-100%-over-4-messages delta score low and a 70%-vs-98%-over-1000-messages delta score high), and `MIN_DELTA` (15 points, a practical-significance floor stopping a statistically-real-but-operationally-meaningless gap like 98.0% vs 98.3% at huge volume from paging anyone). All three must hold; any one failing means no finding. `sms_route_delivery_divergence_flagged` (a sixth/seventh metric alongside #70/#71's original five, `crates/sms-metrics`) and `deploy/prometheus/alerts.yml`'s `SMSRouteDeliveryDivergence` follow the exact shape those five already established.

**No `GROUP BY` in the delegate API, confirmed by reading `cratestack-sqlx`'s own `Aggregate` builder directly (`count`/`sum`/`avg`/`min`/`max`, none grouped)** — matching §9.1's own note on `dashboardSummary`'s ~26 individual `COUNT` queries for the identical reason. Grouping happens client-side over rows fetched through the ordinary `Message` delegate (still R1-compliant), bounded by `FETCH_LIMIT` (20,000) the same way `reap_outbox`'s own `DELETE_BATCH`/`ALERT_BATCH` bound their per-run work — a deployment with more terminal traffic than that in one 7-day `LOOKBACK` window gets the check computed over its most recent 20,000 messages, not an unbounded scan, and self-corrects on the next daily run regardless.

**The handset-validation half cannot be automated, and this PR does not pretend otherwise.** `RouteValidation` (`schema.cstack`, a new model — 23 models total now, up from 22 — §2.10 regenerated wholesale, id/`performed_at` defaults and one lookup index hand-added the same way `AuditAnchor`'s were) is an append-only evidence record: no `update` `@@allow` at all, matching `DeliveryReceipt`/`ConsentRecord`'s own precedent — correcting a mistaken entry means recording a new one, not editing history. `docs/runbooks/grey-route-validation.md` is the human procedure, the same shape `docs/runbooks/36-handset-gate.md` already set for "this needs a real phone, not a test suite." `sms-gateway record-route-validation` (a new CLI subcommand, `app/sms-gateway/src/main.rs`, mirroring `provision-user`'s own "operator action, not generated CRUD" precedent) is what the runbook actually runs — writes through the plain delegate under a stand-in `operator`-role context, since `RouteValidation.create`'s own `@@allow` already admits `hasRole('owner') || hasRole('admin') || hasRole('operator')` and needs no dedicated `Procedures` method. `grey_route_watch`'s other half, `check_overdue_validations`, reads every `enabled` `Route`'s most recent `RouteValidation` under `sys` and flags anything with none in the last 30 days (`sms_route_validation_overdue`, `SMSRouteValidationOverdue`) — a staleness signal only, explicit in both the job's own module doc and the runbook's closing section: a route validated yesterday and turned grey today reports exactly as "fine" as one that never had a problem.

**`grey_route_watch` is a new job kind, not one of §7.5's original nine** — named and scheduled (daily, alongside `purge_retention`/`anchor_audit`) the same way every prior job is, registered in `crate::jobs::default_registry()`, but §7.5's own table is left untouched rather than retrofitted, since it documents the original design doc's own job list and this ticket's alert condition was never part of it.

**The fifteenth instance of this file's own repeated `hasRole('system')` gap — flagged in advance, per this PR's own precedent from `Route`/`User`/`Role`/`ConsentRecord`, not found live.** `RouteValidation.read`'s `@@allow` admitted `hasRole('system')` from the moment the model was written, since `check_overdue_validations` needs it from day one; `crates/sms-api/tests/system_context_golden_list_live_postgres.rs` classifies it into `SYSTEM_READABLE_MODELS` in the same PR. Verified to actually guard something: with `hasRole('system')` temporarily removed from `RouteValidation`'s `read` clause, the live half of that test failed with `a system context could not read back the RouteValidation row it (or an owner, on its behalf) just seeded. RouteValidation's current schema.cstack read/list/detail policy is: @@allow("read", auth().kind == "user" || hasRole('system'))`; restoring the clause restored a pass.

**A real, upstream-documented trap hit while writing the schema, not a new one:** `RouteValidation.notes String? @length(max: 1000)` reproduced cratestack#537 verbatim — `@length` on a nullable `String?` breaks the generated `Update{Model}Input::validate()` at compile time (`E0308`, `&str` expected where `&Option<String>` is passed). `AuditAnchor.prevChainHash` worked around this with a non-null sentinel; a sentinel doesn't fit free-text notes, so `notes` simply carries no `@length` bound at all, matching `SenderId.notes`/`ConsentRecord.evidenceRef`'s own precedent for a nullable free-text field. `expectedSenderId`/`observedSenderId` are non-nullable and keep their `@length`, unaffected — only a nullable field triggers the bug.

**Guard-failure proof, the ticket's own named priority: a large, genuinely divergent sample is flagged; a tiny sample with a worse ratio is not — and the two gates that make that true were each shown to be load-bearing independently, not merely redundant with each other.** At `n=4` vs `n=4` (the issue's own named noise case, "4 messages and 50% delivery"), the z-test alone already refuses to flag regardless of `MIN_SAMPLE` — the largest possible z-score at that sample size (~2.83) never clears `Z_THRESHOLD` (3.0). That made `MIN_SAMPLE`'s own contribution provably real only at a size where the z-test *would* pass on its own: a second test at `n=20` vs `n=20` (100% vs 50%, z≈3.65 — past `Z_THRESHOLD`) with `MIN_SAMPLE`'s own filter temporarily bypassed reproduced a genuine `DivergenceFinding` that must never surface:

```
below MIN_SAMPLE must never be flagged even when the z-test alone would allow it: [DivergenceFinding { operator: orange, class: otp, reference_route_id: "route-a", reference_rate: 1.0, reference_n: 20, route_id: "route-b", rate: 0.5, n: 20, delta: 0.5, z_score: 3.651483716701107 }]
```

Restoring the real filter restored a pass. A second break proved `uncertain`-exclusion the identical way: temporarily folding `MessageState::uncertain` into the failure-count arm of `aggregate_outcomes` reproduced `assertion left == right failed: uncertain must not count as failed / left: 30 / right: 0` against a fixture of 30 delivered + 30 uncertain messages; restoring the real match arm restored a pass. All 15 of this file's own unit tests, plus five live-Postgres tests (`crates/sms-worker/tests/grey_route_watch_live_postgres.rs`) proving the same DB-backed wiring — a genuinely divergent pair flagged through the real `Message` delegate, `RouteValidation`'s own system-context read, `run_at`'s two gauges always set, and the `JobHandler` entry point itself — pass stably.

## Milestone 5's own gate: the automated half of "kill Orange in staging" (#65) — landed 2026-08-13

§12's own M5 gate — "Kill Orange in staging; MTN unaffected, Orange fails over cleanly" — has an automatable half and a half that genuinely needs a real staging deployment, the same split M2's own `#36` gate already established as this repo's model. `crates/sms-worker/tests/kill_orange_gate_live_postgres.rs` is the automatable half; `docs/runbooks/65-kill-orange-gate.md` is the rest, and does **not** claim the gate has passed — it hasn't; nobody has run it against a real staging deployment with real Orange/aggregator credentials yet.

**The whole point of this suite, versus every earlier #63 test: a real transport-level failure, through the real adapters, not a synthetic `ProviderError`.** `dispatch_live_postgres.rs`'s own `a_permanent_failure_fails_over_...`/`an_open_circuit_routes_...` tests (above) use hand-rolled `AlwaysErr`/`AlwaysOk` `SmsProvider` impls that return a chosen `ProviderError` directly — real coverage of the state-machine reaction, never of the transport failure itself. This suite instead talks to Orange through the real `sms_provider_orange_cm::OrangeCmProvider` and to MTN through the real `sms_provider_mtn::MtnAggregatorProvider` (#61), and "kills" Orange by **dropping a real, running `sms_fake_orange::FakeOrange` HTTP server** — the very next submit gets a genuine OS-level `ECONNREFUSED` through `reqwest`, exercising `classify_transport_error`'s real connect-vs-read distinction rather than asserting it separately in isolation (as `sms-provider-orange-cm`'s own `a_connect_refusal_is_still_unavailable` already does).

**Reviving Orange on the exact same port needed `SO_REUSEADDR`, and this was verified empirically before writing any test code, not assumed from platform docs.** `OrangeCmProvider::base_url` is fixed at construction, exactly like every other adapter in this workspace — so "Orange comes back" has to mean a *new* listener on the *same* address the already-constructed adapter still points at, not a second adapter instance. A throwaway Rust program (kept out of this repo) reproduced the actual failure mode first: bind an ephemeral port, complete one real HTTP round trip through it (so the client side leaves a `TIME_WAIT` entry), drop the listener, then a plain `std::net::TcpListener::bind` on that same port fails `EADDRINUSE` — even though *nothing* is currently listening there — because `TIME_WAIT` blocks a fresh *listening* bind on that port regardless of remote endpoint, on both macOS and (per general POSIX socket behaviour) Linux. A socket built via `socket2` with `SO_REUSEADDR` set before `bind()` rebinds immediately. `crates/sms-worker/tests/kill_orange_gate_live_postgres.rs::reuseaddr_listener` is the resulting helper — a new `socket2` dev-dependency (already resolved transitively at 0.6.5 via `tokio`, so this names it directly rather than adding a second version to the tree). `wiremock`'s own `run_server` (`hyper.rs`) already calls `listener.set_nonblocking(true)` itself before wrapping the std listener, so the helper doesn't need to.

**"Nothing double-sends" is checked against the providers' own request logs — `FakeOrange::ledger()` for Orange, `MockServer::received_requests()` for MTN — never against this system's `Message` rows,** matching the issue's own explicit instruction: the database records what this system *believes* it did; a provider's own ledger records what it actually received. Since Orange is genuinely unreachable throughout the outage (nothing ever listens on that port), its own ledger staying at exactly the pre-kill baseline count (not growing at all) is a stronger proof than counting `Message.attempts` could ever be — it proves no connection ever *reached* Orange's request handler during the outage, not merely that this system's own bookkeeping says so.

**One scenario, not four separate tests — the four clauses are properties of one realistic timeline (healthy → killed → revived), not four independent mechanisms.** `orange_outage_fails_over_mtn_stays_up_nothing_double_sends_and_the_breaker_reopens` walks phase by phase (baseline, outage, recovery), each phase's own helper function (`run_baseline_phase`/`run_outage_phase`/`run_recovery_phase`, split out for `clippy::too_many_lines`, the same reason `dispatch_live_postgres.rs`'s own `seed_one_active_provider` is pulled to module scope) asserting the clauses reachable from that phase. Fixture: an operator-scoped Orange route at priority 1000, a wildcard (no `matchOperator`) MTN route at priority 500 — the wildcard is what makes Orange-destined failover to MTN possible at all, and also what makes MTN-destined traffic never even consider Orange, the strongest available form of "unaffected" a fixture can express directly through the real routing engine rather than asserted separately.

**All four guard-failure proofs were run for real, against production code, output captured, then reverted — house standard, and for a gate it matters more than usual.** Each sabotage was a single, clearly-labelled `// TEMPORARY SABOTAGE ... DO NOT COMMIT` edit to the exact mechanism the clause depends on, applied to `crates/sms-worker/src/dispatch.rs` or `routing.rs`, verified to reproduce a real failure, then `git checkout --`'d before moving to the next:

- **Clause 1 (MTN unaffected)**: `resolve_provider`'s adapter lookup temporarily forced to always resolve whichever `Provider` row has `kind == orange_cm_http`, regardless of the message's own routed provider — simulating a regression where adapter resolution stops respecting the routing decision. Failed with `left: queued / right: submitted` on an MTN-destined message (it never reached `submitted` because it was silently resubmitted through the dead Orange adapter instead).
- **Clause 2 (Orange fails over cleanly)**: `handle_submit_error`'s `should_attempt_failover` temporarily forced to `false` — failover disabled outright. Failed with the identical `left: queued / right: submitted` shape, on an Orange-destined message this time (it just backed off the same, still-dead provider forever instead of rerouting).
- **Clause 3 (nothing double-sends)**: `write_submitted` temporarily left `state` untouched (`None`, this framework's own "field not present" convention) while also forcing `leaseUntil` into the past — simulating a successful submit that never marks itself terminal before its lease looks abandoned. This is the one guard-failure result worth reading carefully: it did **not** fail at the double-send-specific ledger assertions deep in the outage/recovery phases — it failed immediately, at the suite's own pre-outage baseline sanity check (`sanity: Orange must be genuinely healthy before this gate kills it`, `left: routed / right: submitted`), because a submit that never marks itself done is indistinguishable from a broken send at any point downstream. That is a *stronger* result than the alternative, not a weaker one — worth recording explicitly per this file's own "if a clause turns out to pass even with its mechanism broken, say so" standard: here it did not pass, it failed even earlier than intended, which means the property is foundational enough that it's caught before the code ever reaches the scenario purpose-built to check it.
- **Clause 4 (the breaker reopens)**: `routing.rs::convert_provider`'s `circuit_open` computation temporarily changed from `row.circuitOpenUntil.is_some_and(|until| until > now)` to `row.circuitOpenUntil.is_some()` — ignoring expiry entirely, so a circuit that ever opened never closes again regardless of how much time (real or forced) has passed. Failed with `left: Some("<mtn-provider-id>") / right: Some("<orange-provider-id>")` on a post-recovery message — it stayed routed through MTN instead of returning to Orange, even after the suite forced the cool-down into the past through a real delegate write (see below).

**Forcing the circuit's cool-down forward uses the same "force it for a faster test" technique this codebase already uses elsewhere** (the `#36` runbook's own `UPDATE messages SET lease_until = ...`, `chaos_live_postgres.rs`'s `force_lease_past`) — a real `UpdateProviderInput { circuitOpenUntil: Some(Some(past_time)), .. }.if_match(version)` delegate call (R1), not raw SQL, setting the value into the past rather than to `None` so the exact same `> now` comparison a real 60 seconds elapsing would exercise gets exercised here too.

**No new external dependency beyond `socket2`, already resolved transitively.** `cargo deny check`, `./ci/assert-no-raw-sqlx.sh`, and the full workspace `cargo check`/`cargo clippy --all-targets -- -D warnings` all stayed clean through this change — confirmed by running them, not assumed.

## Milestone 6 started: observability and alerting (#70, #71) — landed 2026-08-11

Two stories, one PR, deliberately — #70 names five alert conditions, and every one of them needs a metric #71 was the ticket to build; #70 without #71 would be alerting on nothing, #71 without #70 would be instrumentation nobody consumes.

**Backend: Prometheus text exposition (`crates/sms-metrics`, a new pure library crate below both `sms-api` and `sms-worker`), not OTLP.** No collector infrastructure exists anywhere in `deploy/`, and a pull-based `/metrics` needed nothing new to receive it. The `prometheus` crate, `=0.14`, `default-features = false` (drops the `protobuf` feature — the older binary scrape format nothing here speaks; `TextEncoder`/`Registry`/`*Vec` need none of it), Apache-2.0, checked against `deny.toml`'s allowed-license list and against `cargo deny check` directly (`advisories ok, bans ok, licenses ok, sources ok`, confirmed by running it, not assumed from the license string alone).

**Every metric's actual writer, and why:**

- `sms_sm001_total{entity,from_state,to_state}` — incremented inside `crates/sms-api/src/errors.rs::map_database_error`, the one place this workspace already translates a raw `SM001` into something a caller can act on. Labels are parsed out of the guard trigger's own `RAISE EXCEPTION` text (`illegal <entity> transition <from> -> <to> on <id>`) by `sms_metrics::record_sm001` — matching §9.1's own "SM001 rejection count by from/to pair" line, not a plain unlabelled counter.
- `sms_worker_singleton_lease_held{role}` — `crates/sms-worker/src/lib.rs::run_singleton`, the only writer: `1` the instant a lease is acquired, `0` the instant this process is standing by, released, or fails to attempt the lock.
- `sms_dispatch_in_flight_submits{provider}` — `crates/sms-worker/src/dispatch.rs::submit_one`, incremented immediately before `SmsProvider::submit` and decremented immediately after.
- `sms_webhook_outbox_oldest_undelivered_age_seconds` — `crates/sms-worker/src/drain.rs::tick`, reusing the exact `oldest_undelivered_age` that module's own doc already said exists "so alerting could reach it."
- `sms_event_outbox_poison_rows` — `crates/sms-worker/src/jobs/reap_outbox.rs::ReapOutbox::run_at`, reusing `alert_poison_rows`'s own returned count, the same reuse principle.

**The absent-vs-zero problem (#70's own "subtlest requirement") is solved structurally, not with extra bookkeeping.** `run_singleton` only ever calls a role's real body (`run(role, ...)`) from inside the branch that already holds the lease — so `drain::tick` and `dispatch::submit_one` are *only ever reachable* on the process currently in charge. A standby process never touches those two gauges at all, so they are genuinely *absent* from its own `/metrics`, not present-and-zero; only `sms_worker_singleton_lease_held` itself is deliberately written on every outcome (including standing-by, as `0`), because that's the one gauge #70 needs a process to keep reporting even while it isn't in charge. `deploy/prometheus/alerts.yml`'s singleton-unheld rules check both `sum(...) == 0` **and** `absent(...)`, because only one of the two is true depending on whether the role is merely unheld or nobody is even configured to attempt it.

**Two real, latent bugs found wiring the SM001 counter through `sms-worker`'s write sites, not invented.** `crates/sms-worker/src/jobs.rs::swallow_stale_write` and `crates/sms-worker/src/jobs/expire_stale.rs::expire_matching` both had a `CoolError::Conflict(reason)` match arm whose own comment claimed it meant "the message moved on before this write landed" — but nothing on either write path ever produced `Conflict` without going through `map_database_error` first, and neither call site did. That made the arm dead code, and — the actual bug — naively fixing SM001 counting by mapping every error *before* the match (the first attempt) would have made a **genuine** SM001 fall into that same arm and be silently swallowed as a harmless race, exactly the failure mode #70 exists to make loud. `crates/sms-api/src/dlr.rs::ingest_one` had the identical shape, found first, live: its own `Err(CoolError::Conflict(reason))` arm was equally unreachable before this PR. Fixed the same way in all three: check `sms_api::is_illegal_transition` against the *raw*, unmapped error first (it reads `error.db_sqlstate()` directly, no mapping needed), and only *then* call `map_database_error` (which also records the metric) on the confirmed-illegal case, propagating it loudly rather than swallowing it. A genuine version-race (`PreconditionFailed`) is still swallowed as before.

**`/metrics` is a second, standalone listener on both binaries — never merged into `sms-gateway`'s public router.** `deploy/Caddyfile`'s `reverse_proxy sms-gateway:8080` is a blanket, no-path-allowlist proxy (confirmed by reading the file, not assumed) — anything mounted on that router is public the moment it exists. `sms_api::metrics::router()` binds to its own address instead (`--metrics-listen`, default `127.0.0.1:9090` on the gateway, `127.0.0.1:9091` on the worker — loopback by default, `0.0.0.0` only inside the container via each `Dockerfile`'s own `ENV` override, same pattern `SMS_LISTEN_ADDR` already used), never published to the host and never a path Caddy's config names. `app/sms-worker` had **no HTTP surface at all before this PR** ("six poll-loop roles, never a listener" — `main.rs`'s own module doc, now corrected) — it gained `axum` as a real dependency (not dev-only) specifically for this, reusing `sms_api::metrics::router()` directly rather than a second near-identical implementation.

**Correlation is `Message.id` across processes, `cratestack_request_id` within one.** `cratestack-macros` already logs `cratestack_request_id = ctx.request_id().unwrap_or("")` on every generated CRUD/procedure route — found live, by reading the vendored macro source, that nothing in this deployment had ever called `CoolContext::with_request_id`, so that field had been empty on every log line since the router first existed. `crates/sms-api/src/auth.rs::GatewayAuth::authenticate` now honours an inbound `X-Request-Id` verbatim or mints a fresh one — the one place a `CoolContext` is constructed per HTTP request. That ties together every `cratestack_*` log line for one request, within `sms-gateway` — it does **not** cross into `sms-worker` or back through a DLR, which are separate processes (or, for the DLR case, an unauthenticated route with no bearer token and therefore no per-request `CoolContext` at all — `dlr.rs`'s own module doc). `Message.id` is the join key across that boundary instead: `procedures.rs::send`, `dispatch.rs::submit_one`, and `dlr.rs::ingest_one` each log a `message_id`-carrying event at `info`. `docs/runbooks/alerting.md`'s "Correlating a message end to end" section is explicit that this is grep-able log correlation, not OpenTelemetry-shaped distributed tracing — no span tree, no exporter, three log lines sharing one field.

**"Alerting" stops at the rules evaluating — no Alertmanager, no receiver, nothing in this tree can page anyone.** `deploy/prometheus/alerts.yml` holds the five rules; a real `prometheus` service in `deploy/docker-compose.yml` (stood up unconditionally, not behind a compose profile — this repo's own delivery convention is to build a thing and make it live) evaluates them against `sms-gateway:9090`/`sms-worker:9091` and shows firing state on its own `/alerts` page. Wiring a receiver on top is left to whoever operates a real deployment. §9.1 of the design doc is corrected to match what actually shipped (five real metrics/alerts; everything else in the original prose — submit rate/latency, delivery rate by provider×operator, time-to-delivery percentiles, provider balance, DLR silence, webhook dead-letter rate — is still aspirational) rather than left silently stale, and the design doc's own 60s outbox-staleness figure is flagged as not matching `drain.rs`'s real, already-implemented 2-minute `STALLED_THRESHOLD` — the alert rule matches the code that actually runs.

**The Helm chart (`deploy/charts/vsms/values.yaml`) does not get a `/metrics` Service or ServiceMonitor in this PR** — a deliberate, named scope cut, not an oversight: Docker Compose is the deployment path this repo's own §9.2 documents as real ("Kubernetes only when you have a reason that isn't résumé-driven"), and a ServiceMonitor assumes a Prometheus Operator install this chart doesn't otherwise depend on. The chart's own stale "sms-worker has no HTTP surface" comments are corrected regardless, since this PR's own code changes made them false.

**One metric proven to fail its own guard, live, not just reasoned about.** `crates/sms-api/src/errors.rs::sm001_increments_the_labelled_prometheus_counter` was deliberately broken (the `sms_metrics::record_sm001` call commented out of `map_database_error`) and confirmed to fail with `assertion left == right failed: map_database_error must record exactly one SM001 observation / left: 0 / right: 1` before being restored. `crates/sms-worker/tests/live_postgres.rs::run_singleton_reports_held_then_released_on_the_lease_gauge` drives the real `run_singleton` (not `RoleLease` directly) against a live Postgres and asserts the gauge reads `1` while held and `0` again after a graceful shutdown releases it — proof the absent-vs-zero design in `crates/sms-metrics`'s own module doc is real, not just documented.

## Milestone 6 started: retention purge (#67) — decision #5 resolved

**Decision #5 (10-year traffic retention vs 90-day minimisation) was resolved by the maintainer on 2026-08-11: 90-day minimisation, no split ledger.** §10's own split-ledger proposal — a second, parallel ten-year traffic-metadata table alongside a 90-day content/MSISDN purge — was a real, considered option, not a strawman, and is now a documented alternative that was considered and not taken, not the plan of record. vsms purges *content and plaintext MSISDN both* at 90 days and carries no second, longer-horizon ledger anywhere in `schema.cstack`. Long-horizon retention, if it is ever required, is an infrastructure concern for whoever operates the deployment (backup/archival retention configured outside this application), and nothing in this repository fails if nobody configures that — see issue #5's own resolution comment for the tradeoff stated in those terms, and `docs/architecture.md` §10 (updated in the same PR). This unblocked #67, and shrank its scope: implement the 90-day purge, not the split ledger the issue's own text originally described.

`#67` landed as `crates/sms-worker/src/jobs/purge_retention.rs`, the `purge_retention` job — one of the eight §7.5 job kinds `#35`'s own status paragraph named but didn't build, now down to six. Registered in `jobs::default_registry()`, scheduled daily (§7.5's own cadence) in `scheduler::schedule()`, alongside `expire_stale` and `reap_outbox`.

**What gets purged, and the reasoning per column — read the job's own module doc for the full version, this is the summary:**

- **Purged**: `msisdn` (overwritten with a fixed placeholder, not nulled — see below), `body`, `clientRef`, `idempotencyKey` (a verbatim copy of `clientRef` at creation, per `procedures.rs` — purging one and not the other would purge nothing), `stateReason` (free text straight from a provider's API response, via `dispatch.rs`'s `classify()`, not a closed vsms-authored set).
- **Survives, deliberately**: `msisdnHash` (required by the decision's own text — "is what any post-purge correlation runs on"), `bodyHash` (also `NOT NULL`; write-only per `#134`'s own audit, left as a known, considered gap rather than solved here), `senderIdValue` (identifies the sending brand, not the recipient; §2.5's own "linkage" argument needed the plaintext `msisdn` to be meaningful, and that's gone).
- Only **terminal** `Message` rows (`delivered`/`failed`/`expired`/`rejected`/`cancelled` — §7.4's own terminal set) past 90 days are touched. A non-terminal row past 90 days would mean something else is already broken (§7.4's expiry machinery guarantees termination well inside 90 days), so this job trusts that guarantee rather than forcing a still-live row over it.
- `DeliveryReceipt` gets deleted, not redacted — the model carries no correlation-key column worth preserving, and this PR is the first thing that has ever removed one (§2.5 used to call receipts "append-only"; that line is now qualified). Eligibility is the receipt's own `receivedAt`, independent of its parent message's age.

**`Message.msisdn` stays `NOT NULL` — it is overwritten with a fixed 13-character placeholder (`"purged-msisdn"`), not nulled, and this was a deliberate rejection of the more "obvious" fix.** Making the column nullable was considered and rejected: the only two production readers of `Message.msisdn` (`dispatch.rs`'s submit path, `webhooks.rs`'s `Message.created`/`updated` subscriber) structurally can never see a message old enough to be purged — dispatch only touches `accepted`/`queued`/`routed`/`undelivered` rows, and the subscriber fires synchronously inside the mutation that created the row. Making the type `Option<String>` would have forced `.expect()`-shaped defensive handling into two heavily-tested, already-correct hot paths for a branch that can never actually be hit, for no privacy benefit the placeholder doesn't already give (`UpdateMessageInput::validate()` still runs `@length(min: 12, max: 15)` against the placeholder on every write — update-input validators treat every field as present-or-absent, not nullable-or-not, so the placeholder has to satisfy the same length bound a real MSISDN would).

**A `purgedAt DateTime?` column was added to `Message` — a real DDL change, done wholesale per this file's own regeneration workflow, verified against a real Postgres before being trusted.** Without a dedicated marker, "purged" and "never had a body" are indistinguishable, and relying on `body IS NULL` as an implicit signal is exactly the kind of silent contract this codebase keeps getting bitten by — nothing else in this codebase nulls `body` today (the #183 redact-at-terminal-state idea was built and rejected, see §2.5), but that could change. `purgedAt` is also the job's own idempotency guard (`purgedAt IS NULL` is part of the candidate filter). `cratestack --version` matched the pin (`0.7.10` = `0.7.10`) at the time, so the regeneration was trusted without the CLI-skew workaround this file's own "Regenerating migrations" section warns about — confirmed, not assumed. `cratestack migrate diff`'s output diffed to exactly one line against the committed `0001_init` (`purged_at TIMESTAMPTZ,`), and `0002_bootstrap` gained two hand-written indexes (`messages_purge_idx`, a partial index on `(created_at) WHERE purged_at IS NULL AND state IN (...)`; `receipts_received_at_idx` on `delivery_receipts (received_at)`) added to §2.10 of the doc first, then regenerated — never hand-edited into the migration file directly. Both migrations were applied to a real, disposable Postgres and `ci/test-state-machine.sql` passed before either was trusted.

**`DeliveryReceipt` gained its first-ever `delete` capability — the tenth instance of this file's own repeated `hasRole('system')`-shaped gap, but on the `delete` action rather than `list`/`detail`, and an absent clause rather than a broken one.** The model had no `@@allow("delete", ...)` at all before this PR; deny-by-default made that indistinguishable from "deliberately unsupported" until this job actually needed it. `schema.cstack` only, no DDL consequence — confirmed the same way every prior instance in this file was, a byte-identical `cratestack migrate diff` before and after the policy-only change.

**Seeding a genuinely old dataset — the acceptance criterion this issue names explicitly, and the part most likely to be faked.** `Message.createdAt` and `DeliveryReceipt.receivedAt` both carry `@default(dbgenerated())`, excluding them from their own create input (§2.0) — but they are not symmetric past that point. `Message.createdAt` genuinely can be backdated through a delegate: a `@default` excludes a field from `CreateXInput` but not `UpdateXInput` (this file's own framework-constraints table already says so), and — unlike `updatedAt` — no trigger touches `created_at` on write, confirmed by reading `touch_updated_at` itself rather than assumed from the mixin's name. So `crates/sms-worker/tests/purge_retention_live_postgres.rs` seeds a message, drives it to `cancelled` (a direct, legal `accepted -> cancelled` edge), and backdates `createdAt` to a real past `DateTime<Utc>` in the same CAS write — genuinely old data in the database, not a virtual clock. `DeliveryReceipt.receivedAt` has no such seam at all: the model has no `@@allow("update", ...)` clause whatsoever (append-only by design — `dlr.rs` only ever `.create()`s one), so its own tests fall back to the virtual-`cutoff` trick `reap_outbox_live_postgres.rs` already established for exactly this shape of column (framework-stamped, no delegate seam to backdate through) — shift the `cutoff` argument forward instead of the row's own timestamp.

Five boundary points proven against real data, not inferred: comfortably past, just past, exactly at (the `<=` cutoff comparison is inclusive — a message created *exactly* 90 days before the run is purged), just inside, comfortably inside. Verified to actually catch a regression, not just pass by construction: temporarily loosening `RETENTION` from 90 days to 1 hour reproduced a real failure (`just_inside: purgedAt.is_some() expected false ... left: true`) before being restored.

Explicitly out of scope, matching this milestone's own precedent for naming a scope cut rather than leaving it implicit: `Job` (`@@retain(days: 14)`) and `WebhookAttempt` (`@@retain(days: 30)`) also carry `@@retain` in `schema.cstack`, but §7.5's own `purge_retention` table row only ever specified "null `body`/`msisdn` past 90 days, delete receipts past 90" — `Job` and `WebhookAttempt` enforcement, if wanted, is a separate decision this PR doesn't make.

**Found in the coordinator's review of this PR, not by its own tests: a purge would have re-fired a customer's own webhook about a message reported on three months earlier.** The chain, real and confirmed against the tree, not hypothetical: `Message` carries `@@emit(created, updated)`; `purge_messages`'s own `.update()` is a real delegate write — R1 gives no other option; `app/sms-worker`'s `main` registers `crates/sms-api/src/webhooks.rs`'s subscribers unconditionally, regardless of `--roles`, per that module's own documented reason (an unregistered writer *loses* events, not merely stalls them); and `message_event_type` maps four of this job's five terminal candidate states (`delivered`/`failed`/`expired`/`cancelled` — every one but `rejected`) to a catalogued event. Un-guarded, every purge therefore attempted to enqueue — and `hooks` would then have signed and POSTed — a live webhook carrying `to: "purged-msisdn"` and an already-nulled `clientRef`. `webhook_attempts_dedupe` (`endpoint_id`, `aggregate_id`, `event_type`) happened to swallow the common case, where an attempt from the message's original delivery already exists to collide with — a coincidence of an unrelated unique index, not a guard, and it does not cover an endpoint registered *after* the original event.

Fixed at the subscriber, not the write site (there is no seam at the write site to suppress an emit from — R1 forbids going around the delegate): `enqueue_message_webhook_attempts` (`crates/sms-api/src/webhooks.rs`) now returns `Ok(())` immediately on `message.purgedAt.is_some()`, before it ever reads `msisdn` for the payload. Also corrected a wrong claim the first version of `purge_retention.rs`'s own module doc made while justifying `msisdn`'s `NOT NULL`-placeholder design: it asserted `webhooks.rs`'s subscriber "structurally can never see" a purged message, true of `dispatch.rs` and false of `webhooks.rs` — the doc now records why that reasoning was wrong, not just the corrected conclusion, matching this file's own convention of recording found mistakes rather than silently fixing them. `crates/sms-worker/tests/purge_retention_live_postgres.rs`'s `a_purge_never_re_fires_a_webhook_to_a_registered_endpoint` deliberately registers the `WebhookEndpoint` *after* driving the message to `delivered`, the one case dedupe cannot mask, and was confirmed to actually fail without the fix (`left: 1, right: 0` — a real `WebhookAttempt` row) before being trusted.

## Milestone 4: `@version`/ETag/If-Match threaded through operator-editable models (#59) — landed 2026-08-11

`#59`'s own example ("two operators editing the same route") didn't compile against the schema as written: only `Message`, `Job`, `WebhookAttempt` carried `@version` before this PR — the three models the *worker* claims via CAS, not the ones a human edits. `Route` (the ticket's own example) had no `@version` at all. Two honest options existed: thread ETag/If-Match only for the three already-versioned models (cheap, leaves the ticket's actual motivating scenario unsolved), or add `@version` to the models a human actually edits from the console (a real schema change, but the one that makes the ticket's own stated goal true).

**Took the second option, and went through every model's `@@allow("update", ...)` clause rather than trusting the ticket's own illustrative list.** Every model whose update policy admits at least one human role (`hasRole('owner'|'admin'|'operator'|'developer')`) gained `@version`: `App`, `AppClient`, `SenderId`, `SenderIdRegistration`, `Provider`, `Route`, `OperatorPrefixRule`, `WebhookEndpoint`, `User`, `Role` — ten models, not the seven or eight the ticket's own prose named (`User`/`Role` — RBAC/account administration — weren't mentioned there at all, but their update policies are exactly as human-gated as `Provider`'s, and a stale-role-reassignment race is the textbook version of this ticket's own worked example). Left alone, deliberately: the three already-versioned worker-claimed models (no human update policy to begin with), and every model whose update policy is `hasRole('system')`-only or absent entirely (`OauthClient`, `OauthSigningKey`, `Message`, `MessagePart`, `Job`, `WebhookAttempt`, `DeliveryReceipt`, `ClientAssertion`, `OptOut`) — nothing for a human to race there.

**Blast radius was smaller than it looked, and the search for it is worth recording.** `grep`ing for every `Update<Model>Input` construction across `crates/`/`app/` found real internal `.update()` call sites on exactly two of the ten: `Provider` (three sites: `crates/sms-api/examples/send_test_message.rs`, `app/sms-gateway/src/main.rs`'s `seed-provider` command) and `WebhookEndpoint` (`crates/sms-api/src/procedures.rs`'s `rotateWebhookSecret`/`replayWebhookAttempt`, `crates/sms-worker/src/hooks.rs`'s three endpoint-bookkeeping writes) and `SenderId` (one, inside `send_test_message.rs`'s own sender-activation helper). The other seven models — `App`, `Route`, `OperatorPrefixRule`, `SenderIdRegistration`, `User`, `Role` — have **zero** internal `.update()` call sites anywhere in this codebase, not even in a test fixture: every write to them today happens exclusively through the generated REST route, which needs no application-code change at all. Seventeen files in total needed a `.if_match(...)` added once live-test fixtures were counted too (every one of those two models' own `*_live_postgres.rs` seed helpers that activate a `Provider`/`SenderId` row after creating it).

**The framework fact this PR corrects, found live, not assumed: `if_match` is a runtime requirement, not a compile-time one.** This file's own "Verified toolchain API" comment (`// required on @version models`) reads as though a compile error results from omitting it — checked directly against `cratestack-sqlx-0.7.10/src/query/write/update.rs`: `if_match` is a plain `Option<i64>` builder field, defaulting to `None`; `run`/`run_in_tx` compiles fine without it and instead returns `Err(CoolError::PreconditionFailed("If-Match header required for versioned model"))` the first time the write actually executes. Proof this isn't hypothetical: `cargo check --workspace --all-targets` stayed fully green through the entire `@version` addition, on every one of the seventeen files that needed a real `.if_match(...)` fix — the compiler cannot see this gap, the same way it cannot see a misspelled `@@allow` action (§2.0's own already-documented blind spot, now joined by a second one of the identical shape). The only way to find every real call site was `grep`ing for the generated `Update<Model>Input` type names and reading each one by hand, then confirming with the live suites — never trust `cargo check` alone here.

**The REST ETag/If-Match wiring itself needed zero application code.** Read directly, not assumed: `cratestack-macros-0.7.10/src/axum/model/prep/etag.rs` generates, per model, entirely from whether it has a `@version` field — a `PATCH` handler that parses `If-Match` into `Option<i64>` (a missing header is `CoolError::PreconditionFailed("If-Match header required")`, matching the builder-level message above almost verbatim), calls `.if_match(version)` on the same `UpdateRecordSet` this file's own delegate code calls, and stamps the response `ETag` header from the returned row's `version` on success; a `GET`/detail handler stamps the same header from whatever it read. `CoolError::PreconditionFailed` maps to HTTP `412`, code `"PRECONDITION_FAILED"` (`cratestack-core-0.7.10/src/error.rs`, read directly). So the ten new `@version` fields are the entire "put it in the data layer once" mechanism for the REST surface — nothing in `crates/sms-api/src/router.rs` needed to change for this ticket at all.

**A structural finding that changed the shape of the proof this ticket needed: `GatewayAuth::authenticate` (`crates/sms-api/src/auth.rs`) hardcodes `role: "app"` for every real token this deployment ever mints — not read from any JWT claim.** `crates/sms-auth/tests/rbac_layer2_live_postgres.rs`'s own module doc already said "no live success case" exists for `PATCH /providers/{id}` because no human-login flow can mint an `owner`/`admin`/`operator`-role token; reading `authenticate`'s body line by line resolves *why* more strongly than that note states it: `role` is a literal constant in the function, not derived from `scope`/`perms`/anything else the token carries, so even the hand-signed-stand-in-token technique `m1_acceptance_gate_live_postgres.rs`'s `sign_developer_stand_in_token` uses to reach a Layer-2 *denial* cannot reach a Layer-1 *allow* here either — forging claims changes what a real token would have carried into `GatewayAuth`, not what `GatewayAuth` derives from it. Consequence: **no write route any of #59's ten models exposes is reachable over real HTTP by any token this deployment can currently issue, full stop** — including this console's own service-account credential (`packages/gateway/src/token.ts`), which is exactly such a real, `kind: "app"` token. This is not a gap #59 introduced; it already existed for every one of these models' write policies. It does mean the live end-to-end proof for this ticket has to live one layer down.

`crates/sms-api/tests/if_match_live_postgres.rs` is that proof: real Postgres, `Provider` (the ticket's own PATCH-route anchor, `router::PROVIDER_WRITE_ROUTES`), the real generated delegate call the axum handler makes internally (`db.provider().update(id).set(...).if_match(v).run(ctx)`), not a hand-rolled reimplementation. Three tests: two operators loading the same row, one saving successfully, the second's now-stale write rejected with a genuine `CoolError::PreconditionFailed` (asserted directly against `.status_code().as_u16() == 412` and `.code() == "PRECONDITION_FAILED"` — the framework's own HTTP-shape fact, not this crate's own `errors.rs`, which only maps *database*-level SQLSTATEs and never touches a builder-level `PreconditionFailed` at all) and the row left holding operator A's write, never B's; a correct `if_match` in isolation; omitting `if_match` entirely on a versioned model. Verified to actually fail, not just pass by construction: temporarily pointing operator B's write at the *fresh* version instead of the stale one reproduced a real assertion panic naming the exact silent-overwrite this ticket exists to prevent — the panic message printed back the row with `displayName: "Renamed by operator B"` and `version: 2`, i.e. B's write had gone through and clobbered A's, exactly what a genuine `if_match` bug would produce — restored afterward, all three tests passing again.

**The web half (`packages/gateway`) hits the identical structural wall — the console's own credential cannot call any of these routes for real either — so its own proof is mechanism-level, not a live round trip.** `packages/gateway/src/rest.ts` is the new generic seam: `fetchWithEtag`/`updateWithIfMatch`, following `messages.ts`'s existing `getJson` shape (Bearer + one 401 retry) but capturing the response `ETag` header on the way in and sending it back as `If-Match` on the way out — the one piece `messages.ts` never needed, since `Message` has no human edit action. `errors.ts` already mapped `412 → CONFLICT` before this PR (its own module doc names the mapping, clearly written in anticipation of this ticket); `isStaleWriteError` is the one new addition — checks `httpStatus === 412` so a screen can show "someone else changed this, reload" instead of a generic conflict toast, distinct from a duplicate-key `409` landing in the same `trpcCode` bucket. `packages/gateway/src/rest.test.ts` proves the mechanism against a fake upstream (an injected fetcher, the same dependency-injection shape `message-stream.ts`'s own `fetchWindow` already uses) — real header parsing, real `If-Match` attachment, real status-based branching, `token.ts` mocked since key-loading has nothing to do with what this file tests. `vitest.config.ts` gained a real (if fake) `SMS_API_URL` for the first time, needed because `restUrl()` resolves every path against it before the injected fetcher ever runs.

**Migrations were regenerated wholesale, following this file's own documented workflow, and it caught a real trap before it reached CI.** `cratestack --version` matched the pin exactly (`0.7.10` = `0.7.10`, corrected AGENTS.md's own stale claim about this — see the "Regenerating migrations" section above) so regeneration was safe for the first time in this repo's history; the diff against the unmodified schema was byte-for-byte the ten new `version BIGINT NOT NULL` columns and nothing else. Applying the regenerated `0002_bootstrap` to a real scratch Postgres immediately failed: `null value in column "version" of relation "operator_prefix_rules" violates not-null constraint` — §2.10's hand-written seed `INSERT INTO operator_prefix_rules` (14 rows) predates `@version` existing on that model and, being raw SQL rather than a CrateStack `create()` call, never got the framework's own server-side `version = 0` seed (`cratestack-sqlx-0.7.10/src/query/write/create_exec.rs`'s `create_record_with_executor`, which the bootstrap SQL bypasses entirely). Fixed by adding `version` (literal `0`) to every row in `docs/architecture.md` §2.10's own seed table and regenerating; `ci/test-state-machine.sql`'s own hand-written `apps`/`webhook_endpoints` fixture inserts needed the identical fix for the identical reason. Both migration paths — `ci/apply-migrations.sh` and the production `app/sms-migrate` binary — were verified against a real, freshly created Postgres before trusting the regeneration, and `ci/test-state-machine.sql`'s full assertion suite (and `just parity`) passed against the result. `sdks/rust/vsms-sdk-rust/schema.cstack` was re-vendored (`vendor-schema.sh`) and its own `cargo check --all-targets` confirmed clean — the exact step whose omission made #185 red.

Explicit scope cuts, named rather than left implicit: no edit screens (#52–#58's own job, unblocked by this PR rather than built by it); no human-login `AuthProvider` (the structural gap this PR's own finding sharpens, not closes — tracked the same way #24/#25 already tracked it); `WebhookEndpoint`'s hot-path worker writes keep their existing best-effort semantics (a detected-but-still-dropped race, not a CAS-retry loop) rather than being redesigned as part of a ticket about console edits.

## Milestone 4: the Jobs and Workers screens landed (#56/#57) — the diagnostic core, alongside #50

`docs/roadmap.md` names #50 (messages detail), #56, and #57 as "the diagnostic core" of M4's own gate — *"an operator can diagnose a failed message without touching SQL."* #56/#57 landed together, in one PR, because they share a data layer the issue text itself points at: `pg_locks` for #57, `Job` for #56, both read through the same admin console credential.

**#57's data has no delegate — `pg_locks` isn't a schema model** — the same shape this file's own R1 exceptions table already has six entries for (`drain.rs`, `reap_outbox.rs`, the readiness probe, `lease.rs` itself, migrations, `LISTEN`/`NOTIFY`). `crates/sms-api/src/worker_locks.rs` is the seventh: a `pg_locks` ⋈ `pg_stat_activity` query, keyed on the same `(classid, objid)` `lease.rs` takes locks under. Verified live, not assumed, against a real Postgres 16 with a real held lease: a granted two-key advisory lock is exactly one row (`objsubid = 2`), and a losing `pg_try_advisory_lock` leaves **no row at all** — unlike the blocking form, there is nothing to queue. The consequence for #57's own framing ("two `dispatch` workers means a blocked Orange account"): Postgres's own exclusivity guarantee means `pg_locks` can *never* show two granted rows for the same role — if that ever happened for real, it would mean a bug bypassing `run_singleton`'s lease check entirely, not something this table could surface directly. The Workers screen states this plainly rather than implying it would catch that shape of bug.

To make "which node" answerable at all, `RoleLease::try_acquire` (`crates/sms-worker/src/lease.rs`) now takes a `worker_id` and stamps it onto the lease connection's own `application_name` via `PgConnectOptions` — the dedicated, never-pooled connection this module's own doc already explains exists for nothing but holding one lock, so its `pg_stat_activity.application_name` is, for the lease's lifetime, that worker's identity. The `NS`/lock-key table itself moved to `sms_api::worker_roles` (a new, tiny, pure module) rather than staying duplicated: `sms-api` cannot depend on `sms-worker` (the dependency runs the other way), so the one fact both sides need — role name to `objid` — lives on the `sms-api` side of that one-directional edge, and `lease.rs` now looks it up there instead of keeping its own copy. `crates/sms-worker/src/lease.rs`'s own test module cross-checks `sms_api::worker_roles::is_singleton` against `Role::cardinality` for all six roles, so the two tables can't quietly drift apart.

**#56's re-enqueue needed a new state-machine edge.** `dead -> pending` didn't exist — `dead` was a true dead end, on purpose (`0002_bootstrap`'s own comment). Added the same way #43 added the identical edge for `WebhookAttempt`: one row in `job_state_transitions` (§2.10, `0002_bootstrap` regenerated, `ci/test-state-machine.sql` gained a block walking a job to `dead` and back), a `requeueJob` procedure (`crates/sms-api/src/procedures.rs`) that proposes only that edge and returns a named `409 Conflict` for anything else — `failed -> pending` already exists for `jobs::apply_failure`'s own automatic backoff, but `failed` is a same-tick transient state no operator poll can realistically observe, so `requeueJob` doesn't accept it as a starting state at all. `Job`'s own list/detail `@@allow` gained `auth().kind == "app"` (schema-policy-only, no DDL) — the same unscoped shape `SenderId`/`OptOut` already use, since `Job` has no `appId` to scope by the way `Message` does.

**That last point is the real finding of this PR, not a footnote: for `Job`, Layer 2 is the actual perimeter, not defense in depth.** Every prior Layer-2 example in this file (`PROVIDER_WRITE_ROUTES`, `sendMessage`) is provably redundant today, because `GatewayAuth` never mints anything but `role: "app"`/`"system"` and the underlying model's own `@@allow` already excludes `"app"`. `Job` breaks that pattern on purpose: its `@@allow` *does* admit `auth().kind == "app"`, so any provisioned app client — not just the admin console's own credential — passes Layer 1 and reaches the whole system's job backlog unless Layer 2 stops it. New scopes `job:read`/`job:enqueue`/`worker:read` (§5.2, the same literals `operator`'s own `perms` already used for the first two) close that: `router::JOB_READ_ROUTES` gates `GET /jobs`/`GET /jobs/{id}`, and `requeueJob`/`workerLocks` each call `require_permission` directly. Proven with a real, live, end-to-end HTTP success case — `crates/sms-auth/tests/rbac_layer2_live_postgres.rs`'s new `job_read_route_succeeds_for_a_token_carrying_job_read` is the first test in that file to reach a genuine `200` through both layers with a real token, something `PROVIDER_WRITE_ROUTES`'s own tests there explicitly cannot do (that route's Layer 1 already excludes every issuable token). The admin console's own client needs the three new scopes granted at provisioning time — `scripts/demo.sh` and `docs/runbooks/getting-started.md` updated to request them, `@vsms/env`'s `SMS_CONSOLE_SCOPE` default extended to match.

Two Rust guard failures reproduced on purpose, not just asserted: `requeueJob`'s own `.if_match(existing.version)` removed entirely first — cratestack's own runtime refused the write outright (`PreconditionFailed("If-Match header required for versioned model")`), before any race could even matter; restored, then a *wrong* version substituted (`existing.version + 999`) to reach the actual race-losing path — `PreconditionFailed("version mismatch: expected 1002, found 3")`. Both restored, both confirmed passing again.

The admin console gained two screens (`admin/app/jobs`, `admin/app/workers`) — plain `refetchInterval` polling, not a live stream hub like the messages list (§6.5's live-list rules are specific to that flagship screen, and a six-role or job-backlog diagnostics table doesn't warrant a second server-side hub). `@vsms/ui`'s `status-tokens.ts` closed its own long-standing "Job states deliberately are NOT mapped here yet" gap — a `JobStatusPill` alongside `StatusPill`, sharing the same glyph geometry (`StateMarkFromMeta`, extracted from `StateMark` without changing its existing public API) but its own `JOB_STATUS_META`: a job's `failed` is retryable, not terminal, and is deliberately not styled the way a message's own terminal `failed` is.

## Milestone 4 started: the human login flow (#194)

`#97`/`#98` cut the authorization-code/human-login path from the OP because no admin console existed yet to need it — M4 is that console, so the cut came due. #194 closes it: real humans can now log in, hold a real role, and reach a real `hasRole('operator')`-gated policy.

**`authkestra-op` 0.3.3 does support `authorization_code` + PKCE, fully — read from the vendored source, not assumed.** `authkestra_op::handlers::authorize::handle_authorize` enforces S256-only PKCE (rejects `plain`, rejects a `code_challenge_method` with no `code_challenge`), exact `redirect_uri` matching, `response_type == "code"`, and grant-type admission; `authkestra_op::handlers::token::handle_authorization_code` enforces the matching verifier check (`sha256(code_verifier) == code_challenge`, base64url, `S256` only — anything else is a hard `server_error` rather than a silent bypass) and issues a real `id_token` when `openid` is in scope. All of this was already exercised by the library's own test suite (`test_missing_pkce_redirect_error`, `test_plain_pkce_redirect_error`, `test_successful_exchange_with_pkce`, `test_invalid_pkce_verifier`, ...) before this PR ever ran it for real. The `MachineOnlyOpStore` this codebase already assembled for #20 turns out to need **zero changes** for this: its authorization-code and refresh-token slots were always real, correct `MemoryStore<T>` — never exercised, because nothing ever mounted `/authorize` or a login route, not because they were placeholders. In-memory is the *right* choice for both, not a shortcut: this deployment runs exactly one `serve` process, an authorization code lives at most 60s, and a lost refresh token on restart just forces a re-login.

**What the library does *not* give you: a login form, or any way to establish the `Identity` `handle_authorize` requires before it will run.** That's the real design decision #194 had to make, and the issue explicitly left it open: authenticate humans against `authkestra-op` itself, or federate to an external OIDC IdP with this OP acting as a broker? **Chosen: local password authentication, entirely within this system, backed by Argon2id — not a federated external IdP.** Full reasoning is in `crates/sms-auth/src/login.rs`'s own module doc; the short version is that federation needs a second, equally security-sensitive OIDC *client* implementation and an actual external IdP this deployment can point at (none decided — see the "Open questions" list below, unchanged by this PR), plus nothing in this sandbox to prove it against end to end the way this repo's fake-for-every-external-dependency convention (`sms-fake-orange`) demands. Local password auth needs nothing this deployment doesn't already have and is fully testable against a real Postgres with no external dependency.

**Say it as loudly in this file as the PR that introduced it says it in its own doc comments: this system now stores password hashes, which it did not before.** New security surface, not a footnote. `crates/sms-auth/src/login.rs` — Argon2id (crate defaults: 19 MiB, 2 iterations, 1 lane), a fresh random salt per hash, and a **timing-safe "no such user" path**: `authenticate_user` always runs a real Argon2 verify, against a lazily-computed dummy hash when no matching active account exists, so "wrong password" and "no such account" cost the same wall-clock time and return the identical `LoginError::InvalidCredentials`. The password hash itself lives in a **new model, `UserCredential`, not a field on `User`** — because §2.0's own grammar table already answers the question of whether that's safe: **"No field-level read masking. Model-level access only."** `@sensitive` redacts audit snapshots, never an HTTP response body — a password hash on `User` would come back verbatim from `GET /users/{id}` to every role `User.read` already admits (owner/admin/auditor). `UserCredential` is `hasRole('system')` on every action, the same isolation `OauthSigningKey.privateKeyPem` already uses for the OP's own signing key, and no console screen — present or future — may ever read or write it directly. This is a deliberate, flagged deviation from the issue's own "the schema is already shaped for this and needs no new models" framing: the field-masking constraint made the new model unavoidable, not optional.

**The real `authkestra-op` library shape ruled out baking role/perms into the access token at issuance, which §5.3's own worked example assumed.** Found live, not by reading the design doc: `handle_authorization_code` calls plain `TokenManager::issue_user_token`, never `issue_user_token_with_extra` — the only method that can stamp `extra` claims onto a token at mint time. Forking that handler to add one was considered and rejected: it would mean re-implementing PKCE/redirect-uri/client-binding validation alongside it, exactly the security-critical duplication this codebase avoids everywhere else (the jwks/discovery hand-rolling in `app/sms-gateway/src/op.rs` is the precedent, and even those don't touch security-decision logic the way a token-issuance fork would). Instead `sms_api::auth::GatewayAuth`'s new human path (`authenticate_human`, `crates/sms-api/src/auth.rs`) resolves role/perms with a per-request, 60s-TTL-cached `User`/`Role` lookup — the same cache shape `app_cache` already uses for `AppClient`. This is not a consolation: a role change or account deactivation now takes effect within one cache TTL, strictly *more* responsive than "up to 15 minutes" §5.3 originally described for the baked-in-at-issuance design.

**A human token's `aud` is real and must be checked — unlike a service-account token's self-referential one.** `GatewayAuth`'s existing `Validation.validate_aud = false` (§4.2's own reasoning: `aud == sub == client_id` for `client_credentials`, nothing fixed to check) still applies globally, since one `Validation` decodes both realms. The human-only audience check (`claims.aud == Some(human_client_id)`, `human_client_id` a `GatewayAuth::new` parameter, `sms_api::DEFAULT_CONSOLE_CLIENT_ID = "sms-console"`) is a manual, post-decode comparison inside `authenticate_human` — the exact "revisit this line before wiring `identity`-bearing tokens up to anything" the previous revision of this type's own doc comment flagged.

**`POST /login`, a raw axum route in `app/sms-gateway/src/login.rs`, is the login form's server-side leg** — not `GET /authorize` (never mounted; nothing needs it, since `sms-console` is the only OIDC client this deployment will ever have, and a spec-compliant redirect-to-a-hosted-login-page dance buys nothing a first-party BFF needs). It collapses "authenticate the human" and "run the real `handle_authorize`" into one call: `sms_auth::login::authenticate_user`, then a real `authkestra_op::handlers::authorize::handle_authorize` — unmodified library code enforcing every PKCE/redirect-uri/state property #194 requires — with the resulting `Identity`. `admin`'s own `POST /api/auth/login` route handler is the only intended caller; the browser never talks to `sms-gateway` directly for this step.

**`admin/middleware.ts`'s Basic-auth gate (#48) is gone — a hard cutover, not a parallel path**, matching this repo's own standing convention. No `DASHBOARD_AUTH`/`DASHBOARD_BASIC_USERS`/`DASHBOARD_BASIC_REALM` env vars exist any more; `@vsms/env`'s cross-field validation now requires `ADMIN_BASE_URL` to be `https://` in production instead. The full flow: `GET /login` (middleware mints and encrypts a PKCE/state/nonce transaction into a short-lived `vsms_oidc_txn` cookie — has to happen in middleware, not the page component, because Next.js only allows `cookies().set()` in a Server Action/Route Handler/Middleware, never a plain Server Component render) → the login page's plain `<form method="post">` (no client JS) → `POST /api/auth/login` (reads the txn cookie server-side, never trusts the form for `state`/`codeChallenge`; calls `sms-gateway`'s `/login`; on success, redirects the *browser* to the URL that returned — a genuine HTTP redirect, not a JSON response, so `state` is verified on a real callback the way #194 requires) → `GET /api/auth/callback` (**verifies `state`** against the txn cookie, exchanges `code` at the real `/token` with the real `code_verifier`, **verifies the `id_token`** — signature via `sms-gateway`'s own `/jwks.json`, `iss`, `aud`, `exp`, and **`nonce`** against the same txn cookie — then encrypts a `vsms_session` cookie and redirects to `/`). Both cookies are `jose` JWE (`EncryptJWT`/`jwtDecrypt`, direct `A256GCM`, key = SHA-256 of `SMS_CONSOLE_SESSION_SECRET`), `HttpOnly`/`Secure` (in production)/`SameSite=Lax`. `admin/lib/oidc.ts` is deliberately Edge-and-Node-portable (`jose` runs identically under both) because `middleware.ts` — Edge runtime, cannot opt into Node — needs the identical decrypt/verify logic route handlers use, or the two would silently drift.

**Not wired up in this PR, flagged rather than silently assumed done:** every `admin` → `sms-gateway` call still authenticates as the shared `SMS_CONSOLE_CLIENT_ID` machine credential (`packages/gateway/src/token.ts`), not the logged-in human's own access token — #194 built the login mechanism and the session, not the rewiring of every existing tRPC route to use a per-request human token. That's what makes `#50` (message detail, app-scoped) buildable now rather than done. Also unwired: rate limiting on `/login` itself (the same class of gap `#156`/`#168` closed for `/token`, not yet closed here), and `admin`'s own display of "which role is this" (`Session.role` is stamped `""` — the `id_token` carries no role claim by design, and there's no cheap way to fetch one without a dedicated endpoint; cosmetic only, Layer 3, never a security boundary).

**Provisioning tooling, mirroring `provision-client`'s own conventions:** `sms-gateway seed-console-client` registers the `sms-console` `OauthClient` row (`tokenEndpointAuthMethod: none` — a public BFF client, PKCE is the protection, no column could hold a shared secret anyway), idempotent via the same create-then-catch-`23505` shape `create_or_find_provider` uses. `sms-gateway provision-user` creates a `User` + `UserCredential`, generates a random 24-character password (never an operator-supplied `--password` flag — that would land in shell history and the process list, the exact exposure `provision-client`'s own `--key-out` file exists to avoid), and prints it exactly once. Neither seeds `Role` rows: §5.2's six built-in roles are not seeded by any migration, matching this repo's "no seed data assumed" posture — the very first `owner` account has to be bootstrapped by hand against a fresh database (see the deploy runbook), the same bootstrapping problem `rotate-signing-key` already has for the OP's own signing key.

**Every one of the four required guard-failure proofs was run for real, output captured, not merely asserted:**

- **PKCE verifier mismatch** — `app/sms-gateway/tests/login_flow_live_postgres.rs`'s `a_wrong_pkce_code_verifier_is_refused_at_the_token_exchange` spawns the real `sms-gateway` binary, completes a real `/login`, and presents a `code_verifier` that doesn't hash to the original `code_challenge` at `/token` — refused with `invalid_grant`, real HTTP, real Postgres, unmodified library code doing the check.
- **State mismatch** — `admin/lib/oidc.test.ts`'s `a_mismatched_state_is_rejected` (Vitest). Broken for real: `verifyState` temporarily changed to `return true` unconditionally past the empty-string guard, which made this test fail with `expected true to be false`; restoring the real `timingSafeEqual` comparison restored a pass.
- **Inactive-user rejection** — `crates/sms-auth/tests/login_live_postgres.rs`'s `a_correct_password_against_a_deactivated_account_is_refused`. Broken for real: `find_active_user`'s `.and(user::active().is_true())` clause temporarily removed, which made a deactivated account's exactly-correct password authenticate successfully (`Ok(AuthenticatedUser { ... })` where an `Err` was expected); restoring the clause restored the refusal.

## Milestone 6: audit log anchoring landed (#68)

`crates/sms-worker/src/jobs/anchor_audit.rs` — the last unbuilt §7.5 job kind besides `verify_backup`/`poll_balance`/`probe_providers`/`reconcile_clients`/`cleanup_secrets`. The issue itself named no implementation; the design question ("hash chain vs a bare periodic digest vs external anchoring") had to be answered and justified, not assumed — full reasoning lives in that file's own module doc, not repeated here in full, but the load-bearing parts:

**A plain, unkeyed SHA-256 hash chain, not a Merkle snapshot and not external anchoring.** Each daily anchor folds every `cratestack_audit` row in its own period into a `rangeHash`, and chains that onto the *previous anchor's own* `chainHash` — so deleting or editing a covered audit row, or an entire past anchor row, both break a recomputation somewhere in the chain. A bare periodic snapshot (the design doc's own §4.7 suggestion, "hash the day's rows into a Merkle root") was rejected for exactly the gap a chain closes: without linking to what came before, deleting an entire past period's rows *and its own anchor* leaves every remaining anchor internally self-consistent — nothing contradicts it. External anchoring (publishing the digest somewhere this deployment cannot itself rewrite) is the strongest of the three and was rejected only for scope: no such service exists anywhere in `deploy/`, and standing one up is real infrastructure, not a job-kind PR.

**Be honest about what this proves — the module doc's own section, restated here because it's the point of the ticket.** An anchor stored in the same Postgres instance an attacker already has write access to proves less than "tamper-evident" implies: editing a covered audit row is caught (the next run's own re-verification, or a manual one); editing or deleting an entire past anchor row is caught too, as long as a *later* anchor still references its `chainHash`. **Deleting the single most-recent anchor before anything else references it is not caught by anything in this database** — an attacker with the same write access this job itself has, who can also recompute a fresh chain forward from that point, leaves no contradiction. Closing that needs real external anchoring or an offsite copy — named as follow-up, not built here, and not silently implied by the issue title.

**A keyed HMAC chain under `crates/sms-api/src/pepper.rs`'s existing `HashPepper` was considered and rejected — not because it's weaker, but because it's a second, separate secret-management problem this ticket doesn't ask for.** It would raise the bar from "an attacker with only `psql` access can recompute a valid chain" to "...cannot, without the pepper too" — a real improvement. Rejected because `pepper.rs`'s own doc is explicit a pepper is designed to *rotate*, and rotation doesn't retroactively rehash anything: a keyed chain would need every historical pepper value kept around indefinitely just to keep re-verifying anchors signed under it, or every rotation would make every past anchor look like tampering. A plain unkeyed chain has no such coupling.

**A real framework bug, filed upstream, not worked around silently: `@length` on a nullable `String?` field breaks the *generated* `UpdateXInput::validate()`, unconditionally, regardless of whether `@@allow("update", ...)` exists to route to it.** `AuditAnchor.prevChainHash` was originally `String? @length(min: 64, max: 64)` — `cargo check -p sms-api` failed `E0308`, `&Option<String>` passed where `validate_length` needs `&str`. Read from the vendored source, not guessed: `cratestack-macros-0.7.10/src/model/inputs.rs`'s `generate_update_input_struct` unconditionally emits `Update{Model}Input` for every model (no gate on whether any `@@allow("update", ...)` clause exists to ever construct one), and its own `validate_impl_tokens(&fields, true)` wraps *every* field in one `Option<...>` for "present or absent" regardless of the field's own nullability — so a `String?` field becomes `Option<Option<String>>` there. `emit_field_validators`'s own optionality check (`cratestack-macros-0.7.10/src/validators/emit.rs`) only unwraps one layer, binding `value: &Option<String>` and passing it straight to `validate_length`, which wants `&str`. Fixed by *not* making `prevChainHash` nullable at all: the very first anchor uses a fixed 64-`'0'`-character genesis sentinel instead of `NULL` — a cleaner design in its own right (the field is never actually "absent" in the cryptographic sense; "no predecessor" is itself a fixed, known value), and it sidesteps the bug entirely rather than waiting on a fix. `rangeHash`/`chainHash` (both non-nullable) never hit this.

**The DDL is genuinely additive** — one new table, `audit_anchors` (`id`, `period_start` nullable, `period_end`, `row_count`, `range_hash`/`prev_chain_hash`/`chain_hash` each `@length(64,64) @db_enforce`, a real `CHECK`, `chain_hash @unique`, `created_at`), a `cs_cuid()` default and a `created_at` default (hand-added to §2.10's own lists — `AuditAnchor` doesn't `@use(Timestamps)`, no `updatedAt` at all, since nothing ever updates an anchor row, the same shape `DeliveryReceipt.receivedAt` already has), and one hand-written index (`audit_anchors_period_end_idx`, the "find the most recent anchor" lookup every run makes, same reasoning `oauth_signing_keys_active_idx` already documents for an analogous singleton-lookup index). `cratestack migrate diff` at an isolated, pin-matching `=0.7.10` CLI diffed to exactly that against the unmodified `0001_init` — confirmed, and both migrations applied to a real scratch Postgres with `ci/test-state-machine.sql` passing before being trusted.

**The eleventh instance of this file's own repeated `hasRole('system')` gap — flagged in advance, not found live**, the same discipline `Route`/`WebhookAttempt` established: `anchor_audit.rs`'s own `latest_anchor`/`verify_chain_linkage` read `AuditAnchor` under `sys` every run (the job needs the previous anchor's `chainHash` to chain the next one, and needs every prior anchor to re-verify linkage), so `AuditAnchor` shipped with `hasRole('system')` on `read` from the start and was added to `SYSTEM_READABLE_MODELS` in the same PR, not discovered broken afterward.

**R1 exceptions, the seventh and an eighth, test-only one.** `cratestack_audit` has no schema model — same reasoning `drain.rs`/`reap_outbox.rs` already establish for `cratestack_event_outbox`: no delegate, no row-level policy to bypass, no audit trail to skip (a `SELECT` isn't a mutation, and this *is* the audit table besides). The eighth, `crates/sms-worker/tests/anchor_audit_live_postgres.rs`, is the one genuinely new shape: proving tamper-evidence means the test itself has to tamper with a raw `cratestack_audit` row (and, separately, a raw `audit_anchors` row — `AuditAnchor` has no update capability at all, legitimate or otherwise) the same way a real attacker would, simulating the exact threat model this job defends against.

**A live-test-methodology trap worth internalising for the next job whose own `now` has to be pushed forward, not backward, to prove coverage.** `cratestack_audit.occurred_at` has no delegate seam to backdate — it's `chrono::Utc::now()`, stamped by the framework itself. The only way to prove a freshly seeded row falls inside a period is to push the *anchor's* `now` argument forward past `ANCHOR_LAG` instead. The first cut of `anchor_audit_live_postgres.rs` did that independently in three separate test functions sharing one binary's database (`sms_test_support` gives one database per binary, not per test) and two of them started failing `rowCount >= 1` — reproduced live: an anchor's `periodStart` inherits the *previous* anchor's `periodEnd`, which only ever moves forward, never back. Once any call pushes it minutes ahead of real time — which covering a just-now row against a fixed 5-minute lag necessarily requires — every subsequent call's own freshly-seeded row, stamped at genuine unshifted wall-clock time only milliseconds later, is already older than that inherited floor, permanently, for the rest of the process; there is no way to walk it back down without real time actually elapsing. Fixed by confining the forward shift to exactly one test function in the whole file; every other test's own `run_at` call uses real, unshifted `Utc::now()` (which only ever anchors up to the past, never poisoning the floor for whoever runs next) and doesn't depend on covering a specific fresh row.

**Tamper detection was proven to actually detect tampering, twice, the same discipline this file already applies elsewhere: break the guard, watch the test fail, restore, watch it pass.** `verify_period_content` temporarily replaced with `Ok(true)` unconditionally — `anchoring_covers_new_rows_chains_correctly_and_detects_a_tampered_row` failed with `TAMPER TEST FAILED TO DETECT TAMPERING: verify_period_content still reported true...`, restored, passed again. `verify_chain_linkage`'s own `chainHash` recomputation check temporarily short-circuited (`if false && recomputed != anchor.chainHash`) — `a_tampered_anchor_row_breaks_chain_linkage` failed with the equivalent message naming `verify_chain_linkage`, restored, passed again.

## Milestone 6: consent records, quiet hours, and the classification exemption (#72) — landed 2026-08-12

The last M6 compliance story before audit anchoring (#68). Three pieces, and the second is the one that matters: `docs/architecture.md` §10 already said "keep the audit trail proving the classification" — the honest work here was deciding what that sentence can and cannot mean, then wiring the two checks whose asymmetry (`otp`/`transactional` exempt, `marketing`/`notification` not) is what makes a mislabelled class *consequential* in the first place.

**Consent is a new model, `ConsentRecord`, not `OptOut`'s inverse.** `OptOut` is the enforcement primitive — its presence is the entire mechanism `sendMessage` already checked. `ConsentRecord` is append-only evidence with provenance (who, when, channel, scope) that a caller produces *because* the classification or the consent itself gets challenged, and it has no `revokedAt` on purpose: withdrawing consent is a new `OptOut` row, the one thing `sendMessage` already treats as authoritative, so "does this recipient currently receive X" never has two disagreeing sources of truth to reconcile. `appId`-scoped, unlike `OptOut` (a recipient's opt-out has to bind everywhere in this deployment; a consent grant is a specific app's own customer relationship — App A's marketing consent doesn't authorise App B's). `scope MessageClass` reuses the existing enum rather than a second free-form string the way `OptOut.scope` is, so `ensure_consent_on_file` matches it against `Message.class` directly and a typo'd scope string can never silently drift from the class it was meant to describe.

**What the classification audit trail actually proves, said as plainly as the module doc says it — this is the load-bearing finding of this PR, not a footnote.** `Message.class` already carries `@@audit` (present before this PR), so every `sendMessage` call writes a framework audit row, in the same transaction as the `Message` insert, capturing the declared class and the authenticated caller's identity — a real, contemporaneous, tamper-resistant-absent-DB-compromise record of *who declared what, when*. It does **not** prove the declaration was *true*: content classification from free text is not machine-verifiable the way a state transition is, so a caller willing to mislabel marketing traffic as `transactional` bypasses every check this PR adds, and the audit trail records that they did so accurately, not honestly. `crates/sms-api/src/consent.rs`'s own module doc carries the full reasoning; recording it here too because this is exactly the kind of claim that reads as solved from a section heading ("keep the audit trail") and isn't, the same shape this file's own doc-drift corrections keep finding elsewhere. Closing the actual gap needs either a manual compliance-review process reading the audit trail (this system's real answer today) or an independent content classifier — not built, not small, and not attempted here.

**Enforcement scope is derived from `docs/architecture.md` §10's own words, not invented.** Two exhaustively-matched pure functions in `crates/sms-api/src/consent.rs`: `requires_recipient_consent_controls` (governs *both* opt-out honouring and the new consent check — §10 names the identical class pair for both, "`marketing` and `notification`. OTP and transactional are exempt") and `subject_to_quiet_hours` (narrower — `marketing` only; §10's quiet-hours bullet never names `notification`). Exhaustive `match`, not `matches!` with a wildcard, so a fifth `MessageClass` variant fails to compile here rather than silently defaulting either way — the same discipline this file's other "single source of truth" functions (`default_validity`, `message_event_type`) already use.

**A real, pre-existing gap found while wiring the first of those two functions in: opt-out honouring was unconditional for every class, not class-gated at all.** Before this PR, `ensure_not_opted_out` ran on every `sendMessage` call regardless of `class` — more restrictive than §10 ever specified (an opted-out recipient couldn't receive an OTP either), accidentally safe rather than a compliance hole, but not what was asked for. Fixed by gating the existing call site on `requires_recipient_consent_controls(class)`; `an_opted_out_recipient_is_refused_before_persistence` (pre-existing test) had to move from the default `transactional` class to `notification` to keep testing what it always meant to, and a new `an_opted_out_recipient_still_receives_an_otp_or_transactional_message` proves the exemption half directly.

**Quiet hours are a policy knob, deliberately not a hardcoded legal constant, and deliberately not runtime-configurable either.** `MARKETING_QUIET_HOURS_START_WAT`/`_END_WAT` are `pub const`, named and doc-commented as self-imposed best practice ("no Cameroon-specific statutory rule was found") rather than buried inline — the next reader should see a value to reconsider, not a rule to trust. Not wired to an env var or a `Settings` model: no such model exists yet, and this repo's own standing preference is a visible hard-coded decision over a half-built configurability seam nobody asked for. Enforced at `sendMessage` (accept time), not `dispatch` (hold-and-release) — both are defensible, and the choice here follows `send`'s own existing framing ("this procedure's job is the decision, not delivery"): a message accepted at 19:59 and held server-side until 08:00 the next day would sit silently in `queued` for up to twelve hours with no caller-visible signal, where an accept-time rejection gives the caller a synchronous, actionable answer immediately. The real cost: no built-in "schedule this campaign for the next quiet-hours window" — `SendMessageInput.scheduledAt` already exists for a caller to do that itself, but nothing here holds a message across the boundary automatically.

**Tests are structured around one real trap: quiet hours and consent share `marketing`, so a naive test suite would be flaky by time of day.** `consent.rs`'s own unit tests are deterministic and boundary-exact (07:59/08:00/19:59/20:00 WAT, both sides of each edge) with an injected clock, not `Utc::now()`. The live suite's consent-specific tests (`a_notification_send_with_no_consent_record_is_refused`, `a_notification_send_with_a_matching_consent_record_succeeds`, `a_consent_record_scoped_to_a_different_class_does_not_authorise_this_one`) deliberately use `notification`, not `marketing`, so quiet hours can never be the confounding reason for a pass or a failure. The one test that does exercise `marketing` end to end (`a_marketing_send_matches_the_real_clocks_current_quiet_hours_state`) is live-clock-adaptive by construction — it asks `consent::is_within_marketing_quiet_hours(Utc::now())`, the exact function `send()` itself calls, what today's expected outcome is, and asserts against that rather than against a fixed assumption about time of day. Correct and non-flaky at any hour this test happens to run, and it can never silently stop testing the real boundary the way a fixed "assume it's daytime" assumption could.

**The guard-failure proof this ticket asked for, run for real, output captured.** `a_marketing_send_is_refused_but_a_transactional_send_to_the_same_recipient_is_not` sends a `marketing` message with no consent on file (refused) and a `transactional` message to the *same* recipient (accepted) — the literal classification-exemption asymmetry #72 exists to prove. With `Self::ensure_consent_on_file(...)` temporarily short-circuited (`if false && ...`) in `Procedures::send`, both this test and `a_notification_send_with_no_consent_record_is_refused` failed with:

```

Restoring the real call restored a pass on all 16 tests in `send_message_live_postgres.rs`. Separately, the fifteenth instance of this file's own repeated `hasRole('system')` gap — `Procedures::ensure_consent_on_file` reads `ConsentRecord` under `sys` from the moment it was written, so it was classified straight into `SYSTEM_READABLE_MODELS` (never shipped broken, same "flagged in advance" shape as `Route`/`User`/`Role`), and pulling `hasRole('system')` from its `read` clause reproduced:

before being restored.

**No `@@retain` on `ConsentRecord`, and this is a real, unresolved tension flagged rather than solved.** `Message` purges `msisdn` at 90 days because minimisation applies to content with no remaining purpose (#67) — but proof of consent is not that; it's the thing you produce *because* you were challenged, which argues for keeping it at least as long as the relationship lasts, plausibly longer. Keeping `msisdn` in plaintext indefinitely to serve that need reproduces the exact problem #67 closed for `Message`. Not resolved here. `msisdnHash` — what the consent check actually matches on — inherits the same pepper-rotation-orphans-purged-rows caveat every other `msisdnHash` column in this schema already has (§2.5/§3.1, `sms_api::pepper`'s module doc).

## Milestone 4: the console authenticates upstream as the human (#211) — landed 2026-08-13

#194 built the mechanism (a real `authorization_code` + PKCE login, `GatewayAuth` resolving a genuine human principal); nothing used it. `packages/gateway` kept authenticating **every** upstream call as the console's own machine credential (`SMS_CONSOLE_CLIENT_ID`, `role: "app"` always) regardless of who was signed in — found live, signing in as a freshly provisioned `owner` and watching a `Provider` edit fail with `missing required permission "provider:update"`. That made #52/#58's own write screens buildable-but-pointless (every edit would 403 on an otherwise-correct Layer 2 check) and left `@@audit` unable to say *who* made a console write.

**The decision, and why it was nearly free.** Two shapes were possible: forward the human's own `accessToken` and let `GatewayAuth` validate it directly, or exchange the session for a separate per-request token. Checked before assuming: `GatewayAuth::authenticate_human` (`crates/sms-api/src/auth.rs`) already fully validates a human token — signature via JWKS, issuer, and audience against `sms-console` (`human_client_id`) — and `admin/middleware.ts` already refreshes `session.accessToken` ~60s ahead of expiry on *every* request, redirecting to `/login` outright if refresh fails. So by the time a request reaches the tRPC route handler, the token is already fresh for that request's lifetime. No exchange step, no expiry logic needed in `packages/gateway` at all — forwarding the session token verbatim was correct and, per the issue's own framing, "nearly free."

**The plumbing: `AsyncLocalStorage`, not a threaded parameter — and why that shape specifically.** `packages/gateway`'s ~13 upstream-calling functions across 9 files (`rest.ts`, `providers.ts`, `routes.ts`, `route-simulator.ts`, `workers.ts`, `dashboard.ts`, `jobs.ts`, `messages.ts`, `client.ts`) are called via `ctx.gateway.xxx()` in `packages/api/src/routers/*.ts` — a reference to the whole module, not a per-request-bound instance. Threading an explicit credential parameter would have touched every one of those call sites *and* every router. Instead, `packages/gateway/src/request-credential.ts`'s `AsyncLocalStorage<RequestCredential>` is set exactly once, at the single true per-request boundary — `admin/app/api/trpc/[trpc]/route.ts`'s `handler`, reading the `x-vsms-access-token` header `admin/middleware.ts` forwards (same mechanism already established for `x-vsms-actor`/`x-vsms-role`, just carrying a real bearer token this time) — and every ordinary call site resolves it implicitly via `resolveUpstreamAccessToken()`.

**The property the ticket actually asked for — impossible for a new screen to silently get the machine credential — is structural, not a convention to remember.** `resolveUpstreamAccessToken()` throws if no credential scope was ever entered, rather than defaulting to the machine credential. A new gateway function gets the human token automatically the moment it's invoked through the ordinary tRPC path (which always sets one). Reaching for the machine credential requires importing `getMachineAccessToken` from `./token` directly, by name — grep-able, and reserved by that module's own doc for exactly two documented exceptions:

- **`client.ts`'s `previewMessage`/`sendMessage`.** `crates/sms-api/src/procedures.rs::Procedures::caller_client_id` hard-rejects any caller whose `kind` isn't `"app"` — "sendMessage currently requires a machine (client_credentials) caller — deriving an App for a human caller has no design yet." This is a pre-existing Rust-side constraint, not a choice #211 made: forwarding a human token here wouldn't merely be the wrong credential, it would turn every composer send into a guaranteed `Validation` error.
- **`messages.ts`'s `listMessagesForStream`.** `MessageStreamHub` is a process-wide singleton — one poll loop shared by every open browser tab, triggered by whichever request happens to call `subscribe()` first. `AsyncLocalStorage` context set up inside a `.run()` call propagates to timers/callbacks scheduled during that call's lifetime, indefinitely — so if this function resolved the ambient credential, the *first* operator to open the Messages tab would have their own token captured into `hub.start()`'s `setInterval`, and every other operator's tab would silently poll using that first operator's credential. `messages.ts::getJsonWith` takes `resolveToken`/`onUnauthorized` as parameters specifically so `getJson` (human, used by `listMessages`/`getMessageById`/`listMessageReceipts`) and `getJsonAsMachine` (used only by `listMessagesForStream`) can share one fetch/retry implementation while never sharing a token source.

**A real, pre-existing bug found and fixed in the same PR, because forwarding a human token for the first time is what finally exercised it.** The seeded role `permissions` (`schema/migrations/postgres/0002_bootstrap`, source of truth `docs/architecture.md` §2.10) used `message:read`/`message:send` where `crates/sms-api/src/rbac.rs::require_permission` actually checks the literals `sms:read`/`sms:send` — the same ones the service-account scope table already used correctly (`SMS_CONSOLE_SCOPE=sms:send sms:read ...`). And no role carried `dashboard:read` at all, despite §5.2's own prose table naming it for `operator`. Both were silent because no human token had ever reached `sms-api` before #211 to hit `listMessageReceipts`/`dashboardSummary`'s own `require_permission` checks. Fixed by renaming the seed literals (`message:read`→`sms:read`, `message:send`→`sms:send`) and adding `dashboard:read` to `owner`/`admin`/`operator`/`auditor` — data-only, no schema/DDL change (`permissions` is a plain `String` column; `cratestack migrate diff` untouched). This is the same recurring shape this file has now recorded many times over (a policy gap invisible until the right context actually exercises it), just on seeded data instead of a `@@allow` clause.

**A real, deliberate consequence, not a bug: cross-app visibility becomes live for the first time.** `Message`/`DeliveryReceipt`'s own `@@allow` already admitted `auth().kind == "user"` unconditionally — unscoped by `appId` — before this PR (`schema.cstack`, unchanged by #211). Nothing had ever exercised it, because no human token reached `sms-api`. Forwarding one means the Messages list and Dashboard now show *every app* in this deployment to *any* signed-in human, regardless of role — genuinely wider visibility than the machine-credential-scoped-to-one-app behaviour before it, and exactly the "cross-app visibility" the issue named as something it unblocks for #50. The messages list's own live-update poll (`onStateChange`) stays scoped to the machine credential's one app, deliberately (see `listMessagesForStream`'s own exception above) — so a row belonging to another app can appear in the initial list but won't receive a live update until the next refetch. `messages-screen.tsx`'s own module doc and on-screen banner state this; it is not silently smoothed over. `providers-screen.tsx`, `routes-screen.tsx`, and `dashboard-screen.tsx`'s own stale "cannot succeed / scoped to this app only" banners (written before #211, when they were true) were rewritten to match reality rather than left to rot — the exact "documentation asserts something the code does not do" shape this file has flagged repeatedly, caught here before merge rather than found live later.

**Proven live end to end**, not just reasoned about, via `just demo` (`docs/runbooks/getting-started.md`'s own login flow): signed in as `demo@vsms.local` (`--role-key owner`), a `Provider` edit that previously 403'd now succeeds — `Provider.displayName` and `version` genuinely changed in Postgres, and `cratestack_audit`'s own `actor` column reads `{"sub": "<demo@vsms.local's real User.id>", "kind": "user", "role": "owner", ...}`, not the machine `AppClient`'s `client_id` — the audit trail can now say *who*. A second user provisioned with `--role-key auditor` (which carries `provider:read` but not `provider:update`) gets a real, live `403` — `Save failed: missing required permission "provider:update"` — on the identical edit, and the row is confirmed unchanged in Postgres afterward. `packages/gateway/src/request-credential.test.ts`'s own fail-loud guard was broken on purpose (made `resolveUpstreamAccessToken()` silently return the machine token instead of throwing when no scope was entered) and confirmed to fail with `promise resolved 'machine-token' instead of rejecting` before being restored.

**One same-origin trap hit while proving this live, worth recording so it isn't rediscovered:** `packages/api/src/context.ts`'s pre-existing CSRF check (`assertSameOriginForMutations`, unrelated to #211, untouched by it) compares the request's `Origin` header against `new URL(req.url).origin`. Reaching the dev server via `http://127.0.0.1:3100` in a browser-automation environment produced a genuine mismatch (`req.url`'s computed origin came back `http://localhost:3100` even though the browser's own `window.location.origin` and `Origin` header both correctly said `127.0.0.1`) — GET requests were unaffected (the check only runs on POST), so reads worked throughout, but the mutation 403'd until the whole flow (login redirect_uri included) was redone consistently through `http://localhost:3100`. Not a bug this PR introduced or needed to fix; recorded so the next person debugging a "read works, write 403s with a cross-origin message" symptom in a similar sandboxed setup doesn't waste time suspecting the credential-forwarding mechanism first.

## `packages/gateway`: one null-normalization seam replaces fourteen (#221) — landed 2026-08-13

The exact bug this file's own #54/#50/#52-#58 sections each record finding once — sms-api sends an explicit JSON `null` for a nullable column with no value, never an omitted key, and every TypeScript type in this package assumed the opposite (`field?: T | undefined`) — had been fixed three separate times, each with its own local `normalize*` function next to whichever screen happened to render the one field that exposed it. By the time this PR started counting, that was fourteen near-identical functions across twelve files (`routes.ts`, `providers.ts`, `route-simulator.ts`, `app-clients.ts`, `apps.ts`, `roles.ts`, `dashboard.ts`, `opt-outs.ts`, `users.ts`, `senders.ts` ×2, `webhooks.ts` ×2), not the five the issue was filed against — #52/#58 alone added five more after the issue's own count was taken. Two modules, `jobs.ts` and `workers.ts`, had never been caught at all: `JobRecord.dedupeKey`/`leaseOwner`/`leaseUntil`/`lastError`/`startedAt`/`finishedAt` and `WorkerLockInfo.workerId`/`pid`/`heldSince` are exactly the same shape of nullable column, silently unguarded, latent until someone happened to drive the Jobs or Workers screen through a case that renders one.

**`packages/gateway/src/json.ts` is now the single seam — option (1) from the issue's own three, taken as written.** Option (2), adopting the generated `packages/sms-client` (T3), remains the thing that would stop this *class* of bug recurring for good — `OPEN_QUESTIONS.md` §5 still tracks it, unchanged by this PR — but it's blocked on an upstream cratestack release and out of scope here. Option (3), changing the server to omit nulls, was rejected for the same reason the issue itself gives: a breaking API change to fix a client-side assumption, when other consumers may reasonably prefer explicit nulls.

**The hazard the issue asked to be checked before writing a line of code, and the actual mechanism chosen.** A blind recursive `null -> undefined` strip over every response would silently corrupt data if any response legitimately carries a JSON value where `null` is meaningful — most obviously a stored JSON payload forwarded byte-for-byte. Checked directly against `schema/schema.cstack`, not assumed: every field in this codebase that carries free-form or pre-serialised JSON — `WebhookAttempt.payload` (the signed envelope's `data`, forwarded exactly as stored per `hooks.rs`'s own doc — AGENTS.md's own #40 section is explicit that what gets signed must be exactly what gets sent), `cratestack_audit`'s `actor`/`before`/`after`/`primaryKey` snapshot columns (`audit_log.rs`), and `Provider.config` — is declared a plain `String`, never a structured type. sms-api therefore always sends each as a JSON *string* value, and `JSON.parse` on the outer response turns every one into a single opaque string leaf; `normalizeValue`'s recursion only ever descends into a plain object or an array, never into a string's own contents, so these fields are structurally unreachable regardless of what they encode — including a payload whose encoded text contains the literal substring `"null"`. `RawCallback`/`DeliveryReceipt.rawPayload` were checked too and found moot: neither field ever reaches this console at all (`DeliveryReceiptSummary`, `messages.ts`, deliberately omits `rawPayload`). That structural fact is the primary guarantee; `VERBATIM_STRING_FIELDS` (`payload`/`actor`/`before`/`after`/`primaryKey`/`config`) is a second, named guard on top of it, defence in depth for if a future schema change ever turned one of these columns into a genuinely structured type — costs nothing today since skipping recursion into a value that's already a string leaf is a no-op.

**The paged envelope (`{ items, totalCount, pageInfo }`, only `@@paged` models) and the bare array (`Provider`/`Route`, per #54's own finding) both fall out of the same generic walk with no special-casing** — an envelope is just an object whose `items` value happens to be an array of objects, and a bare array is just the top-level value being an array instead of an object; `normalizeValue` doesn't need to know which shape it's looking at. `pageInfo.offset: number | null` normalizes to `undefined` along with everything else — grepped before writing this section, and confirmed nothing anywhere in this codebase reads it, so there was nothing to preserve.

**Every per-module `normalize*` was deleted, not deprecated** — this repo's own standing "hard cutover, not a parallel path" convention. Two exceptions, kept because they are a *different* concern from #221 and would be actively wrong to fold into the generic seam: `senders.ts`'s `foldClearedSentinel` (renamed from the null-folding half of `normalizeSenderId`/`normalizeRegistration`) still folds an explicit `""` back to `undefined` — that's #53/#55's own workaround for cratestack#567 (a generated `PATCH` route cannot distinguish a `null` from an absent key, so this module writes `""` to mean "clear"), unrelated to what `null` means on a `GET`. `webhooks.ts`'s `normalizeEndpoint` still unpacks `eventTypes` from its sentinel-packed wire string into an array — model-specific shape logic, not null-handling.

## The `xtask` PR's own "deliberately not touched" list, finished — `containerize-tooling`

The maintainer's direction went further: no bash script survives *anywhere* in this repo, not just in `ci/`, and beyond that — nothing runs on a developer's host at all; the actual work happens in pinned containers, driven by Compose. `scripts/demo.sh`, `scripts/e2e-integration.sh`, `ci/apply-migrations.sh`, and `deploy/{backup,restore,restore-drill,backup-entrypoint}.sh` — the seven scripts the xtask PR above named and explicitly deferred — are gone. `git ls-files | grep -E '\.(sh|py)$'` now returns nothing, repo-wide.

**Where the line actually got drawn, stated plainly rather than left implicit:** `cargo xtask`/`just`/`docker compose` themselves still run on the host — that's the same accepted exception the xtask PR above already established for `cargo xtask <check>`, extended here to the two thin orchestrators (`just demo`, `just e2e-integration`) that sequence a handful of `docker compose`/`docker` calls. What changed is that every *application* process — Postgres, migrate, sms-gateway, sms-worker, sms-fake-orange, admin, and now backup/restore/the e2e verification tool — runs in a container built from a pinned base image, and the tooling that used to be bash is now either a real Rust binary or a declarative compose file, never both a script and a container wrapping it.

- **`ci/apply-migrations.sh` is simply deleted, not ported.** `app/sms-migrate` already was its Rust equivalent (`AGENTS.md`'s own "rustls, musl, and distroless" section, months earlier) — every caller (`.github/workflows/ci.yml`'s `migrations` job, `justfile`'s `schema-check`, `CONTRIBUTING.md`'s own documented workflow, two runbooks) now runs `cargo run -p sms-migrate` directly. The CI job change is a real, if incidental, strengthening: it now proves the actual production migration binary applies cleanly to an empty database, not a parallel shell-script path that could silently drift from it — the exact "two copies of one concept, only one gets updated" shape this file warns about elsewhere.
- **`scripts/demo.sh` (300 lines: `docker run` by hand, backgrounded host processes, `pnpm exec next dev`, hand-parsed subcommand stdout) became `compose.dev.yaml`** — a third full-stack compose file, deliberately not reusing `compose.yml` (considered and rejected: Compose's multi-file merge semantics for list-typed keys like `ports` were more fragile to verify than a six-line duplicated `postgres:` service, and `compose.demo.yaml` had already independently made the identical call) and structured to mirror `compose.demo.yaml`'s own shape (a chain of one-shot seed/provision services, `--profile console` for R4) with `build:` in place of `image:`. `just demo` is now `docker compose -f compose.dev.yaml --profile console down -v` then `up -d --wait` — no host Rust/Node build step for the running system at all (a developer's own `cargo build`/`pnpm install` for *editing* code is unaffected, obviously; this is about what `just demo` itself does).
- **A real, reproduced BuildKit hazard, not theoretical:** every `app/*/Dockerfile` builder stage deliberately shares one cache-mount id (`cargo-registry-musl`) "so building any one warms the cache for the other three" (their own comment) — true for sequential builds, and a genuine race (`failed to unpack package ...: File exists (os error 17)`) for `docker compose build`'s default parallelism building all of them uncached for the first time at once. Reproduced twice, gone entirely under `COMPOSE_PARALLEL_LIMIT=1`, which `just demo`'s own recipe now sets for its build step. A second, independent finding from the same investigation: giving all seven `sms-gateway`-image services in `compose.dev.yaml` the *same* explicit `image:` tag (rather than Compose's default of one distinct image per service, even for byte-identical `build:` blocks) was necessary — without it, two builds from identical `context`+`dockerfile` intermittently produced different tagged images on this machine, one of them stale (missing a subcommand the source genuinely had).
- **`scripts/e2e-integration.sh` (bash + `openssl dgst -sign` + `curl` + `jq`, hand-rolling RFC 7523 client-assertion signing) became `ci/e2e-integration`**, a small standalone Rust binary (its own Cargo workspace, like `examples/rust`/`sdks/rust/vsms-sdk-rust` — invisible to `cargo check --workspace` by construction) reusing `vsms-sdk-rust`'s own `private_key_jwt` token exchange rather than reimplementing it a second time. **Found live, not assumed, while building it: `VsmsClient::private_key_jwt(base_url, config)`'s own doc comment claims `base_url` backs both the OIDC `/token` endpoint and the REST API — false.** `PrivateKeyJwtTokenStore::new` (`sdks/rust/vsms-sdk-rust/src/token.rs`) derives `token_endpoint` exclusively from `config.issuer`; `base_url` only ever reaches the generated REST client. Confirmed with a real `401 invalid_client` from the real `/token` route when the two values differ. This is the identical "documentation asserts something the code does not do" failure shape this file has now recorded many times over vsms itself, this time in the SDK — flagged as a spawned follow-up rather than fixed here (`sdks/rust/vsms-sdk-rust` is outside this PR's own file ownership). The practical consequence: `ci/e2e-integration` cannot run as a bare host process against `compose.dev.yaml` the way `examples/rust/sms-send` is designed to run against a real, single-address deployment — `sms-gateway`'s own configured issuer has to be the internal Compose DNS name for `admin`'s server-side OIDC calls to work at all, and a host process can't reach that name. Fixed structurally, not worked around: `ci/e2e-integration` gets its own Dockerfile and runs as a one-shot container joined to `compose.dev.yaml`'s own network, where the address it connects to and the gateway's own configured identity are simply the same string.
- **`deploy/{backup,restore,restore-drill,backup-entrypoint}.sh` became `deploy/backup-tool`** (`vsms-backup`, another standalone crate, its own Cargo workspace under `deploy/` since `app/` was out of this PR's ownership) — `backup`/`restore`/`restore-drill`/`schedule` subcommands. `pg_dump`/`pg_restore`/`rclone` stay external processes on purpose (the same reasoning `app/sms-migrate`'s own module doc already gives for *not* reimplementing `psql`'s protocol — these are real binary tools nobody reimplements), but every ad-hoc `psql -Atc` query became a typed `postgres::Client` call (`db.rs`), the JSON manifest became `serde`-typed, and Alpine's busybox `crond` + a hand-written `/etc/crontabs/root` line became an in-process cron-expression scheduler (`cron` crate) with its own `SIGTERM`/`SIGINT` handling — found live while designing it, not assumed: a process that is PID 1 *within its own PID namespace* (which this container's entrypoint always is) is kernel-exempted from a signal's *default* disposition unless it installs a handler, so an unhandled `SIGTERM` would have been silently ignored rather than terminating the process, and `docker stop` would have hung for the full grace period every time. A stronger result than the check was designed to produce, recorded as such rather than silently claiming only the intended path fired. Reverted, rebuilt (confirmed byte-identical image manifest to the pre-sabotage build), re-run clean.

### A real regression, found and fixed: DELETE from the admin console

`packages/gateway/src/rest.ts`'s `deleteResource` (and the hand-rolled equivalents that used to live in `apps.ts`/`users.ts`/`roles.ts`) sent no `If-Match` header at all. Every caller — `deleteRoute`, `deleteWebhookEndpoint`, `deleteApp`, `deleteUser`, `deleteRole` — targets a `@version`'d model, so every one of these delete buttons would genuinely 412 against a real cratestack 0.7.16 gateway. `admin/`, `packages/ui/`, and `docs/design/` were excluded from this PR's scope — `packages/gateway` was not, and that is exactly where the fix belongs: `deleteResource` now acquires the row's current `ETag` via an internal `GET` (reusing `fetchWithEtag`) before issuing the `DELETE` with it as `If-Match` — **the function's own signature is unchanged**, so every existing call site (`deleteRoute`, `deleteWebhookEndpoint`, and `deleteApp`/`deleteUser`/`deleteRole`, the latter three now simply delegating to `deleteResource` instead of duplicating the same request a second time) keeps working with zero screen changes, nothing to collide with the console redesign in flight under `admin/`.

**Honest about the cost, not just the fix.** There is a real TOCTOU window between the internal `GET` and the `DELETE`: a row edited by another operator in that window makes the captured `ETag` stale, and the `DELETE` gets a genuine `412` — that is `If-Match` doing exactly its job, not a bug, but it can fail a delete that would have succeeded moments earlier. A caller that already holds the row's current `version` (every screen does, since it necessarily rendered the row to offer a delete button) could pass it straight through and skip both the round trip and the race — named in `deleteResource`'s own doc comment as the better long-term shape for Phase 2 of the console redesign, needing a signature change and per-screen wiring this interim deliberately doesn't attempt.

**Verified live against a real gateway (`just demo`), both directions, not assumed from reading the mechanism.** A temporary vitest script (not committed) logged in as the demo's own provisioned operator through the real `authorization_code` + PKCE flow, then called the real `deleteResource` inside a real `runWithRequestCredential` scope against the real running `sms-gateway`:

- **Positive case**: created a throwaway `Route`, called `deleteResource` — returned successfully, no throw, no `412`; a follow-up `GET` confirmed a real `404` (the row is actually gone).
- **Negative case**: created a second throwaway `Route`, captured its `ETag` (`"0"`), then a genuine concurrent `PATCH` bumped its version to `1` — simulating the exact TOCTOU race the doc comment names — and a `DELETE` carrying the now-stale `"0"` `ETag` came back `412 PRECONDITION_FAILED`, `"version mismatch: expected 0, found 1"`, straight from the real server. Proof the header is genuinely being honoured, not silently ignored.

`packages/gateway/src/rest.test.ts` gained five unit tests for `deleteResource` covering the same two shapes at the mock level (acquire-and-send, no-version-no-header, 404-on-the-GET-still-attempts-the-DELETE, a stale-`If-Match` `GatewayError` recognisable via `isStaleWriteError`, and the 401-retry-on-the-DELETE-itself case) — 52 tests total in the package, all passing; `tsc --noEmit` and `biome check` both clean.

## Invariants that fail the build rather than production

Three silent failure modes are now loud. Do not delete these without reading why they exist:

- **`cargo xtask parity`** (R2, `ci/assert-state-machine-parity.py` before the `xtask` PR) — every edge in the design doc's state diagrams must exist in `message_state_transitions` / `job_state_transitions`, and vice versa, terminal states included. Drift's first symptom would otherwise be a production `SM001` on an edge that looks legal in the diagram everyone reads. Run with `just parity`.
- **`crates/sms-api/tests/create_inputs.rs`** — constructs every create input exhaustively, with no `..Default::default()`. Adding a `@default(...)` to a caller-settable field silently removes it from `CreateXInput`; `@server_only` removes it from create *and* update (R3). Both become compile errors naming the field.
- **`crates/sms-api/src/errors.rs`** — `map_database_error` turns SQLSTATE `SM001` into `CoolError::Conflict` (409) and `23505` into a named conflict. Untranslated, an illegal transition is a `500 DATABASE_ERROR`, which callers retry and operators read as a gateway fault. Genuine database faults stay 500 on purpose.

**And one failure mode that is still *not* guarded, which is why it keeps happening.** A model whose `@@allow` omits `hasRole('system')` does not error — CrateStack's list-route policy denial is row-level filtering to an **empty array** (see #97's finding on `GET /oauth_signing_keys`), so an internal system-context read just quietly returns nothing, and the calling code behaves as though the table were empty. That has now been found **seven separate times**, always live and never by review: `App`, `AppClient`, `SenderIdRegistration`, `OperatorPrefixRule` (#94), `Provider`, `Job` (#100), `Message` list/detail (#96, which is why #29's claim loop had been returning zero rows for a milestone), and `DeliveryReceipt` (#121). Seven repetitions of one mistake is a missing invariant, not seven oversights — the other three entries above each turned a silent failure into a loud one, and this one has no equivalent. ## Build cost — fixed upstream, keep the pin

**Do not drop below `cratestack =0.5.0`.** On 0.4.x, `include_server_schema!` expansion was **exponential in relation-graph connectivity**, and this schema could not be compiled at all on a 32 GB machine: rustc was SIGKILLed after 20 min 53 s having driven swap from 20 GB to 45 GB. Measured with synthetic chained schemas, `cargo check`, same machine:

| chained models | 0.4.19 | 0.5.0 |
|---|---|---|
| 4 | 13.4 s / 1.70 GB | 8.1 s / 0.48 GB |
| 6 | 568.6 s / 10.49 GB | 1.9 s / 0.40 GB |
| 8 | >600 s, unfinished | 2.5 s / 0.46 GB |
| 16 | — | 4.3 s / 0.71 GB |

Cause was a path-local rather than memoised recursion guard in `cratestack-macros/src/relation/recursive_entries.rs`: `visited` was cloned per branch, so every distinct path through the relation graph re-expanded the whole nested module subtree. Reported as [cratestack#252](https://github.com/cratestack/cratestack/issues/252), fixed in 0.5.0. The whole workspace now builds in ~21 s.

Retained because they are cheap and still correct, not because they are load-bearing any more:

- `[profile.dev] debug = "line-tables-only"` — panic backtraces keep file and line, variable/type DWARF is dropped.
- `[profile.release]` is `thin` / `opt-level = 3` / `codegen-units = 16`, with a `[profile.dist]` for shipped artifacts. Fat LTO plus one codegen unit is the worst case for codegen memory — see [cratestack#250](https://github.com/cratestack/cratestack/pull/250). Note a dependency's profile never reaches us; Cargo honours profiles only from the root workspace manifest, so that setting spreads by copy-paste.
- `CARGO_BUILD_JOBS=4` and `CARGO_INCREMENTAL=0` in CI, and `just` recipes cap jobs locally. Raise with `just jobs=8 check`.

## The three rules

Full reasoning in [CONTRIBUTING.md](CONTRIBUTING.md). In short:

- **R1 — all data access goes through CrateStack delegates. Never raw `sqlx`.** Raw SQL bypasses row-level policy, audit rows, `@@emit` outbox rows and `@version` bumping — all four, silently. Twelve named exceptions (see `CONTRIBUTING.md`'s own table for the full list and reasoning; the four broadest categories are migrations, `pg_advisory_lock`, `LISTEN`/`NOTIFY`, and the `/readyz` probe's bare `SELECT 1`, #157 — it touches no table, so there is no policy to bypass and no audit row to skip, and the delegate alternative would read a real table on an unauthenticated route, which is the DoS amplifier that endpoint must not become). Enforced by `cargo xtask no-raw-sqlx` (`ci/assert-no-raw-sqlx.sh` before the `xtask` PR).
- **R2 — state transitions are proposed by Rust and decided by Postgres.** Legal edges live in `message_state_transitions` / `job_state_transitions`; triggers reject the rest with SQLSTATE `SM001`. Map it to `CoolError::Conflict` → 409.
- **R3 — nothing that must be written can be `@server_only`.** It excludes a field from create *and* update, so such a field can never be populated.
- **R4 — the admin console is optional; the backend must run without it.** Some deployments ship the backends only, with no admin surface — a supported configuration, not a degraded one. No server-side code may depend on the console existing; every operator action needs a `sms-gateway` subcommand, not only a screen; and both the Helm chart and the compose stack must be able to omit the console without a console-only value becoming a hard requirement. Review test: *if `admin/` were deleted from this repo entirely, would this change still work?* Currently satisfied by the code layer and **violated by the deployment layer** — see `CONTRIBUTING.md` R4 for the specifics.
- **R5 — Helm charts are built on `bjw-s` common ≥ v4, as one umbrella chart.** Not hand-written manifests, and not a chart per service: `sms-gateway`, `sms-worker`, `admin` and the migrate/seed jobs are one deployable unit sharing a database, a migration ordering and a secret set, so they ship as one release with several controllers. v4 is the floor because the `controllers`/`route` schema this chart is written against is v4's; earlier majors are an incompatible shape, not a bump. Currently pinned at `4.6.2`, via a **classic HTTP repo dependency — no OCI reference for the library chart exists** (verified against the GHCR API and bjw-s-labs' own release workflow, not assumed).

## Framework constraints that are not in any documentation

Each of these was found by running the toolchain. Each will silently waste an afternoon. Full table with exact error text in [§2.0](docs/architecture.md#20-grammar-and-emitter-constraints).

**Will not compile / will not parse:**

- **Scalar list fields panic the server macro** — `String[]` / `Int[]` give `proc macro panicked: unsupported SQLx value type for this slice`. The parser and migration emitter accept them happily; only `include_server_schema!` fails. Multi-values here are space-delimited strings with **sentinel separators** (`" a b "`, so `.contains(" a ")` can't false-match `ab`).
- **Exactly one whitespace character** between field name and type. No column alignment — `id  Cuid` fails with `invalid type reference:`.
- **The parser is line-based.** An `@@allow` cannot wrap onto a second line.
- **Relation scalars and policy comparisons require type-name equality.** A `String` FK to a `Cuid` PK is a hard error, including through `auth().x` comparisons.

**Will compile, and be silently wrong:**

- **`@@use` instead of `@use`** parses, is retained as an unknown attribute, and does not expand the mixin. No error.
- **A misspelled `@@allow` action is dropped**, and deny-by-default makes that operation unreachable.
- **Unknown attributes are ignored** — a typo'd attribute is a no-op.
- **Enum `@default` values are not checked against variants** — a typo reaches the DDL and fails at `psql` time.

**Shape the schema:**

- **Any `@default(...)` excludes the field from `CreateXInput`** — literals included, not just `dbgenerated()`. A `@default` on a caller-settable field makes it unwritable. Kept only where unsettable is the control: `Message.state @default('accepted')` is why no client can create a message that is already `delivered`.
- **Defaulted fields *are* settable on update.** So `@default(auth().x)` protects creation only.
- **`@pii` / `@sensitive` redact audit snapshots only** — they add no serde attribute, so the field is still returned by the API. Not confidentiality controls.
- **Ids must be lowercase alphanumeric, no separator.** `Cuid` is format-guarded `[a-z0-9]{2,32}` on REST query filters, so a `msg_` prefix makes `GET /messages?id=…` return 400. `cs_cuid()` emits 23 chars.
- **No `@@index`, no triggers, no column defaults** come out of the emitter — all hand-written in `0002_bootstrap`. **Foreign keys changed at `=0.7.8`**: the emitter now writes a plain `ON DELETE NO ACTION` `FOREIGN KEY` into `0001_init` for every `@relation`, so the seven hand-written duplicates left `0002_bootstrap`. The trap, found live: **two `FOREIGN KEY` constraints on the same column enforce independently.** Leaving the emitted `NO ACTION` beside a hand-written `CASCADE` does not resolve to the more permissive one — Postgres raises `violates foreign key constraint` on `NO ACTION` before `CASCADE` ever runs, silently reinstating the block. So the three relations that need cascade (`message_parts`, `delivery_receipts`, `webhook_attempts`) **drop the emitted constraint by name** and replace it, rather than adding a second beside it.
- **`pluralize()` is naive** (`ends_with('s') ? +"es" : +"s"`) and there is no `@@map`. `WebhookDelivery` would become `webhook_deliverys` — the model is `WebhookAttempt` for that reason.
- **`upsert` doesn't exist when the `@id` has a default.** Dedupe is `create` + catching SQLSTATE `23505` via `err.db_sqlstate()`.
- **`SKIP LOCKED` is not expressible.** `.for_update()` is. Claim loops use optimistic CAS on `@version`, treating `PreconditionFailed` as "another worker won" — and **`Forbidden` is ambiguous** (policy denied *or* row gone), so log it rather than folding it into the race branch.
- **`@db_enforce` backs `@length`/`@range` with a real `CHECK` and is a silent no-op on `@regex`.** No error, no warning — verified with an isolated probe schema. Anything pattern-shaped needs a hand-written `CHECK (col ~ '...')` in `0002_bootstrap` instead.
- **0.5.0 changed enum-typed columns from native `CREATE TYPE ... AS ENUM` to `TEXT` + `CHECK (col IN (...))`, silently.** Anything referencing the old type name directly — our `message_state`/`job_state` transition-table columns were — breaks at `psql` time on the next full regeneration with `type "message_state" does not exist`. `cratestack check` and `cargo build` both stay green through it; only applying the migration for real catches it.

## Milestone 0 crates — what was non-obvious

`sms-encoding` and `sms-msisdn` are done ([§3.3](docs/architecture.md#33-encoding--write-this-crate-first), [§3.4](docs/architecture.md#34-msisdn-normalisation)). Findings that weren't in the design doc's prose and would otherwise get rediscovered the hard way:

- **Segment counting is a packing loop, not division.** A GSM-7 escape pair (`€`, `[`, …) or a UTF-16 surrogate pair (emoji) must not straddle a segment boundary. `ceil(length / per_segment)` undercounts by one on exactly the bodies where the straddle happens — see `crates/sms-encoding/src/segment.rs`.
- **Most uppercase accented vowels are *not* in GSM-7, even though the lowercase forms are.** `à è ù ì ò` are single septets; `À È Ù Ì Ò` are not — only `É` made it into the default alphabet. A body that's one segment in sentence case can become UCS-2 the moment it's upper-cased (e.g. shouty confirmation codes). `Ä Ö Ñ Ü` and their lowercase forms are all encodable either case.
- **Normalisation and transliteration are deliberately different passes, and the split matters for correctness, not just policy.** `normalise` (unconditional) only touches characters that are typographically identical to a GSM-7 character — `’→'`, en/em dash → `-`, NBSP → space. `transliterate_to_gsm7` (opt-in per `App.transliterateToGsm7`) additionally strips accents via NFD decomposition + combining-mark removal, which is *perceptible* (`ç→c`) and must never run by default.
- **Cameroon's numbering plan puts a chunk of mobile numbers in the `2xx` range, not `6xx`.** Camtel mobile is `242`/`243`, sitting inside the fixed-line leading digit `2`. A classifier that assumes "starts with 6 = mobile, starts with 2 = fixed" misclassifies it.
- **`63x` and `643`–`649` are syntactically well-formed 9-digit numbers in no assigned block.** They need a distinct outcome (`Unallocated`) from both "wrong length" and "known-but-not-mobile" — collapsing them into a generic parse failure loses the operator-relevant distinction.
- **The `88x` toll-free/shared-cost range is 6–7 digits after the prefix, i.e. 8 total digits, not 9** — the one legitimate 8-digit number in the plan. It has to be special-cased before the generic "8 digits = pre-2014 legacy number" rejection, or every toll-free number gets misdiagnosed as a legacy number that needs a `6`/`2` prefix guess.
- **`OperatorPrefixTable` ships with zero built-in rows on purpose** ([§3.4](docs/architecture.md#34-msisdn-normalisation) is explicit that prefix routing "must never be load-bearing"). The table type does longest-prefix-match lookup only; the actual MTN/Orange/Camtel prefix data belongs in the database, seeded and corrected from observed DLRs, not compiled into the crate.

## Verified toolchain API (don't guess these)

```rust
db.message().find_many()
    .where_expr(FilterExpr::from(message::state().in_([MessageState::accepted]))
                  .and(message::expiresAt().gt(now)))
    .order_by(message::priority().desc())   // appends, doesn't replace
    .limit(n).run(&ctx).await?

db.message().update(id).set(UpdateMessageInput { ..Default::default() })
    .if_match(version).run(&ctx).await?     // required on @version models —
    // but only at RUNTIME, not compile time. `if_match` is a plain
    // `Option<i64>` builder field (`UpdateRecordSet::if_match`,
    // `cratestack-sqlx-0.7.10/src/query/write/update.rs`), defaulting to
    // `None`; omitting the call still compiles and instead returns
    // `Err(CoolError::PreconditionFailed("If-Match header required for
    // versioned model"))` the first time `run`/`run_in_tx` actually
    // executes. #59 confirmed this live while adding `@version` to ten
    // models: `cargo check --workspace --all-targets` stayed green through
    // every pre-existing call site that had never supplied `if_match` for
    // those models (there were none in production code, but several in
    // live-test fixtures) — the compiler cannot see this gap the same way
    // it cannot see a misspelled `@@allow` action. Never trust `cargo
    // check` to have caught a missing `if_match`; grep for every
    // `.update(` call on a model before/after adding `@version` to it, or
    // run the live suites that actually exercise the write.
```

- Filter helpers: `cratestack_schema::<model_snake>::<fieldNameVerbatimCamelCase>()`.
- Ops: `.eq .ne .lt .lte .gt .gte .in_ .is_null .is_not_null .eq_or_null .contains .starts_with .is_true .is_false`. No `not_in`, `between`, `ilike`.
- `.and()` / `.or()` are on `FilterExpr`, not `Filter` — wrap with `FilterExpr::from(...)`. Separate `where_*` calls are always ANDed.
- Enum variants are lowercase-verbatim: `MessageState::accepted`. `Int` is `i64`. Nullable setters are `Option<Option<T>>`.
- Transactions: every builder has `.run_in_tx(&mut tx, &ctx)`; audit and outbox rows join that transaction. `cratestack::run_in_isolated_tx(pool, isolation, closure)` — the closure takes an owned tx and must return `(T, tx)`.
- `@@emit` is a **real transactional outbox** (row written in-tx, survives process death), but delivery is **synchronous, blocking the mutation, and not panic-isolated**, with no `SKIP LOCKED` on drain and no retry cap. Subscribers must be trivial, idempotent, and must not panic.

`cratestack migrate diff` has **no `--check` or dry-run mode**; its only flags are `--schema`, `--out-dir`, `--backend`, `--name`, `--allow-destructive`.

**"Parses" is not "compiles."** `cratestack-parser` and `cratestack-migrate` both accept schemas that `include_server_schema!` refuses. Once `crates/` exists, `cargo check -p sms-api` is the real gate. Expanding all 16 models is memory-hungry — budget for it.

## Conventions

- Commits: imperative subject, body explaining *why*. Record framework surprises in the commit body and in §2.0 — that table is the most valuable thing here for whoever comes next.
- Schema changes ship with their migration and a design-doc note if a decision changed.
- New R1 exceptions need reasoning in the PR, not just an allowlist edit.
- **Every PR checks [`docs/roadmap.md`](docs/roadmap.md) and updates it when the PR changes the sequencing picture.** The check is mandatory; the edit usually is not — most PRs change nothing there, and saying so in the PR is a complete answer. Update it when the PR:
  - **completes a milestone or passes its §12 gate** — the phase table's status column, and the snapshot date above it;
  - **resolves, adds or reframes a blocker or decision** — the decisions table, and the "what actually blocks first production traffic" list if the answer moved;
  - **changes a dependency** — something that was blocked no longer is, or a new constraint appears. The mermaid graph's arrows are claims about what genuinely blocks what, not decoration;
  - **lands infrastructure ahead of its milestone** — add it to "Already built, ahead of its milestone", which exists so the next person doesn't rebuild it after reading the milestone counts as complete.

  **Do not update it merely because a story closed.** GitHub owns live status and is always more current; the roadmap deliberately carries only a dated snapshot, and turning it into a changelog would recreate the drift problem it was written to avoid — this file has already recorded four separate incidents of documentation asserting something the code did not do. When you *do* touch the status column for one of the reasons above, move its date to the day you verified it, and verify against `gh`, not memory.

## Open questions blocking later milestones

1. **Hosting location.** Law No. 2024/017 requires prior authorisation for *all* cross-border personal-data transfers, and "legitimate interest" is not a lawful basis. Cameroon-hosted is the safe default. Needs an answer before production.
2. **Own ART title?** Determines whether direct SMPP (milestone 7) exists at all.
3. **10-year traffic retention (Law 2010/012 art. 25) vs 90-day minimisation.** Split-ledger proposal in §10 needs a lawyer.
4. **Does `authkestra-op` stay?** All machine auth runs through it, and it needs a custom `ClientStore` to work around a grant-type authorisation bug, plus `/token` rate limiting it lacks, with no revocation endpoint and no proof-of-possession. Compare against Keycloak / ZITADEL before milestone 1, not after.
5. **#72: how long should a `ConsentRecord` be kept, and should its plaintext `msisdn` eventually be purged the way `Message.msisdn` is?** No `@@retain` was added — proof of consent plausibly needs to outlive the relationship plus a limitation-period buffer, which is a different answer than `Message`'s 90-day content-minimisation window, and nobody has decided what that answer is. `msisdnHash` (not `msisdn`) is what `Procedures::ensure_consent_on_file` actually matches against, so a future purge job for this model is possible the same way `purge_retention` (#67) is for `Message`, once the retention period itself is decided. See `ConsentRecord`'s own `schema.cstack` comment and `docs/architecture.md` §2.7.
